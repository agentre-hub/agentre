# 设备端口转发：从控制台与桌面端访问设备上跑着的本机服务

> Status: Approved
> Owner: 桌面端 / 服务端 / 控制台前端
> Last updated: 2026-09-08

**Objective:** 让用户声明「某台设备的某个端口」，然后在浏览器控制台或 agentre 桌面端里直接访问那个本机服务，包括它的长连接与 WebSocket。

**Hard invariant:**

- 设备侧只连 `127.0.0.1` 上**已在这台设备上声明过的那个端口**。目标主机不由请求携带，端口不在声明集内一律拒绝。
- 一条转发流不得拖垮同一条连接上的其他会话：大文件下载与长连接必须有背压。
- 转发能力对两类客户端（浏览器控制台、桌面端）与两类目标设备（agentred、另一台桌面端）一视同仁，不为其中某一组合另开一套语义。
- 新增迁移一律追加，不修改既有迁移——设备侧的 `internal/daemon/migrations` 同样适用。

## Problem

1. **设备上跑着的服务只有坐在那台机器前才看得见。** 用 agentred 在远端机器上干活时，agent 起的 dev server、临时 HTTP 服务、预览进程全都停在那台机器的 `127.0.0.1` 上。两个客户端都能看到 agent 说「服务已启动在 3000 端口」，但都没有办法访问它——远程干活这件事在「验证跑起来的东西」这一步断掉。

2. **中继上已有「把请求转给本机服务」的先例，但它够不着用户。** `internal/daemon/handlers/mcpproxy.go` 与 `wire/mcptunnel.go` 做的正是这件事，但它是内置工具 MCP 专用的、缓冲式的、路径写死在 `/mcp/<name>/`，用户配置不了。

3. **没有任何地方承载「哪台设备的哪个端口」。** 服务端 `internal/api/` 下没有这类路由；agentred 与桌面端上也没有这样一张表。

## Actors and user stories

1. 作为在远端设备上跑 dev server 的用户，我希望在浏览器里点一下就能打开它，这样我能亲眼看到 agent 改出来的界面。
2. 作为在桌面端盯远端会话的用户，我希望同一件事在桌面端也做得到，这样我不必为了看一眼页面切去浏览器控制台。
3. 作为用着热更新开发流的用户，我希望转发下的 WebSocket 也通，这样改一行代码不必手动刷新。
4. 作为账号所有者，我希望只有我自己能访问我声明出去的端口，这样这个入口不会变成一个对外的洞。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | **映射存在被访问的那台设备上**，不存在服务端 | 用户决定。谁被转发谁持有，与 `remotefs.*` / `workspacefs.*` 同一条路子（都是「问那台机器」）。服务端因此不需要新表与迁移，R19 的守卫面完全不碰；更关键的是桌面端可以**局域网直连**设备（`client.DialProtobuf`），那条路上根本没有服务端，映射若只存服务端，桌面端在直连场景下就用不了转发。Rejected: 存在服务端 —— 直连场景读不到；Rejected: 设备持有 + 服务端另存一份索引 —— 同一件事两个存储点，会漂 |
| 2 | 访问地址形如 `/fw/<设备>/<端口>/*`，设备与端口都在 URL 里 | 决策 1 的直接后果：服务端没有映射表，必须能从 URL 自己解析出「转给谁、转到哪个端口」。端口不是秘密，鉴权从来靠登录态而不靠地址不可猜；端口有没有被声明由设备判 |
| 3 | 服务端用路径前缀，**桌面端为每条映射单开一个本机端口** | 两个宿主的约束不同，不强求同形。服务端发不出端口给浏览器，只能用路径前缀（用户已就其代价做过决定，见「安全」）。桌面端能 `net.Listen`，给每条映射一个专属的 `127.0.0.1:<随机端口>` 就消掉了路径前缀的两个毛病：被转发应用的绝对路径资源（`/assets/x.js`）正常，且不会与本机网关自己的 `/ctl/*`、`/mcp/*` 撞车。这也正是 `ssh -L` 的形态，用户对它有预期。Rejected: 桌面端也用路径前缀挂在既有网关上 —— 绝对路径资源会打到网关根上并撞它自己的路由 |
| 4 | 接受「被转发应用与控制台同源」这一风险，不加 `Content-Security-Policy: sandbox` | 用户决定（明知取舍），仅适用于**服务端**那条路径前缀。见「安全」。桌面端走独立端口，天然跨源，不存在这个问题。Rejected: 加 CSP sandbox —— 会把被转发应用压进不透明源，它自己的 cookie / localStorage / 登录态一并失效 |
| 5 | 支持流式与 WebSocket，而不是缓冲式请求/应答 | 用户决定。缓冲式（MCP 反向隧道那种形状）带不了 HMR、SSE 与大响应。Rejected: 一轮先做缓冲式 |
| 6 | 转发流照 `terminal.*` 的形状建模：一条 open 请求开流，此后数据双向流动，close 收尾 | 中继上已有这一族的完整先例（`RPC_METHOD_TERMINAL_OPEN/WRITE/CLOSE` + `TerminalDataNotification`），含它的背压与断连处理。Rejected: 为转发新造一套流语义 |
| 7 | 宿主在请求行与响应头这一层理解 HTTP，协议升级之后退化成纯字节管道 | 服务端要剥掉路径前缀，两端都要改写 `Host`；而 `101` 之后的内容不再是 HTTP，宿主没有立场解释它 |
| 8 | 端口白名单在**设备侧**判定，客户端不持有授权 | 设备是声明的持有者也是最终执行者。任何一条指向未声明端口的 open 都在落地前被拒，不依赖调用方做对 |
| 9 | 控制台的入口是**设备卡展开区里的一个小节**，与「能跑的 Agent」「项目」「对话」并列 | 设计稿 C1，对着 `agentre-server/frontend/src/pages/Devices.tsx` 的真实结构定的：`/devices` 是一列可展开的设备卡，**不存在**设备详情页，也没有页签。Rejected: 新开设备详情页或页签 —— 为一个小节引入这一页今天没有的一层导航 |
| 10 | 桌面端的入口是 `DeviceActionMenu` 里的一项，点了在设备行下展开一个子块 | 桌面端已有完全同形的先例：`remote-devices/device-action-menu.tsx` 的「供应商同步」项切换 `DeviceProvidersSync`，后者渲染成行下的 `rounded-md border bg-secondary/40` 子块。Rejected: 在设置里另开一页「端口转发」—— 映射属于某台设备，脱离设备行无处安放 |
| 11 | 桌面端点「打开」拉系统默认浏览器 | 用户决定。dev server 本来就该在真浏览器里看——DevTools、拣元素、扩展都在那里。零新增 UI（`BrowserOpenURL` 现成）。Rejected: 桌面端内嵌 webview 标签 —— 要新增一种标签类型，且没有 DevTools |
| 12 | 访问地址本身只提供复制；「打开」是行上独立的动作 | 设计稿 C1。地址的常见去处是粘到别处，不是就地点开；两件事挤在同一个元素上会让复制变成误触 |
| 13 | 界面**不常驻**同源风险提示 | 用户决定。风险记录在「安全」一节；界面里长期挂一条改不掉的警示，第二天就会被无视，而它又占掉列表最显眼的位置。Rejected: 列表页脚常驻一条；新增弹窗里说一次 |
| 14 | 两张失败页都给「刷新」与「回到设备」两个动作 | 设计稿 C2。两种失败都可能自己好转（机器回来、服务起来），刷新有意义；而用户此刻在一个空白的转发地址上，需要一条回得去的路 |

## 映射的声明与生命周期

一条映射是**被访问设备上的一条声明**：这台机器允许把它 `127.0.0.1` 上的某个端口转出去。任何一个有权连上这台设备的客户端（浏览器控制台、桌面端）都能列举、新增、启停与删除它，改动落在那台设备上，另一个客户端下次列举就看得到。

**前提**：用户在设备的端口转发入口里。**动作**：新增一条映射，填端口与一个用于辨认的名称。**结果**：那台设备记下这条声明，客户端拿到一条可复制、可打开的访问地址。

- 端口在一台设备下唯一。
- 映射有启用开关。停用的映射保留声明，但访问一律拒绝。
- 删除立即生效：正在进行的转发流被关闭。
- 设备被解除配对或吊销后，客户端不再够得着它，它名下的映射随之不可用；声明本身留在那台机器上。

## 两端的入口

两端呈现同一批映射（它们读的是同一台设备上的同一份声明），形态各自跟随所在宿主：

**控制台**：设备卡展开区里的「端口转发」小节，与相邻两节同为等宽小字标题 + 紧接其下的内容，节间用同一条分隔线。每行给端口、名称、访问地址、启用开关与操作。

**桌面端**：`DeviceActionMenu` 里新增「端口转发」一项，点了在设备行下展开一个子块，形态与「供应商同步」子块一致。行的内容与控制台同构。

三种非常态两端一致：

- **还没有任何映射**：一句「这台设备上还没有端口映射。」加一个新增入口——与控制台同一展开区里「这台设备上还没有能跑的 Agent。」同形。
- **设备离线 / 够不着**：一句离线说明，**不出新增入口**（点了必然失败的入口不该渲染），已经列出来的映射整行保留、只是打不开。**但首屏就离线时列表是空的**——决策 1 把声明放在被访问的那台设备上，够不着就读不到那份声明，客户端手上没有可列的东西。只有「先列举成功、随后某个动作撞上离线」这条路径才保留得住已列出的行。两个宿主同此一条。
- **停用的映射**：整行保留，但不出现「打开」。

设计源：`agentre.pen` 的「文件打开与端口转发」分区 —— `C1 控制台 · 设备 · 端口转发`（Light / Dark）、`C2 控制台 · 端口转发 · 新增与失败`、`C3 桌面端 · 远程设备 · 端口转发`（Light / Dark）。

## 访问与鉴权

两个宿主各有一条访问路径，共用同一套设备侧判定。

**控制台**：浏览器请求 `/fw/<设备>/<端口>/<任意路径>`。服务端按序校验，任何一项不过就以对应的失败结束，不再往中继上发任何东西：

- 没有有效登录态 → 拒绝。
- 该设备不属于当前账号 → 拒绝。
- 设备当前不在线 → 回一个说明设备够不着的错误页，可重试。

通过之后，服务端把 `/fw/<设备>/<端口>` 前缀从路径上剥掉，将剩余路径、方法、请求头与请求体经中继交给那台设备。

**桌面端**：用户点「打开」时，桌面端在本机网关（`internal/pkg/httpgateway`）之外为这条映射绑一个 `127.0.0.1:<随机端口>` 的专属监听，然后用系统默认浏览器打开它。这个监听：

- 只绑环回地址，不对外。
- 生命周期跟随这次打开：映射被停用 / 删除、设备离线、或 App 退出即关闭，与网关 token「仅在内存中维护，App 退出即失效」同一口径。
- 收到请求后原样（不剥前缀——它没有前缀）经桌面端**已有的那条连接**交给设备，直连或经中继都可以，两者收敛成同一个 `protorpc.Conn`。

## 流式与 WebSocket

- **响应体流式返回**：设备读到多少就带回多少，宿主边收边写给浏览器。大文件下载不在任何一端整体缓冲。
- **请求体流式送达**：上传同理。
- **协议升级**：被转发服务回 `101 Switching Protocols` 时，宿主把这条连接交出去，此后两个方向都是纯字节转发，不再解释内容。WebSocket 因此可用，HMR 随之可用。
- **背压**：任一方向的消费者跟不上时，转发流自身减速，而不是把承载它的连接顶死或无界堆积。同一条连接上的会话流不受一条大传输影响。

## 断开与失败

每一种断开都要有确定的收尾，不留悬挂的流：

- **浏览器断开**（关标签、取消下载）→ 关闭对应的转发流，设备侧随之关掉它到本机服务的连接。
- **设备离线 / 连接断开** → 转发流结束；正在进行的 HTTP 响应以截断结束，已升级的连接随连接关闭而结束（**不**补一个 WebSocket 关闭帧——决策 7 明写宿主在 101 之后没有立场解释内容，而生成关闭帧必须解释并序列化 WebSocket 帧。浏览器因此看到 1006）。
- **本机服务不在监听**（端口写错了，或服务没起）→ 设备侧连不上，如实回一个「设备上这个端口没有服务在监听」，而不是一个笼统的失败。
- **映射被删除或停用** → 正在进行的流立即关闭；桌面端那条专属监听一并关掉。

「设备离线」与「端口上没有服务」是用户真正会撞上的两种。**在控制台那条路径上**，它们各自是一张完整的页面（设计源 C2；用户此刻在浏览器标签里，四周没有宿主的外壳）：说清是哪一种失败、下一步该做什么，并给「刷新」与「回到设备」两个出口。两者的区别必须说出来——一个要等机器回来，另一个要去把服务起起来，混成一句话用户就不知道该做哪件事。**桌面端那条路径只要求把两种失败分开说**——它的「回到设备」在浏览器里没有一个去得了的地址，完整页留给控制台。

## 设备侧的目标限制

设备侧（agentred 与桌面端共用同一份实现——两类设备都可能是被访问的一方）只接受这样的 open：目标主机恒为环回地址、端口来自这台设备自己记下的声明集。请求里不携带主机，端口不在声明集内一律拒绝。这条限制不依赖任何客户端做对。

## 安全

**这一节是同源风险唯一的记录处（决策 13）：界面里不出现它。**

**已知并接受的取舍（决策 4），只发生在控制台那条路径上**：路径前缀让被转发的应用与控制台同源。会话票是 HttpOnly + Secure + SameSite=Lax，被转发应用的脚本读不走它；但同源的 `fetch` 会由浏览器自动带上那张票，因此**设备上被转发的那个服务里的任意脚本，能以当前用户身份调用控制台的接口**。用户在明知这一点的情况下选择了路径前缀，理由是转发的只是自己机器上自己起的服务。改变部署形态（例如把控制台开放给团队）时需要重新评估。

桌面端不受这条影响：每条映射一个独立的环回端口，与桌面端自己的本机网关天然跨源。

其余：

- 控制台的访问地址不可分享——它只在登录态下有效，换个人打开同一条 URL 得到的是拒绝。
- 桌面端那条 `127.0.0.1:<端口>` 地址只在本机有效，且随这次打开结束而失效。
- 服务端不落库、不记录被转发的内容正文。
- 服务端这一轮**不新增任何表、任何迁移**，其响应面不变——R19 的守卫面因此不碰。

## 数据

映射存在被访问的设备上：端口、名称、启用位、时间戳。

**没有所有者标识。** 那张表整张落在这台设备自己的库上，设备身份由「这是哪个库文件」回答；而上面「映射的声明与生命周期」一节写明任何一个有权连上这台设备的客户端看到的都是同一份、不按来源拆分。再放一列会是恒定值，不表达任何区分。既有设备侧表上的`peer_fingerprint` / `device_fingerprint` 是另一种形状——一台设备的库里混着多个来源的行时才需要它们。

- **agentred**：追加到 `internal/daemon/migrations`，不修改既有迁移；DDL 用原生 SQL。
- **桌面端**（作为被访问的一方）：追加到桌面端自己的 `migrationList()`，同样只追加。

## Out of scope

- 任意 TCP 隧道（数据库、SSH 等非 HTTP 协议）。
- 可分享的公开链接、临时访问令牌。
- 自动探测设备上正在监听的端口。
- 从 agent 输出里自动识别 `http://localhost:PORT` 并自动建映射。
- 转发到 `127.0.0.1` 之外的任何地址。
- 桌面端内嵌 webview 打开被转发页面（决策 11 走系统浏览器）。
