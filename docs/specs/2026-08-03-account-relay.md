## 问题与目标

**目标：让 agentred 归属到用户账号，使同账号的任意客户端都能跨网段连上它并同时使用，而 LAN 直连与离线可用性不因此退化。**

**硬不变量：同一个客户端无论走直连还是中转，在 daemon 眼中必须是同一个对端标识；路径切换不得使前置规格的事件游标失效。**

### 问题

1. **信任关系只有 LAN 配对，与账号无关。** `internal/daemon/rpc/auth.go` 只有两种握手：`auth.pair`（配对码换 `DeviceToken`）与 `auth.connect`（token + 指纹），凭据落在 `state.PairedPeers[设备指纹]`（`state/types.go:13,28-33`）。换一台设备就要重新拿配对码，浏览器则完全无法参与——它没有地方存 `DeviceToken`，也走不了配对码流程。
2. **跨网段完全不可用。** `internal/daemon/rpc/transport_hub.go` 整个文件只有一段注释，标记 Hub 中转为未实现的扩展点。产品界面已经把这件事承诺出去了：设备面板的描述文案写着「LAN 同网段直连，Cloud 中转跨网段（v0.3+）」（`frontend/src/i18n/locales/zh-CN/common.json` 的 `remoteDevices.panel.description`），而实现不存在。
3. **`Conn` 与单条 websocket 硬绑。** `rpc/conn.go:28-42` 的 `Conn` 直接持有 `*websocket.Conn`。中转下 daemon 只有一条到 server 的连接却要承载多个逻辑对端，当前结构无法表达。
4. **daemon 的推送仍是每条会话一个目标、不做多客户端共享。** 前置规格已把 handler 注册改成 per-conn 私有 registry（`transport_lan.go:72` 的 `s.opts.Registry.Clone()` + `daemon.go` 的 `bindConn` 把 `runtime.*` 挂到 `c.Registry()` 上），会话通知也改成按会话解析属主连接（`connRegistry` 的 `live`/`claims`，`daemon.go` 的 `ownerOf` / `routerFor`）。但每条会话在任一时刻仍只有一个推送目标，**不向多个客户端扇出**（`daemon.go` 的 connRegistry 注释自陈「本轮规格的非目标仍排除多客户端同时接入」）；会话可见性默认限定在创建它的对端。多客户端同时消费同一批会话、账号级可见性，仍属本规格。
5. **MCP 反向隧道的路由仍是全局启发式，多客户端下会串道。** 前置规格已把全局 `mcpNotifier` 换成 `connRegistry.tunnelTarget()`（`daemon.go` 的 `tunnelTarget`）：按「最近被认领的那条会话的属主连接」定目标，没有认领时回落到最近完成鉴权的活连接，答错时返回面向 LLM 可读的工具错误而非裸 503。单客户端下正确；多客户端下「最近被认领」是全局启发式——两条会话分属 A、B 时，会把 A 的工具请求发给 B。且隧道请求（`mcpproxy.go` 的 `NewMCPTunnelHandler`）身上**没有会话标识**（路径是 `/mcp/<server>/`，鉴权头是 desktop 签的不透明 token，daemon 既签不了也验不了），要做按会话路由，请求必须带上会话身份——本规格需要为它补上。
6. **agentre-server 没有任何 websocket 能力。** cago 的 `server/mux` 只有 HTTP 路由（`binding.go` / `http.go` / `middleware.go` / `router.go` / `struct.go`），没有 upgrade；`agentre-server` 全仓库检索不到 websocket 依赖。中转的两个端点都要从零建。
7. **账号侧已经就绪，但缺一个消费者与一个端点。** `agentre-server` 已有 `users` / `user_identities` / `devices` / `device_tokens` / `device_flow_codes` 五张表、完整 RFC 8628 端点（`/v1/oauth/device/{authorize,token,approve,deny,pending}`）、`internal/pkg/jwt` 的 RS256 签发、`middleware/device_jwt.go` 的设备 JWT 鉴权与 `jwt_blacklist:<jti>` 吊销表（:48-52）。**唯独没有公钥分发端点**，所以 daemon 无法离线验签；而 `devices.fingerprint` 与 daemon 的 `DaemonFingerprint(uuid)`（`rpc/auth.go:57-60`）本就是同一个概念，两边从未接上。

## 用户流程

### 认领一台 agentred

在远端机器执行登录命令，终端打印用户码与验证地址。用户在任意浏览器打开该地址、用 GitHub 登录并批准。daemon 轮询换到凭据，在账号下登记为一台计算节点，随后保持一条到 server 的出站长连接。这台机器从此对该账号的所有客户端可见。

### 桌面端登录

桌面端走同一条设备授权流。**不使用浏览器 OAuth 回调**——那需要桌面端起一个 HTTP listener 接收 callback，直接违反 `docs/architecture.md` 中「前后端只走 Wails binding，不得添加 HTTP 风格 app API」这条可被一行命令检验的不变量。凭据存入既有的系统钥匙串封装。

### 连上一台 daemon

客户端**同时**发起直连与中转两条尝试，先建立的那条胜出，另一条丢弃。不做「先探测再决定」：探测本身就是一次连接，探完再连等于连两次；而且同网段不等于可达（防火墙、VPN 分流、多网卡），只有真正连上才作数。

### 路径切换

从办公室 wifi 走到 4G，直连断开、中转接管。因为客户端在两条路径上呈现同一个对端标识，daemon 眼中仍是同一个对端、同一批会话，前置规格的游标继续有效，切换后按游标补齐即可。这是本规格的硬不变量。

### 多客户端同时在场

桌面与手机同时连着同一个会话。双方都收到实时事件；任一方回答待决策，另一方通过事件流看到它被解决；双方的补充指令按既有队列语义排队。任一方发出的用户消息在另一方的界面上带来源设备标识。

### server 不可用

server 挂掉、或客户端与 daemon 都在内网而外网不通时：中转路径不可用，直连路径不受任何影响。daemon 用缓存的公钥离线验签，照常接受同账号客户端。已登录客户端在凭据过期前一直可用。

### 未认领的 agentred

尚未登录账号的 daemon 仍可用配对码本地使用——这不是遗留兼容，而是必需：新装的 agentred 还没有凭据，而登录需要网络，完全离线的首次使用只有配对码做得到。这类机器只对完成过配对的那台客户端可见。

## 范围

- **agentred**：登录子命令与设备流客户端、账号归属与公钥缓存、第三种握手模式、出站长连接与重连、帧复用器、`bindConn` 去单客户端化、MCP 隧道按会话解析、可见性按认领状态分流。
- **agentre**（`rpc` 层）：`Conn` 与具体传输解耦。
- **agentre**（桌面端）：设备流登录与凭据存储、中转 transport、并发选路、设备面板改造、他端消息来源标识。
- **agentre-server**（后端）：公钥分发端点、两个 websocket 端点、Redis 寻址与帧总线、daemon 在线态与过期。
- **agentre-server**（web 前端）：设备管理页（列出、解除授权，承载 R4 的延迟说明）、设备授权批准页的风险文案强化（**后被 2026-08-08 裁决改为「无条件单档」，见「界面与交互」一节的 superseded 说明**）。

## 非目标

- **web 会话客户端。** 浏览器如何换取一份能连 daemon 的凭据、以及会话界面本身，整个属于下一轮——本规格的三类客户端里，浏览器只到「登录并管理设备」为止。
- **端到端加密。** 已定为中转明文可转发，见实现决策 6。
- **一台 daemon 归属多个账号。** 见实现决策 3。
- **即时吊销。** 离线验签的必然代价，见 R4 与安全一节。
- **LAN 配对机制本身的改造。** 现有配对码流程一行不改，只在其之上新增账号路径。
- **前置规格未覆盖的会话语义。** 事件补齐、待决策幂等、隧道不可达时的工具错误均由前置规格定义，本规格只做多客户端下的路由。

## 行为要求

### R1 — daemon 归属唯一账号

daemon 完成登录后记录唯一的归属账号。已归属的 daemon 拒绝第二个账号的登录，除非先显式解除归属。未归属的 daemon 不接受任何账号凭据，只接受配对码路径。

### R2 — 第三种握手模式，本地验签

在既有的 `auth.pair` / `auth.connect` 之外新增一种握手：客户端出示账号签发的凭据，daemon 用缓存的公钥本地验签，并校验凭据中的账号与自身归属账号一致。既有两种模式的行为与代码不变。

### R3 — 验签不访问 server

上述验签在 daemon 与 server 之间零网络往返。公钥在登录时获取并缓存，此后仅在 daemon 主动刷新时更新。server 不可达不影响任何已缓存公钥的 daemon 接受客户端。

### R4 — 吊销不即时，且这一点必须被说明

daemon 在线时定期拉取吊销列表并本地生效；离线期间无法感知新的吊销，凭据在其有效期内仍被接受。因此签发的访问凭据必须是分钟级短有效期，靠刷新续期。**产品界面在解除设备授权时必须告知该延迟**，不得让用户以为点击即刻生效。

这条延迟的适用面后来被 R19 收窄：**中继连接这一路是即时的**（撤销后一个心跳内断连，重连被拒），残留的只有「撤销时不在线、拿着未过期凭据在本地做事」的那台机器。界面文案仍要保留延迟说明——它对离线机器依然成立，而用户没有办法在点击的那一刻知道对方在不在线。

### R5 — 两条路径上对端标识一致

同一个客户端经直连与经中转连接同一台 daemon 时，daemon 解析出的对端标识必须相同。桌面端在账号下登记设备时，其指纹取自它已有的 LAN 配对指纹，不另行生成。

### R6 — 并发选路，先到者胜

客户端连接一台 daemon 时并发发起直连与中转尝试，第一条成功建立的胜出，其余立即关闭。任一路径不可用不构成连接失败，两条都失败才算失败，且错误信息需分别说明两条路径各自的失败原因。

### R7 — 中转用外层信封，不改动既有帧结构

中转链路上传输的是包裹了通道标识的外层信封，其内容是原样的既有 JSON-RPC 帧字节。既有帧结构不新增任何字段。外层信封只存在于 server 与 daemon 之间，两端之外不可见。

### R8 — `Conn` 不再绑定具体传输

`Conn` 依赖一个帧读写接口而非具体的 websocket 类型。LAN 直连提供 websocket 实现，中转提供虚拟通道实现。**`Conn` 之上的一切——方法注册表、业务 handler、握手、通知——不感知自己坐在哪种传输上**，改动不得外溢到这些层。

### R9 — 帧总线跨实例可达

客户端与 daemon 连在不同 server 实例上时，帧仍能双向送达。寻址与转发经 Redis，使普通负载均衡即可工作，不要求粘性会话或按实例可寻址的主机名。

### R10 — 不限制并发客户端数

同一台 daemon 可同时接受任意数量的同账号客户端。server 与 daemon 均不设并发上限。

### R11 — MCP 隧道按会话解析到发起端

内置工具的反向隧道请求路由到**发起该会话的那个对端**，而非任何「当前活跃」的连接。会话记录其发起对端。该对端不在线时，按前置规格返回语义明确的工具错误。

### R12 — 已认领 daemon 的可见性是账号级

已归属账号的 daemon 上，任一同账号客户端可以看到并操作该 daemon 上的全部会话，无论会话由哪个对端发起。前置规格中「查询限定在调用方自己的对端范围内」的默认在此被放宽——放宽的是过滤条件，会话主键结构不变。

### R13 — 未认领 daemon 保持对端级可见性

未归属账号的 daemon 没有账号概念，其上的会话仅对创建它的对端可见，与前置规格一致。

### R14 — 出站链路故障不影响本地

daemon 到 server 的长连接断开时：本地正在运行的会话不受影响，LAN 直连路径不受影响，daemon 按退避重连并在恢复后重新登记在线态。

### R15 — 设备面板一行一台机器

同一台 daemon 同时存在于 LAN 配对与账号归属两个来源时，在设备面板合并为一行，靠设备指纹判定同一性。该行呈现它的**可达路径**而非凭据来源：当前使用中的路径高亮，尝试过但不可达的路径标为失效。

### R16 — 路径信息只在设备面板

直连与中转的区别在设备面板呈现，不进入聊天界面。它是设备属性，不是会话事件。

### R17 — 他端用户消息标明来源

非本机发出的用户消息在转录流中带一个来源设备标识；本机发出的不带，呈现与今天完全一致。单客户端使用时界面零变化。

多客户端会让用户看到自己「没发过」的消息凭空出现，这是本规格新引入的困惑，不标来源用户无法自行理解。

### R18 — daemon 不保存用户身份信息

daemon 侧只保存账号标识与验签公钥，不保存用户名、邮箱、头像或任何可识别个人的字段。daemon 不需要知道用户是谁，只需要判定「这份凭据的账号等于我的归属账号」。

### R19 — 解除归属与解除授权是两个不同的动作，都必须存在

**解除授权**（在账号一侧）：用户在 web 端的设备管理页撤销某台设备的凭据。撤销后该设备无法再刷新，现有访问凭据在其短有效期内仍可能被离线的 daemon 接受——确认文案必须说明这一点（R4）。

**解除归属**（在 daemon 一侧）：在远端机器上执行的本地命令，清除 daemon 的账号归属与缓存公钥，使其回到未认领状态。这是 R1 中「先显式解除归属」所指的动作，也是换账号、转让机器、以及账号侧已删除设备后清理 daemon 本地残留的唯一途径。

**本地清理不依赖网络**——这条保证不变，断网时解除归属照常完成。但它会**先尽力通知账号侧解除授权**（用户裁决 2026-08-16）：连得上就顺带把账号里那台设备一并撤掉，连不上只提示一句，绝不阻挡本地清理。注意它的前置条件是 daemon 已经停了，存盘的访问凭据多半已经过期，因此这一步要先用刷新令牌换一张新的再调；换来的那张不落盘（下一步归属信息就要被清空）。

这样两侧走的是**同一条服务端路径**，「解除授权时清掉只属于那台设备的行」（工作区同步规格 R14）对二者一视同仁，不需要第二套实现，也不会产生行为差异。

两者仍不能互相替代：账号侧撤销不会让**离线**的那台机器知道自己已被撤销；daemon 侧解除在**连不上账号时**也只清得掉本地，账号下那条设备记录仍需用户去控制台撤销。

**对在线的那台机器，撤销即刻生效。** 撤销之后一个心跳之内，它已经建好的中继连接会被服务端主动断开（关闭码可与网络中断区分），它照常退避重连、而重连会在握手处被拒。因此「凭据在短有效期内仍可能被接受」这条残留只对**当时不在线、事后才回来**的机器成立——它回来时握手同样过不去，真正的窗口是它在离线期间用手上那份凭据能做的事。同一条收尾也覆盖浏览器：用户登出后，该次会话建立的中继连接一并被断开，不牵连同账号的其它浏览器。

判据取的是撤销方**本来就会写**的共享状态（凭据黑名单、会话记录），由持有连接的那个服务端副本自行复查，因此不依赖「撤销请求恰好落在持有连接的那个副本上」，也没有一条会静默失败的踢人投递路径。复查失败（如缓存不可达）时**不断连**：撤销本身早已生效，这里只是收尾，一次抖动把全账号连接一起踢下线比晚一个心跳更糟。

### R20 — 在线态自动过期，不留幽灵

daemon 的在线登记带存活期限，由 daemon 的出站连接持续续期；连接断开或进程消失后，登记在超时后自动消失，不依赖任何显式清理。server 实例崩溃也不得留下永久「在线」的记录——否则客户端会反复尝试连接一台早已消失的机器。

### R21 — 目标不可达时的错误必须可区分

客户端请求连接一台 daemon 而失败时，错误需区分三种情形：该 daemon 从未登记过（不属于此账号）、登记过但当前离线、在线但转发失败。三者的用户处置完全不同——分别是「先去认领」「去把那台机器开起来」「稍后重试」——合并成一个通用失败会让用户无从下手。

## 状态、数据与接口

### daemon 的两个生命周期阶段

```
未认领 ──登录──▶ 已认领（归属某账号）
  │                    │
  └ 配对码 + 设备令牌   └ 账号凭据（离线验签）+ 保留既有配对
    本地路径，无需网络     主路径
```

配对不被废弃，它是「这台机器还没有主人」时的唯一可用路径。

### 中转的分层

```
LAN 直连:  Conn ──▶ websocket                          （不变）
中转:      Conn ──▶ 虚拟通道 ┐
           Conn ──▶ 虚拟通道 ┼─▶ 复用器 ─▶ 一条 websocket ─▶ server
           Conn ──▶ 虚拟通道 ┘                                  │
                                                    Redis 寻址 + 帧总线
                                                                │
                                                          另一 server 实例
                                                                │
                                                             客户端
```

### server 的两个端点

一个供 daemon 出站接入并登记在线态，一个供客户端接入并指定目标 daemon。两者都以既有的设备 JWT 中间件鉴权。寻址记录「某台 daemon 当前挂在哪个实例」，帧总线负责实例间投递。

### 帧总线的可靠性要求

通知丢失是可接受的——前置规格已使其可凭游标补齐自愈。**但 RPC 请求与响应丢失会让调用悬挂**，那是用户直接感知的「发出去没反应」。因此总线必须提供投递确认，不能是即发即弃的广播。

这是前置规格挣来的余裕：若通知不可补齐，中转层就必须自行实现可靠投递，复杂度完全不同。

## 界面与交互

原型：`.dev-kit/artifacts/2026-08-03-account-relay/mockups/index.html`（**本地产物，不在 Git 里**）。以下散文是判据，原型仅为佐证。

### 设备面板

标题与「添加」入口保持现状。每台机器一行，行内含：在线点、名称、地址或「经中转」、最近活跃时间，以及可达路径标记。

**现状那个形似筛选器的独立标签被移除。** 它看上去在等一个兄弟标签（LAN / Cloud），但设备通常只有一到三台，按路径筛选没有意义；路径信息下沉到每一行更直接，也更贴近用户真正的问题——「这台我现在是怎么连上的」。

### 他端消息

来源标识跟随在消息的角色标签之后，形态极简，不占独立行，不使用状态色（它不是状态）。

## 安全、隐私、兼容性与可访问性

- **中转明文可见。** 已定：中转帧在 server 侧可解析。这意味着经中转时代码、文件内容与 diff 会明文经过 server。自托管时无所谓；官方托管时这是必须写进隐私政策的承诺，且 R16 的路径标记是用户判断「这次是否经过公网」的唯一依据——这也是它不能被省略的原因。
- **吊销延迟。** 见 R4。这是选择离线可用性的代价，必须在界面上说明，不得隐藏。
- **daemon 不持有个人信息。** 见 R18。
- **凭据存储。** 桌面端用系统钥匙串；daemon 用 `0700` 的数据目录（与前置规格一致）。凭据不进日志——遵循既有的日志红线。
- **兼容性。** 老 daemon 不认识新握手模式：桌面端探测失败后回落到配对路径，行为与今天一致。老桌面端连新 daemon：新握手是新增方法，老端不调用，配对路径不受影响。两个方向都不需要强制升级。
- **可访问性。** 见界面一节。

## 实现决策

| # | 决策 | 理由（及被否方案） |
|---|---|---|
| 1 | 账号即信任边界，配对降为「未认领」时的本地路径 | 用户选择。配对不废是因为新装 daemon 尚无凭据而登录需要网络，完全离线的首次使用只有配对码做得到。否：保留配对为独立的第二条信任路径——两套信任模型并存会让「这台机器谁能用」要查两张表，且账号级可见性在配对路径上无法成立 |
| 2 | 凭据离线验签（缓存公钥），不在线校验 | 用户选择。server 挂了内网照用，与「直连优先」一致。否：每次接入向 server 校验——把内网使用绑架到公网，直接推翻直连优先 |
| 3 | 一台 daemon 只属于一个账号 | 多账号共用需要按账号隔离工作目录、provider 凭据与会话可见性，是另一个量级。要共享机器可跑两个实例（`AGENTRED_DATA_DIR` 已支持）。否：多账号归属 |
| 4 | 帧总线用 Redis Stream，不用 pub/sub | 通知可靠性由前置规格的游标兜底，但 RPC 请求/响应丢失会让调用悬挂，必须有投递确认；Stream 有持久化与确认，pub/sub 即发即弃。否：pub/sub；否：实例间直连转发或粘性路由（要求按实例可寻址的主机名，普通 LB 环境下很痛） |
| 5 | 外层信封包裹既有帧，不给帧加通道字段 | 既有帧结构被桌面端、daemon、远端文件与运行时四处共用，为一条链路的寻址污染它等于让 LAN 直连也背上一个恒为空的字段。否：帧内加通道字段 |
| 6 | 中转明文，不做端到端加密 | 用户选择。明文才能做服务端推送摘要、待决策提醒等；密钥协商与轮换是真正的密码学工作，做错比不做更危险。否：端到端加密；否：预留加密字段而不实现——预留位置往往是错的，真要加密时还得重新设计密钥分发 |
| 7 | 并发选路，先到者胜 | 探测本身就是一次连接，探完再连等于连两次；同网段不等于可达。否：先探测再决定；否：固定优先直连并等待超时——超时窗口要么太短误判要么太长卡顿 |
| 8 | 桌面端设备指纹复用 LAN 配对指纹 | 见 R5 与硬不变量。两条路径上标识不一致会让路径切换的瞬间在 daemon 眼中变成另一个对端，游标失效、补齐拉空。否：账号侧另生成指纹 |
| 9 | MCP 隧道按会话解析而非全局活跃连接 | 内置工具的实现与数据在发起端本地，别处执行结果不同，web 端更是没有。否：保留全局活跃连接（多客户端下会把 A 的工具请求发给 B） |
| 10 | 并发上限不设在任何一端 | 用户选择（原方案为 server 侧限 1）。上限一旦存在就要设计「被占用」的提示与抢占语义，而不限反而更简单 |
| 11 | 桌面端登录走设备流而非浏览器 OAuth 回调 | 回调需要桌面端起 HTTP listener，违反「不得添加 HTTP 风格 app API」的既有不变量；设备流不监听任何端口，且服务端已完整实现 |
| 12 | 移除设备面板上形似筛选器的独立标签 | 设备通常一到三台，按路径筛选无意义；路径信息下沉到行内更贴近用户的实际问题。否：把它做成真的 LAN/Cloud 筛选器 |
| 13 | ~~`devices` 表零迁移，复用既有 `kind` 与 `capabilities`~~ **→ 只剩 `kind`（superseded）** | 原依据：`kind` 已是自由文本、`capabilities` 已是 `jsonb`，装得下计算节点；批准页本就在渲染这两个字段，填对即自然区分。否：为 daemon 新增专用列或专用表——凭空造出第二套设备模型。**`capabilities` 那一半已被 `agentre-server/docs/specs/2026-08-08-drop-device-capabilities.md` 决策 4 推翻**（用户裁决 2026-08-08）：分档依据是客户端自报字段，失效方向是漏警告，因此两个能力列被追加迁移 DROP，两端生产者一并清空。「零迁移」这个结论本身也随之不再成立 |
| 14 | 解除归属（daemon 本地）与解除授权（账号侧）是两个动作，都要有 | 见 R19。账号侧撤销传达不到一台离线的机器，daemon 侧解除也清不掉账号下的记录；只做一个必然留下一端的残留状态。否：只做账号侧撤销（换账号/转让机器时 daemon 本地永远卡在旧归属）；否：只做本地解除（web 端撤销不了丢失的设备） |
| 15 | 在线态用存活期限自动过期，不做显式清理 | 见 R20。显式清理依赖「断开时一定执行到清理代码」，而 server 实例崩溃时不会执行；过期是唯一对进程猝死免疫的机制。否：断开时删除登记 |
| 16 | 不写单独的验收标准列表 | 「行为要求」各条已按「前置—动作—可观察结果」写成可直接建检的形式；再维护一份平行的验收列表意味着两份需要保持一致的副本。否：仓库既有 spec 的双列表体例 |

- **靠人工验证**：真实跨网段（家中 daemon + 外网笔记本）、wifi 与蜂窝网络之间切换时的路径迁移与游标延续、server 停机时内网直连仍可用。真实 NAT、运营商网络与 TLS 中间设备模拟不出来。按 `docs/verification.md` 留证据到 `e2e/scratch/2026-08-03-account-relay/`。
- **覆盖较弱**：R4 的吊销延迟只能验「在线时拉取后生效」与「离线时不生效」两个端点，无法覆盖真实时钟漂移下的边界。
