# 新版本提醒：从「自己去设置里点」改成「它来告诉你」

<!-- File: docs/specs/2026-08-19-update-notice-ux.md -->

> Status: **Approved**（2026-08-19，用户裁决「可以」）
> Owner: 桌面端（`agentre`，后端调度 + 前端状态栏/浮层/设置页三处消费同一份状态）
> Last updated: 2026-08-19
> Mockup（本地产物，不在 Git 里）：`.dev-kit/artifacts/2026-08-19-update-notice-ux/mockups/`
> —— `?view=now` 现状对照、`?view=pill` 三层提醒全貌、`?view=pop` 更新面板、
> `?view=states` 胶囊六态与面板五态、`?view=variants` 三方案对比。

**Objective:** 用户不主动去找，也能在新版本发布后的当天知道有更新，并且从「知道」到「装完」
不必离开当前页面。

**Hard invariant:**

1. **状态栏高度不变（`h-7` = 28px）。** 胶囊替换的是 `chrome.tsx:392` 那一段 `{version}` 文本，
   占同一个位置，不新增行、不改左侧 agent 摘要的布局。
2. **不新增第二套通知视觉。** 到达提示复用 `notification-toast.tsx` 已有的卡片形状与右下角视口。
3. **不发系统级通知**（用户裁决，决策 4）。`notification_svc` 的系统通道继续只服务会话事件。
4. **不改下载 / 校验 / 安装本身。** `update_svc.DownloadAndUpdate` 的三平台安装路径、SHA256 校验、
   `CHECKSUM_FETCH_FAILED:` 协议一行不动；本轮只改「什么时候查」和「查到了怎么告诉人」。
5. 不新增数据库表、不新增迁移。新持久化项复用 `app_settings` 键值表。

## Problem

1. **后端已经在自动查，但结果掉进真空。**（已验证）`internal/app/update.go:129` 在
   `info.HasUpdate` 时 `wailsruntime.EventsEmit(a.ctx, "update:available", info)`，`:89` 的注释
   写着「有新版本时发送 `update:available` 事件供前端弹横幅」。在 `frontend/src` 全量搜索
   `update:available` **零命中**——这个事件今天没有任何消费者，那条横幅从未被实现。
   于是「自动检查」这个能力实际等于不存在。

2. **一个进程只查一次。**（已验证）`startAutoUpdateCheck`（`update.go:92`，由 `app.go:164`
   起一个 goroutine）的结构是 `time.Sleep(5s)` → 读节流 → 查一遍 → 函数返回。
   `autoUpdateCheckInterval = 24h`（`update.go:18`）配合持久化的 `update.last_check`
   挡的是「频繁重启导致的重复请求」，挡不住「一直不重启」：桌面应用连开一周＝一周零次检查。

3. **唯一有效入口埋在设置第 7 节。**（已验证）今天要知道有没有更新，必须「点齿轮 →
   滚到版本与更新 → 点检查更新」。`UpdateSection`（`update-section.tsx`）是全部更新 UI 的
   唯一所在；状态栏右下角的 `<span className="text-subtle-foreground">{version}</span>`
   （`chrome.tsx:392`）是死文本，不可点、永不变化；左栏齿轮没有任何标记。
   有没有新版本，在应用的任何常驻表面上都看不出区别。

4. **安装状态被组件私有，天然无法多处显示。**（已验证）`update-section.tsx` 的 `phase`
   是组件内 `React.useState`，`update:progress` 也在该组件内 `EventsOn`。只要状态还在组件里，
   「状态栏显示下载进度」就不可能与设置页显示同一条真相。

## Actors and user stories

1. 作为**长期开着应用的日常用户**，我希望新版本发布后应用主动告诉我一次，这样我不必记得定期去
   设置里点检查。
2. 作为**当时不在电脑前的用户**，我希望回到电脑前仍然能看出「有更新」，这样错过一次提示不等于
   永远不知道。
3. 作为**正在忙的用户**，我希望提示可以关掉且不再骚扰我，但「有新版本」这个事实不被一并抹掉。
4. 作为**决定要更新的用户**，我希望在看到提示的地方直接装完，而不是被打发去设置页翻第 7 节。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | 三层提醒：到达 toast（实时）＋ 状态栏胶囊（常驻）＋ 点胶囊展开的更新面板（就地安装）。齿轮红点作为路径标记 | 用户裁决（2026-08-19，见 `07-variants.png`）。三层各管一段：缺 toast 则不实时，缺胶囊则错过即失联，缺面板则「知道了也懒得装」。Rejected: **B 顶部横幅** —— 永久占一条横向空间且是纯解释性的条，与既定的「界面只写现在会跑什么、不要总述性解释条」冲突，且关掉后完全回到今天；**C 只加 toast + 红点** —— 改动最小但 toast 错过就没了、安装仍要跨页 |
| 2 | 后端改为常驻 ticker（每 4h tick），并在窗口重新获得焦点时补一次检查；沿用已有的 24h 持久化节流 | 用户裁决。ticker 让「连开不重启」也保证约每天一次；获焦补检让「睡醒打开电脑」这一刻立刻拿到结果。GitHub 未认证限流 60 次/小时，两者叠加远不触顶。Rejected: **只加 ticker** —— 少一个触发点，最坏延迟等于 tick 间隔；**把节流缩到 6h** —— 更密集但收益有限，版本本身不会一天发好几次 |
| 3 | 「跳过此版本」只关掉 toast 与齿轮红点，**不关胶囊** | 用户裁决。胶囊是事实陈述（有 v0.9.2 可用），不是待办项；跳过的语义是「别再主动弹我」。Rejected: **删掉该控件** —— toast 本来每版本只弹一次，「跳过」与「关闭」看似重叠，但少了它就无法表达「这个版本我不打算装，别再提」；**跳过时连胶囊一起隐藏** —— 用户可能一年后都不知道自己落后了，等于回到今天 |
| 4 | 不发系统级通知 | 用户裁决。更新不是「需要你现在处理」的事，应用内 toast + 常驻胶囊已经够；系统通知目前只服务会话完成 / 待审批，混进发版公告会稀释它的分量。Rejected: **仅窗口未聚焦时发** / **给它独立开关** —— 都要接 `notification_svc` 并新增设置项与 i18n，换来的信息量与胶囊重复 |
| 5 | 更新状态（含下载进度）提到一个前端 store，`UpdateSection` 从「自己持有 phase」改成消费者 | 由 Problem 4 的代码事实推出：状态栏胶囊、更新面板、设置页要显示同一条进度，就不能有第二份真相。这是本轮唯一的真重构点。Rejected: **让胶囊自己也监听 `update:progress`** —— 两份独立状态必然漂移（一处 42% 一处 idle），正是「在消费端加兜底掩盖生产端问题」的反模式 |
| 6 | 更新 toast 渲染进现有的 `NotificationToastViewport`，但读自更新 store，不塞进 `notification-toast-store` | 该 store 的 `NotificationToast` 是会话绑定的（`sessionId: number` 必填，用于头像查找与「跳转到会话」）。为更新把 `sessionId` 变成可选会污染现有 5 个测试的类型契约。视口的职责是「右下角浮层容器」，渲染两种卡片不违反 SRP。Rejected: **再挂一个 fixed 视口** —— 两个视口都定位在 `bottom-4 right-4`，会互相叠压 |
| 7 | 「何时该查」抽成可注入时钟与间隔的纯决策函数，脱离 `*App` 与 `time.Sleep` | 用户裁决（测试接缝）。今天的实现无法在单测里验证节流是否生效。Rejected: **不动、只靠人工验证** —— 节流失效会变成对 GitHub 的静默高频请求，没有回归网 |
| 8 | 切换更新通道后立即重查一次，绕过 24h 节流 | 通道是用户主动动作，此刻他在等结果；今天 `handleChannelChange` 只把 `phase` 清成 idle，胶囊会退回灰色版本号，用户得到的是「未知」而不是答案 |

## 何时检查（后端）

**常驻调度。** 应用启动后 5s 触发首次判定（沿用今天的 `autoUpdateCheckDelay`，避开前端冷启动与
迁移高峰），此后每 4h 触发一次判定，直到应用退出。判定不等于请求：每次判定先读持久化的
`update.last_check`，距上次检查不足 24h 时跳过，不发起网络请求。

**获焦补检。** 窗口从未聚焦变为聚焦时触发一次判定，同样受 24h 节流约束。
监听落在前端（`window` 的 `focus` 事件，仓库已有同形做法：`use-remote-devices.ts:243` 用它做
远端设备的回窗刷新，并有对应测试 `use-remote-devices.test.ts:356`），但**判定不在前端**：
前端调用的是一个受节流约束的「自动检查」入口，它与 ticker 走同一个判定函数。
今天的 `CheckForUpdate` 绑定保持「用户主动、绕过节流」的语义不变。

**主动动作绕过节流。** 两种情况下跳过节流直接请求：用户在设置页或更新面板里点「检查更新 /
重新检查」；用户切换了更新通道。两者都是用户此刻在等结果的场景。

**判定是纯函数。** 「上次检查时间 + 当前时间 + 触发源」→「查 / 不查」的决策与 ticker、
`*App`、网络请求分离，可用表驱动单测覆盖。ticker 的定时行为本身不做单测。

**失败沉默。** 检查失败（网络不通、GitHub 限流、解析失败）时**不弹 toast、不亮红点**，
只把胶囊置为「检查失败」态并记录日志。理由：自动检查是背景行为，用户没有发起它，
失败不应打扰他；用户主动点「检查更新」时的失败仍按今天的方式显性报错。

## 三层提醒（前端）

### 状态栏胶囊 —— 常驻层

`chrome.tsx:392` 那段 `{version}` 文本按更新状态呈现六种形态，占据同一位置，右对齐，
宽度随文案变化但不推挤左侧的 agent 摘要（见 `05-states.png`）：

| 状态 | 呈现 | 可点击 |
|---|---|---|
| 空闲（无更新 / 从未检查） | 今天的灰色 `v0.9.1`，`text-subtle-foreground` | 是（打开面板，面板显示「已是最新」或触发一次检查） |
| 检查中 | 无底色胶囊 + 旋转图标 + 「检查中」 | 否 |
| 有新版本 | `primary-soft` 底 / `primary-text` 字 + ↑ 图标 + 「v0.9.2 可更新」 | 是 |
| 下载中 | 同上底色 + 下载图标 + 「下载中 42%」，百分比等宽 | 是 |
| 已安装待重启 | `status-running-bg` 底 / `status-running` 字 + 「重启以完成更新」 | 是 |
| 检查失败 | `destructive-soft` 底 / `destructive` 字 + 「检查失败」 | 是 |

关键是「有更新」必须是一次**真的视觉状态跃迁**：没有更新时它退回今天那段灰字，
而不是常年挂一个彩色装饰在那里。

### 更新面板 —— 就地安装层

点胶囊在状态栏上方弹出面板（`bg-popover`，右下角锚定，见 `04-popover.png`），五种形态：

- **有新版本**：标题「Agentre v0.9.2 可更新」，副行给出发布时间、当前通道、当前版本；
  正文是可滚动的更新说明（沿用今天 `AvailableCard` 的纯文本呈现）；
  底部「下载并安装」「发布页」，右侧「跳过此版本」。
- **下载中**：进度条 + 已下载/总量 + 百分比。
- **已安装待重启**：「立即重启」「稍后」。副行必须明说**重启会结束正在运行的会话**，
  用户可以先收尾再重启。
- **已是最新**：当前版本、通道、上次检查时间，「重新检查」「打开更新设置」。
- **检查失败**：一句人话原因 + 可选中复制的原始错误文本，「重试」「打开更新设置」。
  错误详情按仓库既有约定用选中复制，不加复制按钮。

面板不承载通道 / 镜像 / 调试日志的设置——设置页仍是这些的全量控制台，只是不再是唯一入口。
面板里的「打开更新设置」直达设置页的版本与更新一节。

校验文件获取失败时的「仍要继续」确认对话（今天的 `ChecksumDialog`）在面板发起的下载中同样生效，
行为与设置页一致。

### 到达 toast —— 实时层

自动检查发现新版本时，在右下角弹一张卡片（复用 `notification-toast.tsx` 的 360px 卡片形状与
3px 主色侧条，渲染进同一个视口）：标题「Agentre v0.9.2 可更新」，正文给出当前版本与通道，
一个「查看更新」按钮打开更新面板，一个 ✕ 关闭。

**每个版本最多弹一次。** 关闭后同一版本不再自动弹；出现更新的版本时重新计一次。
用户主动点「检查更新」发现新版本时**不弹 toast**（他正看着结果）。

toast 在 8 秒后自动消失——胶囊已经兜住了「错过」，让它常驻只是重复占位。

### 齿轮红点 —— 路径层

有未跳过的新版本时，左栏设置按钮右上角显示一个 7px 的 `primary` 圆点（`SidebarButton` 本来
就是 `relative overflow-visible`）。它只表示「设置里有新东西」，不解释是什么。
用户跳过该版本或完成安装后消失。

## 状态与持久化

前端持有唯一一份更新状态：当前阶段（空闲 / 检查中 / 有更新 / 下载中 / 已安装 / 失败）、
最近一次检查结果、下载进度、上次检查时间。状态栏胶囊、更新面板、设置页的 `UpdateSection`
全部从这一份读；`update:available` 与 `update:progress` 两个事件只在这一处订阅。

新增一项持久化：**被跳过的版本号**（`app_settings` 中的 `update.skipped_version`）。
它只影响 toast 与红点是否出现，不影响胶囊。写入时机是用户点「跳过此版本」；
被更高的版本号取代时自然失效。

已有的 `update.channel` / `update.download_mirror` / `update.last_check` 三项语义不变。

## 失败与恢复

- **自动检查失败**：胶囊置「检查失败」，不弹 toast、不亮红点，下次 tick 正常重试。
- **手动检查失败**：胶囊置「检查失败」，面板展开时显示原因与原始错误文本，提供「重试」。
- **下载失败**：回到「有新版本」态并在面板内报错；已有的 checksum 获取失败分支
  （`CHECKSUM_FETCH_FAILED:`）继续走确认对话。
- **安装成功但重启失败**：保持「已安装待重启」态，用户可再次点「立即重启」。
- **下载中应用被关闭**：不在本轮范围内处理，与今天行为一致。

## 可访问性与 i18n

- 胶囊是按钮，有可读的 `aria-label`（包含状态与版本），键盘可达、有 `focus-visible` 环。
- 面板遵循仓库既有的浮层交互：Esc 关闭、焦点陷阱、点击外部关闭。
- 红点是纯装饰（`aria-hidden`），其信息由设置按钮的 `aria-label` 承载。
- 全部新增可见文案走 `t(...)`，同步更新 `zh-CN` 与 `en` 两棵树。
- 更新说明正文是上游 release notes，属动态内容，不进 i18n、不做任何文本改写。

## Out of scope

- 下载 / 校验 / 三平台安装逻辑本身（`update_svc.DownloadAndUpdate` 及其平台分支）。
- 更新说明的 markdown 渲染（今天是纯文本 `<pre>`，保持不变）。
- 「自动下载」「自动安装」等无人值守更新策略。
- 系统级通知（决策 4 明确排除）。
- 下载中退出应用的续传或清理。
- `agentred` 守护进程自身的更新。
