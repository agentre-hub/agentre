## 问题与目标

**目标：让一台桌面端和 agentred 一样，成为账号下一个可被寻址的执行端 —— 别的端（浏览器、另一台桌面端）能列出它上面的对话、接进去读写、并把新对话派给它；同时把「本机」这个相对执行目标从模型里拿掉，让每一个执行目标都指向一台具名的机器。会话内容仍不因此离开设备。**
（末句已被 [`2026-08-18-server-session-mirror.md`](2026-08-18-server-session-mirror.md) 决策 1 推翻：保存进账号的对话，其内容镜像在 server 上。）

**硬不变量（已被推翻）：~~`agentre-server` 不持有任何会话内容。~~** 这句在本轮成立：轮 B/C 同样没有新增任何存放会话、消息或转录的服务端表，中继只转发帧、不落盘。**[`2026-08-18-server-session-mirror.md`](2026-08-18-server-session-mirror.md) 决策 1 推翻了它**（2026-08-18）：账号里保存过的对话，其摘要与整条转录镜像在 server 上；没保存过的一个字都不上行。中继本身仍然只转发、不落盘——落盘的是 server 作为常驻中继客户端另开的那条路。

### 问题

1. **桌面端不可被寻址，这条限制的执行点是三行硬判。** `relay_svc/relay.go:158` 拒绝 `kind != KindAgentred` 的登记，`:165` 复核设备行、`:201` 解析客户端目标时各判一次。因此账号下即使有两台桌面端同时在线，也没有任何路径能从一端够到另一端；浏览器同样只能连 agentred。轮 A 的决策 19 刻意没有放开它 —— 「那条检查是前一轮『桌面端不可被调用』这条非目标的唯一执行点，放开它等于在没有配套界面与授权语义的情况下先把门打开」。本轮补齐配套。

2. **桌面端上的对话在别处完全看不到，即使桌面端正开着。** 一条对话的会话行、标题、消息与转录都在发起它的那台桌面端上（工作区同步规格决策 11）。轮 A 交付之后，用户出门能看到 agentred 上的对话，却看不到家里那台开着的电脑上的 —— 而那恰恰是绝大多数对话所在的地方。

3. **`internal/daemon` 整套搬进桌面端解决不了问题 2。** `daemon.New`（`internal/daemon/daemon.go:686-717`）自带一套 SQLite、自己的 migrations、state 文件与配对管理器，它服务的会话住在 `daemon_sessions`。桌面端跑一份只会多出一个**空的**会话存储，浏览器接上去看不到 `chat_sessions` 里的真会话。层级也是错的：`handlers/runtime.go` 的包注释自陈是「`agentruntime.Runtime` + 7 个控制子接口的 1:1 透明代理」，是**运行时级**的；桌面端上同一件事的对应物是 `chat_svc`，一次入站的 `runtime.run` 必须走它的发送路径（排队、权限模式、MCP 注入、消息行与转录落库），而不是新起一个 runtime。

4. **补齐历史在桌面端上没有现成的来源，而照搬 agentred 的日志会让同一段内容存两份且更不完整。** 浏览器的转录是**归约 canonical 事件流**得到的（`agentre-server/frontend/src/lib/transcript.ts` 开头明写识别的 kind「与 Go `agentruntime.EventKind` 一致」，其余落 raw）。agentred 用一张通知日志供给它，而那张日志**会被回收** —— `SilentSessions` + `DeleteBelow` 按静默窗口删掉高水位以下的前缀，`OldestSeq` 存在的唯一理由就是让客户端认出「那截尾巴真没了、复位游标」（`notification_repo/notification.go:57-76`）。桌面端照搬这套，等于把它已经完整持有的转录再存一份，还要跟着配回收策略，然后在手机上给出**比桌面端自己少**的历史。

5. **「本机」是一个相对执行目标，每出现一个新的派发语境就要为它新配一条解析规则。** `agent_backends.device_id` 空串表示本地运行（`agent_backend_entity/agent_backend.go:55-57`），而 backend 行是账号级同步的（工作区同步规格决策 14）—— 于是**同一行**在桌面 A 上读是 A、在桌面 B 上读是 B、在浏览器上读**没有指代对象**。R15d 就是为最后这种情况打的补丁（「从 web 派发时跳过 `device_id` 为空的档」）。桌面端可被派活之后，「桌面 A 派给桌面 B 时『本机』指谁」需要第三条规则，再来一个语境就是第四条。这不是一次性的推翻，是模型每次外扩都会复发的症状。

6. **相对槽位还在硬撑一处已知的语义冲突。** 工作区同步规格 R15e 写着「同一档在两台桌面端上显示不同的继承态是正确的 —— 『本机』本来就指各自那台」。那一行 backend 确实对应两台机器上两套独立的 CLI 安装：版本不同、装了哪些技能包也不同。决策 33 已经因此把技能授权按档拆开，但只要那一档还是**一行**，「一行、两个现实」就还在。

7. **执行目标的顺序被账号级同步，而它表达的偏好本质上是机器相关的。** `AgentExecTarget` 整行带 `syncmeta_entity.SyncMeta`（`agent_entity/exec_target.go:17-25`），`sort_order` 因此是同步的：在桌面 A 上拖一下排序，桌面 B 上那个 Agent 的顺序跟着变。而「优先在我面前这台跑」在 A 上和在 B 上要的是不同的第一名 —— 一份共享的有序列表表达不了它，正是这个约束逼出了相对槽位（问题 5）。

## 参与者与用户故事

1. 作为**出门在外的用户**，我想用手机看家里那台开着的电脑上正在跑的对话并接着往下聊，而不是只能看到 agentred 上的那几条。
2. 作为**同时有台式机和笔记本的用户**，我想在笔记本上把一个任务派到台式机上跑（那儿代码是齐的），而不是先走过去。
3. 作为**在两台机器间来回的用户**，我想在每台机器上各自决定这个 Agent 优先在哪跑，而不是我在一台上排的顺序把另一台也改了。
4. 作为**只有一台电脑的用户**，我不想因为这些多端能力，让界面和行为跟今天有任何不同。
5. 作为**注重隐私的用户**，我不想因为桌面端可以被接入，就让对话内容被 server 存下来。

## 设计决策

| # | 决策 | 依据（及被否方案） |
|---|---|---|
| 1 | 轮 B 与轮 C 合成一轮做完 | 用户裁决（2026-08-11）。B 之后桌面端已经既是客户端又是服务端，C 主要是让另一台桌面端成为可选目标；分两轮会留下「浏览器能驱动桌面端、桌面端却不能驱动桌面端」的中间态。否：只做 B（中间态不自洽）；否：B 再切细（「可派活」那一半被拿掉，用户已明确要它） |
| 2 | 桌面端的入站面是**会话级适配层**，不复用 `internal/daemon` | 问题 3。daemon 的会话住在 `daemon_sessions`、handler 是运行时级透明代理，两条都对不上桌面端的现实。适配层把 `runtime.session.*` 与控制族映到 `chat_svc`，让浏览器看到的就是它真正的那批对话。否：桌面端内嵌一份 daemon（多出一个空会话存储，问题 2 原样留着）；否：为桌面端另定一套方法族（轮 A 决策 19 承诺浏览器侧「只是多一种可选的目标设备，不需要重写」，另定一套等于让浏览器长出第二条代码路径） |
| 3 | 浏览器与桌面端之间说的是**与 agentred 同一套 wire 词汇** | 轮 A 决策 19 的直接兑现。浏览器的转录归约器、中继客户端与界面因此一行都不用改，桌面端只是清单里多出来的一类目标。代价是桌面端必须发出 canonical 事件（实时与补齐都要），见决策 4。否：新方法族（同上） |
| 4 | 补齐历史**从既有转录反向合成** canonical 事件，不新建通知日志 | 用户裁决（2026-08-11）。问题 4：新建日志会把同一段内容在桌面端上存两份，且配了回收之后手机上看到的历史比桌面端自己少。合成的代价是一个 `event_convert.go` 的逆向转换器并长期维护两个方向，以及合成流在分片粒度上与真实流不逐字节一致 —— 轮 A 的 R8 已为渲染保真度留了口子。实时推送不走合成器，在 `dispatcher.Apply` 之前 tee canonical 事件（三个循环：`chat.go:4044`、`autonomous_turn.go:190`、`subagent_activity.go:103`）。否：新建通知日志（重复存储 + 历史更少）；否：实时 tee、历史合成的混合游标（两个 seq 空间要接成一个单调游标，是三者里最容易出重复投递与卡游标的一个） |
| 5 | 同一条会话从两处列出时**合并成一条**，优先桌面端那份 | 用户裁决（2026-08-11）。桌面端发起、落在 agentred 上执行的会话，两边的清单里各出现一次。`SessionSummary` 带 `PeerFingerprint` 与 `SessionID`（`wire.go:420-421`），而 agentred 本就按发起端指纹给会话建键，因此两边算得出同一个合并键。优先桌面端是因为它持有完整转录与标题；桌面端离线时退到 agentred 那份，轮 A 已交付的能力不回退。否：桌面端只暴露本机执行的会话（那些对话在手机上永远只剩 agentred 侧的一半，即使桌面端就开着）；否：两处都列不合并（两条长得一样、点进去内容不同的对话，无法解释） |
| 6 | **删除相对执行目标**，每个 backend 都指向一台具名机器 | 问题 5 与问题 6。相对槽位是「一行、两个现实」的根源，也是每个新派发语境都要新配解析规则的原因。全具名之后 R15d 不是被改写而是**不再需要**，轮 C 里「桌面 A 派给桌面 B 时本机指谁」这个问题从一开始就不存在。代价是 backend 与执行目标行 fan-out：今天两台桌面端共用一行「本机 · Claude Code」，之后各占一行，组织架构里看得见。这个 fan-out 是**如实的** —— 那本就是两台机器上两套独立安装。否：保留相对槽位、只把 R15d 改成「只在具名执行端里选」（病根留着，下一个语境再配一条规则） |
| 7 | 顺序 = **账号级默认（仍同步）+ 各端本地覆盖（不同步）** | 用户裁决（2026-08-11）：「还是有顺序，只是各端顺序自己调整，不同步」。问题 7：顺序表达的偏好是机器相关的，但完全不同步会让「在 A 上精心排的顺序换台机器完全帮不上忙」。保留一份同步的默认作种子、各端本地覆盖，同时满足两头：新机器零配置就有合理顺序，浏览器直接用默认（它没有「自己」可提前），而任何一端拖拽只改自己。否：`sort_order` 从同步载荷里彻底拿掉（每台机器都要重排一遍）；否：顺序仍同步 + 「本端自动提前」规则（本质还是一条语境相关规则，且无法表达「这台就是不要优先跑本地」） |

| 9 | 不设「接单开关」，登录即完全开放 | 用户裁决（轮 A 规格已记录 B 轮边界：「不设开关，登录即完全开放」），与 2026-08-08 的同一条裁决一致：设备连上账号即拥有完整权限。否：桌面端可被派活需单独开启（多一套授权语义，而账号内的设备之间本就互信） |
| 10 | 轮 C 的「另一台桌面端」不新增配对概念，它就是执行目标列表里的一类具名目标 | 决策 6 之后，具名桌面端与具名 agentred 在列表里地位完全相同；出站拨号也已经是按指纹的通用实现（`server_svc/relay.go` 的 `DialDaemonRelay`）。因此轮 C 在传输与数据两层几乎没有新增，主要是界面。否：为桌面端之间另设配对流程（账号已经是信任边界，再加一层配对是重复的） |
| 11 | 桌面端不因入站面获得任何新的可寻址身份 | 桌面端在 server 上本就注册为 `kind=desktop`（`server_svc/login.go:122`），本轮只让这个 kind 可以被寻址，不新增设备种类、不改设备注册流程。否：为「可被接入的桌面端」新增一种 kind（设备列表多一类要解释的东西，而它与 desktop 没有任何字段差异） |
| 12 | 具名机器的同步身份用**设备指纹**；相对行由每台桌面端在**运行期幂等认领**，不在一次性 SQL migration 里认领 | 用户裁决（2026-08-11）。跨机持久化与同步使用 canonical device fingerprint，落地派发时才翻回该端本地的 paired-row ID。认领在数据库迁移完成、keychain 与 `remote_device_svc` 初始化之后运行；本端指纹从 OS keychain 读取或生成，不依赖登录态或 `server_state.device_fingerprint`。克隆、原 backend/执行目标墓碑与同步队列沿用正常本地变更路径，未登录时待认证后上传。否：存 server 设备行 ID（各端本地值不同，无法同步）；否：在 `migrationList()` 中做一次性数据认领（migration 没有逐安装身份，无法兑现「每台桌面端为自己认领」） |
| 13 | 桌面端的跨机器会话入口由**设备设置页列清单，聊天页 Peer Tab 承载详情** | 用户裁决（2026-08-12）。设备设置页的桌面端行展开会话列表；点击一条后切到现有聊天页并打开 Peer Tab，完整承载转录、实时流、输入、提问与工具审批。它不新增导航项、独立路由页面或新的传输层，也不把完整聊天交互挤进设置面板。否：设置页行内展开完整详情（设置面板职责与空间都不适合持续聊天）；否：新增远端会话页面或导航项（违反本轮界面边界） |

## 桌面端成为可被寻址的一端

**R1 — 一台已登录的桌面端在 App 运行期间可被账号内的其它端寻址。** 桌面端持一条常驻的出站中继连接登记自己的在线态；此后同账号的浏览器与其它桌面端可以按它的设备指纹连上它。登记与寻址复用中继既有的设备 JWT 鉴权，桌面端不因此获得任何新的设备身份（决策 11）。App 退出后登记随连接消失，它不再可被寻址。

**R2 — 「App 没运行」与「机器离线」是两种说法，不折叠。** 目标桌面端不可达时，界面说明的是「那台电脑上的 Agentre 没有运行」并给出「打开它」这一动作指向，而不是「机器离线」（决策 8）。agentred 的离线表达一个字不变。

**R3 — 桌面端可被接入不改变它的权限边界，也不新增开关。** 账号内任一设备连上即拥有对该桌面端上会话的完整读写能力（决策 9）；解除某台设备的授权后它的中继连接被拒，其余设备不受影响。桌面端自身仍然是中继上的出站调用方，被寻址不改变这一点。

## 列出与接入桌面端上的会话

**R4 — 从设备页下钻到一台桌面端的会话列表。** 用户在设备页选中一台**正在运行**的桌面端后，进入它的会话列表：列出这台桌面端上的全部对话。未运行的桌面端不可进入，行上按 R2 说明原因与最后在线时间。

**R5 — 会话列表每条显示的信息与 agentred 一致，且桌面端上不存在退化形态。** 每条显示：对话标题、运行状态、是否正在等待用户输入、最后活动时间，以及所属 Agent 的名称与头像。轮 A 的 R5 为 agentred 上的老会话定义了「未命名」退化分组（标题与 Agent 标识随每轮携带才到达）——**桌面端不需要它**：标题与 Agent 归属本就是桌面端自己库里的一等数据，每一条都有。分组沿用轮 A 的形态（桌面按 Agent、移动按状态）。

**R6 — 接入一条会话后收到实时流，并可与桌面端自己的界面同时在场。** 用户打开一条会话即接管它，随后按 seq 游标补齐历史转录并开始接收实时事件。**同一条会话可以同时被这台桌面端自己的界面与远端的浏览器接入**，两边收到同一份实时流；桌面端界面上的输入与远端的输入进入同一条会话队列。

**R7 — 历史转录由桌面端从它已有的转录合成，且不会因为回收而缺失。** 补齐的事件流与 agentred 供给的同构（同一套 canonical 事件），因此浏览器侧的归约与渲染不作区分。与 agentred 不同的是：**桌面端的最老可用 seq 恒为该会话的第一条**——它的历史不回收，用户在手机上看到的历史与在那台电脑上看到的一样完整。客户端既有的「前缀被回收、复位游标」那条路径对桌面端永远不触发，但保持可用（agentred 仍会回收）。

## 读与写

**R8 — 浏览器读到的转录与桌面端一致。** 消息、工具调用与结果、各类结构化卡片按轮 A 的 R8 呈现：浏览器实现通用形态，不识别的按原始形态如实呈现而不是隐藏。合成的事件流在分片粒度上与实时流不必逐字节一致，归约后的可读内容必须一致。

**R9 — 浏览器可以给桌面端上的一条会话发新消息。** 消息进入该会话的下一轮，在那台桌面端上按该会话原本钉住的执行目标执行。会话本身落在某台 agentred 上时，桌面端照常把这一轮转给它 —— 此时**那台 agentred 也必须可用**，不可用时按 R11 说明，且历史仍读得到。

**R10 — 浏览器可以批准工具调用与回答提问。** 会话停在等待用户输入时，浏览器给出与桌面端同一套选择，用户的决定即时生效。**同一个待决策只能被回答一次**：已被桌面端自己的界面或别的端回答过时，浏览器就地说明它已被处理并刷新状态，而不是报错或静默失败。

**R11 — 不可达与失效各自可区分，本轮新增两类。** 在轮 A 的四类（目标不可达 / 与 server 断线可重连 / 本设备已被解除授权 / 账号已登出）之外，新增并区分：

- **目标桌面端上 App 没有运行**（R2），与「机器离线」分开说；
- **桌面端在场、但该会话执行所在的 agentred 不可用** —— 此时历史读得到、新消息发不出，说明必须同时表达这两件事，不得笼统报「不可达」。

断线重连后自动补齐断连期间的事件，用户不需要手动刷新。

## 执行目标：删除相对槽位

**R12 — 每一个执行目标都指向一台具名的机器。** 「本机」这一相对取值不再存在（决策 6）；`AgentBackend.DeviceID` 的跨机持久化与同步取值是目标设备的 canonical fingerprint，不是 server 设备行 ID，也不是某一端本地的 paired-row ID；落地派发时再把 fingerprint 翻回接收端的本地标识。因此**任何端**解析执行目标时都不需要知道「谁在读这份列表」，也不存在需要跳过的槽位。

**R13 — 升级时每台桌面端在运行期为自己认领一份，不改写共享的那一行。** 原先的相对 backend 是一行、两个现实（问题 6）。数据库迁移完成、keychain 与远端设备服务初始化后，本端运行一次幂等认领：从 OS keychain 读取或生成 canonical fingerprint，每台桌面端**新建**一行属于自己的 backend（沿用原有配置，指向自己的指纹），引用它的执行目标同样各自新建一档；原相对行与引用它的档落墓碑，并通过正常同步变更队列在认证后上传。认领不依赖 server 登录态或 `server_state.device_fingerprint`，也不放进 `migrationList()` 的一次性 SQL 数据迁移。认领的判据是「原取值为相对」，因此一台桌面端不会把另一台刚认领出来的行再认领一次。净可观察结果：账号下 backend 与执行目标各多出一份，组织架构里看得见，**每一份如实对应一台机器上的一套安装**。单台桌面端的账号在数量上与升级前一致。

**R14 — 顺序是「账号级默认 + 本端覆盖」。** 账号下每个 Agent 有一份默认顺序，随账号同步；每一端另可持一份**只属于自己、不同步**的顺序覆盖。解析规则：本端有覆盖就用覆盖，没有就用默认；桌面端在没有覆盖时把**自己**排到第一（这是「优先我面前这台」的落点）；浏览器没有「自己」可排，直接用默认。在任一端调整顺序**只改这一端**，不影响别的端，也不改默认。

**R15 — 派发按解析后的顺序取第一个可用的，判据不变。** 可用性判据沿用工作区同步规格 R15 的四类（未配对或不可达 / 离线 / 该机器上这个项目没配路径 / 既有的各类 `BlockReason`），并按 R2 把「桌面端 App 没运行」计入不可达。全部目标都不可用时不静默失败，逐项说明原因。**从 web 派发不再有任何特殊规则**（R15d 随相对槽位一并删除）。会话仍钉在它起初落到的那一档上，续轮不改派。

**R16 — 顺序控件改的是这一端自己的顺序。** 组织架构里那个可拖拽的执行目标列表，今天改的是账号级顺序、改完全账号生效；本轮之后它改的是**这一端自己的**顺序，且它显示的内容与顺序恒等于这台电脑当前实际的派发顺序。界面上不出现「账号默认顺序」这个概念 —— 它退化成不可见的初始值 / 兜底，因此不要求为它提供编辑入口，也没有「恢复为账号默认顺序」这一动作（本条由 [2026-08-14 执行目标顺序：每端自己排](./2026-08-14-exec-target-order-ux.md) 决策 1/2/4/5 修订；R14 的解析规则与 R22 不变）。

## 派活与跨桌面端

**R17 — 浏览器可以把新对话派到一台桌面端上。** 用户挑一个 Agent 与一个项目，按 R14 解析出的顺序取第一个可用目标；目标是桌面端时，对话在那台桌面端上建立并执行，会话行、标题与转录都住在那儿。轮 A 的 R17（web 发起的对话不注入 `org`/`subagent`/`hook`）**在目标是桌面端时不适用** —— 这三个内置工具的真身就在桌面端上，隧道有落点，能力与在那台机器上手动发起完全一致。目标是 agentred 时，轮 A 的 R17 原样成立。界面在发起前如实说明当前目标下哪些工具可用。

**R18 — 一台桌面端可以把对话派到另一台桌面端上。** 具名桌面端在执行目标列表里与 agentred 地位相同（决策 10），因此这条不需要新的配对或授权流程：把它排进顺序即可。派出去的对话整条住在执行端那台机器上。

**R19 — 一台桌面端可以列出并接入另一台桌面端上已有的会话。** 路径与浏览器的下钻一致：设备设置页 → 展开一台正在运行的桌面端 → 它的会话列表 → 一条会话。点击后切到现有聊天页并打开一枚 Peer Tab，由该 Tab 按 R6 到 R11 承载完整转录、实时流、输入、提问与工具审批；关闭 Tab 只结束本端接入，不删除执行端会话。这是轮 C 的主体。

**R20 — 同一条会话不因为两处都列得出来而重复出现。** 桌面端发起、落在 agentred 上执行的会话会同时出现在两份清单里；客户端按「发起端指纹 + 会话标识」认出它们是同一条，只呈现一行，取桌面端那一份（它有完整转录与标题）。桌面端不在场时退到 agentred 那一份，并标明此时只读得到执行端保留的那部分历史（决策 5）。

## 桌面端上的呈现

**R21 — 别的端发起的一轮，在桌面端上读得懂。** 远端发出的用户消息在桌面端的转录里落成正常的一行用户消息并带上来源标识（「来自 <设备名>」）。轮 A 已为浏览器→agentred 这条路实现了该渲染层与「开新一轮」的携带；本轮让桌面端**作为执行端**时走到同一处，不新造控件。显示名缺失时回退到指纹或通用文案，**不阻塞消息落地**。

**R22 — 单端使用界面零变化。** 账号下只有一台桌面端、且没有别的端接入时，除 R16 那处顺序作用范围的标注之外，界面与行为与今天一致：本机发出的消息不带来源标识，呈现逐像素不变。

## 界面

新增与改动集中在三处，**不新增导航项**：

- **设备页**：桌面端行可展开出一节「对话」（条数、等待处理数、进入入口），与 agentred 的展开区同形；行上的在线态按 R2 用「Agentre 未运行」而不是「离线」。
- **会话列表与详情**：沿用轮 A 已交付的形态（桌面按 Agent 分组、移动按状态分组，机器语境放顶栏面包屑），桌面端只是清单里多出来的一类目标；重复会话按 R20 合并后只出一行。
- **组织架构的执行目标列表**：控件形态、拖拽与键盘等价物不变，改的是标注与作用范围（R16），以及每一档现在都显示一台具名机器（R12）。

桌面端侧不新增导航项、独立路由页面或新的窗口：设备设置页只负责列出远端桌面端及其会话，详情复用现有聊天页的 Peer Tab（决策 13）。新增文案在 `agentre-server/frontend/src/i18n/` 与 `agentre/frontend/src/i18n/locales/{en,zh-CN}/common.json` 同时落 en 与 zh-CN，由既有的 `locale-parity.test.ts` 与 `i18n.test.ts` 守卫。**可访问性**：运行状态、等待输入、App 未运行、机器离线与解除授权五类状态不得仅靠颜色区分，均带文字。

## 安全、隐私与兼容性

- **~~server 不持有会话内容。~~ 已被 [`2026-08-18-server-session-mirror.md`](2026-08-18-server-session-mirror.md) 推翻**（2026-08-18）：账号里保存过的对话，其摘要与整条转录存在 server 上；没保存过的一个字都不上行，删除会把 server 与执行端两份一起清掉。帧的转发本身仍然只过境、不落盘。
- **桌面端可被寻址扩大了失窃凭据的后果面。** 一台设备的凭据失窃后，攻击者此前可读写全部 agentred 上的会话，此后还包括正在运行的桌面端上的会话。对冲仍是设备列表里的单独解除授权（R3），与 2026-08-08 的裁决一致：不为此另设开关。
- **老桌面端与老 agentred 兼容。** 未升级的桌面端不登记入站，它照常作为客户端工作，只是在别的端上不可被进入；未升级的 agentred 沿用轮 A 已定的退化与「需要升级」说明。升级后的桌面端面对老对端照常工作。
- **执行目标模型的迁移会改变账号里的行数**（R13）。这是可见的一次性变化，不是数据丢失：每一份新行都对应一台真实机器上的一套安装，原相对行落墓碑后不再被解析。单台桌面端的账号在数量上不变。
- **不改动既有握手与帧结构。** 本轮只新增字段与方法，不改变前置规格定下的握手、中继信封与既有帧的语义。

## 非目标

- **server 托管 `org` / `subagent` / `hook` 三个内置工具的 MCP 服务端**（块 3 的另一半）。目标是 agentred 时这三个工具仍不可用并如实说明；目标是桌面端时它们本就可用，不需要托管。
- **把某个设备的某个对话「拿出来」到 server**（块 4）、**用量与配额**（块 5）、**审计**（块 6）。
- **会话与消息同步到 server。** 见硬不变量。
- **别的端上的终端、文件树与技能管理。** 桌面端与 daemon 上都有这些能力，本轮不接。
- **转录渲染的逐卡片对齐。** 见 R8。
- **桌面端在 App 未运行时被唤醒。** 本轮不做任何唤醒机制（R2 只负责如实说明）。
- **会话中途改派执行机器。** 沿用工作区同步规格的决策 16：会话钉在它落到的那一档上。
- **默认顺序的自动学习。** R14 的默认顺序由用户编辑，本轮不按使用频率或最近活跃自动调整它。
