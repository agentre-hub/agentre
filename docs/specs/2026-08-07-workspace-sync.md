## 问题与目标

**目标：让同一账号下的多台 agentre 桌面端共享同一份工作区——项目、部门、Agent 与它们的执行配置；Agent 不再绑死一台机器，而是带一个有序的执行目标列表，在哪台机器上跑由「当前哪台可用」决定。只有「项目在本机的绝对路径」是每台桌面端各自的，单向上报给 agentre-server。未登录的桌面端行为不变。**

### 所有权模型

本规格只有一条不变量：**除了本机文件系统路径，工作区配置一律属于账号，不属于某一台机器。**

| 对象 | 归属 | 传播 |
|---|---|---|
| 项目、部门、Agent、Agent 的执行后端配置、项目的 Agent 成员关系 | 账号 | 双向同步 |
| 项目在某台 agentred 上的路径 | 账号（键里带那台机器的指纹） | 双向同步 |
| 项目在本机的路径（`projects.path`） | 那台桌面端 | 单向上报 |

账号下只有**一个**叫「开发」的 Agent，不管有几台桌面端。它在哪台机器上执行不是它的身份的一部分，而是一个**有序的候选列表**（R15）：优先本机、其次某台 agentred，第一个可用的胜出。本机没配对某台 agentred 时，指向它的那一档自动跳过（R2b）——Agent 本身照常可见可用。

**硬不变量：桌面端的自增主键不得改动。** `project_id` 被 4 处引用（`issues`、`project_agents`、`chat_sessions`、`project_locations`），`agent_id` 被 5 处引用（`project_agents` 复合主键、`agents.parent_agent_id`、`chat_sessions.agent_id`、`issues.assignee_agent_id`、`departments.lead_agent_id`）。跨机身份一律靠**新增列**承载，不迁移主键；同步载荷里的引用一律翻译成同步标识或指纹（R2）。纯本机数据对本地 ID 的引用（`chat_sessions`、`issues`）不受影响——账号级对象在每台桌面端本地照样有自己的自增 ID。

### 问题

1. **web 控制台拿不到对话的命名层。** 设计稿屏 42 要渲染「后端 Agent」「改 refresh 的过期判断」「PINNED」，但 `agent_entity.Agent`（名称、头像、Pinned）、`chat_entity.Session.Title`、`project_entity.Project` 全部只存在于桌面端本地 SQLite。daemon 侧 `session_repo.DaemonSession` 只有 `(peer_fingerprint, peer_session_id, agent_id, cwd, backend_type, lifecycle_state)`，`wire.SessionSummary`（`internal/pkg/agentruntime/runtimes/remote/wire/wire.go:384-393`）同样没有名称类字段。agentre-server 的 MySQL 只有 `users` / `user_identities` / `devices` / `device_tokens` / `device_flow_codes` 五张表，与工作区配置无关。

2. **桌面端之间零同步，服务端也拿不到清单。** 一个账号下可以有任意多台 `kind=desktop` 设备（`device_entity` 无数量约束），但桌面端两两之间没有任何数据交换：一台机器上建的项目，另一台完全看不到；账号下有哪些 Agent，服务端同样无从得知。

3. **同一个 Agent 要在每台机器上各建一遍，账号里于是有 N 个「开发」。** `agents` 只存在于本地库，一个人两台桌面端就要建两个同名 Agent；共用一台 agentred 时，「项目 P 在这台机器上是哪个目录」也要各配一遍。从服务端看更明显：账号下三个「开发」分散在三台设备名下，而它们本该是同一个 Agent。

4. **Agent 绑死一台机器，机器不在就只能手动改配置。** `Agent.agent_backend_id` 指向单个 `agent_backends` 行，该行的 `device_id` 决定在哪跑（`agent_backend.go:54`：「空串表示本地运行；非空表示用户意图绑定远端，服务层按 `DeviceIDInt()` 派发」）。这是一条硬绑定：本机关机、或想临时改用构建机，都要去改 Agent 的后端配置。前端已有的离线守卫（`new-project-chat-source.tsx:378-392`）只能拦住，不能改派。

5. **「项目存在但本机没有路径」这个状态今天不会出现，多端之后会成为常态。** `project_entity.Project.Path` 是 `not null` 且无默认值，产品里项目一律由本机创建、路径当场就有；`project_location_entity` 的包注释也写明「本地 path 仍住在 `projects.path`（避免双源同步），本表不存空 `device_id` 的行」。项目开始跨机同步后，新登录的桌面端会拿到一批本机尚未指定路径的项目，而这条路径上今天没有任何界面表达与错误语义。

6. **项目、部门、Agent、backend 都没有跨机身份。** 它们的主键都是本地自增 `int64`；两台机器上的 `id=1` 是两个不同的对象。没有一个稳定标识就无法判断「这两端的这一行是不是同一个」。

7. **没有墓碑。** 这几张表都只有 `Status` 字段，没有删除时间戳。双向同步下，A 删掉的对象会被 B 的旧副本重新推上来复活。

8. **桌面端没有来自 server 的账号级下行通道。** `internal/service/server_svc/` 的出站面是 HTTP 请求-响应（`login.go` 设备流、`refresh.go` 刷新、`devices.go` 列设备、`healthcheck.go`），加上一条**按需拨起的 WebSocket**——`relay.go:22` 的 `DialDaemonRelay` 经 `client.DialRelay` 连 server 的 `/v1/relay/client`，但它是「桌面端要连某台 daemon 时才拨、拨完只服务那台 daemon」的中转管道，不是账号维度的常驻通道。除此之外没有 SSE、也没有任何轮询。「别的机器改了什么」当前传不回来。

9. **指向 agentred 的引用都是本地自增 ID。** `agent_backends.device_id` 与 `project_location_entity.ProjectLocation.DeviceID`（`project_location.go:23`）存的都是 `paired_agentreds.id` 的字符串形式（`project_location_svc/impl.go:34-38` 用 `remote_device_svc.Get(id)` 校验存在性）。`paired_agentreds` 是每台桌面端各自的配对表，`id` 各不相同，server 更没有这张表——原样出机是永远解析不了的整数。`project_locations` 还有一条 `uniq_project_locations_proj_device ON (project_id, device_id) WHERE status = 1`（`migrations/202605220005_projects.go:64`），自然键建在本地 ID 上，跨机之后既挡不住重复也容不下「指纹已知但本机没配对」的行。

10. **`agent_backends` 里混着可跨机的配置与不可跨机的凭据引用。** 大部分字段描述的是「怎么跑」，可以跨机：`Type`、`ModelRoutes`、`Sandbox`、`Approval`、`ReasoningEffort`、`DefaultPermissionMode`、`DefaultModel`、`OpenClaw*`。`LLMProviderKey` 与 `ModelRoutes` 的值指向 `llm_providers.provider_key`——**那是个带唯一索引的字符串键（`llm_provider.go:41`），不是自增 ID，天然可跨机**，但它指向的 provider 行含 `APIKey`，不能出机。`CLIPath` 是文件系统路径，在不同机器上可能不同。`EnvJSON` 是用户自填的透传环境变量，可能被塞进密钥。

11. **LWW 所比的时间没有单一来源。** 冲突判定要比「最后修改时间」，而修改发生在不同物理机上。桌面端之间无任何时钟同步机制，一台机器慢 10 分钟就会让它的每一次编辑都输给对端的旧版本。

12. **登录前已存在的项目没有身份来源。** 桌面端今天一律先建项目后（可能）登录；双机办公的用户两台机器上本就各有一份同一个仓库的项目。两端各自生成同步标识后上行，账号下会出现两个项目、每台机器上也看到两个——正是用户故事 1 要消除的现象。

### 基线事实

本节的测试基线（两个仓库各自的全量测试结果与既有抖动）在本轮 worktree 建立后采集并补记，采集前视为未知。

前置规格 `2026-08-03-account-relay` **已合并**：`agentre` 侧是 `82a2f845`（PR #27），规格文件已在 `docs/specs/` 下，本文开头指向它的链接解析得到；`agentre-server` 侧引入的 `access_jti` 列已随该仓 `93ea7a5`「压缩未发布迁移基线」并进 `202605200004_device_tokens.go`，不再是独立迁移。它对本规格的实施排序约束因此解除。

本文引用的代码事实以 `agentre` main `a958cf5d`、`agentre-server` main `8fb4629` 为准复核过。此前记为「main 上与本轮无关的未提交改动（chat/transcript 8 文件）」的那批，已作为会话文件面板的两轮（#29 / #31）合入 main——它们引入的 `workspace_fs_svc` 是本机路径解析的新消费者，已计入决策 6 的使用点清单。

**设备能力模型（`devices.capabilities` / `device_flow_codes.client_capabilities` 与 agentred 上报的 `compute`）正由用户另行删除**，本规格不依赖它，也不为它写任何要求：设备连上账号即拥有完整权限。

## 参与者与用户故事

1. 作为**双机办公的用户**，我想在公司和家里的桌面端上看到同一批项目与同一批 Agent，而不必两边各建一遍。
2. 作为**账号下有一个「开发」Agent 的用户**，我不想因为有三台机器就在云端看到三个「开发」——它就是一个 Agent。
3. 作为**在家办公的用户**，我希望「开发」平时就在我面前这台电脑上跑；等我关机之后从网页派活时，它自动落到构建机上，而不是要我先去改配置或手动挑机器。
4. 作为**想临时换机器的用户**，我要能为某次对话手动指定在哪台机器上跑，而不受默认顺序限制。
5. 作为**换机的用户**，我想在新机器上登录后拿到全部项目与 Agent，只需为本机重新指定各项目的目录。
6. 作为**web 控制台的使用者**，我想在一个地方看到账号下所有 Agent，以及每个 Agent 能在哪些机器上跑。
7. 作为**离线工作的用户**，我想断网时照常增删改项目与 Agent，联网后自动补上去，不丢改动。
8. 作为**注重隐私的用户**，我不想让本机目录结构（含系统用户名）出现在服务端网页上。

## 设计决策

| # | 决策 | 依据（及被否方案） |
|---|---|---|
| 1 | 双向同步，不是单向推副本 | 用户裁决（2026-08-07）。已就「双向是 2–3 轮工作量」提出顾虑，用户复述后仍选双向。否：主设备单向推（副机改动同步不上去，双机办公场景直接受损） |
| 2 | 去掉「主设备」概念，所有桌面端平等 | 用户裁决。项目与 Agent 在每一台桌面端上都是完整的，「主设备持有数据」的理由消失。设计稿屏 28「主设备不能关 —— 项目和 Agent 都记在它那儿」需随之改文案。否：保留为「默认执行机器」（决策 10 的目标列表已经覆盖了这个需求，且比一个全局默认精确） |
| 3 | 跨机身份用新增 `sync_id`(ULID) 列，桌面端主键不动 | 硬不变量。加一列 + 部分唯一索引即可承载跨机身份，从别端同步来的行在本地照常分配自增 ID。需要它的是：`projects`、`departments`、`agents`、`agent_backends`、`project_agents`、`project_locations`。否：把主键迁移成 ULID（要动 `project_id` 的 4 处与 `agent_id` 的 5 处引用，以及全部历史数据） |
| 4 | 冲突用行级 LWW（比同步版本号，同值按 `sync_origin` 字典序打破平局） | 配置数据的并发写极少，行级 LWW 可预测且必然收敛；打破平局规则是收敛的必要条件（否则两端可能互不相让）。版本号的来源见决策 19 与 27——它是账号级单调序列，因此平局规则实际不触发，仅作兜底。否：字段级合并（复杂度高出一个量级，且 `prompt_json` / `tools_json` 这类整体语义字段合并没有意义） |
| 5 | 被覆盖的版本本地保留 30 天，界面不提示 | 用户裁决。配置数据冲突极少，弹窗的干扰大于价值；但静默丢改动不可接受，故留可追回的副本。30 天与 daemon journal 的默认留存窗口一致（`internal/daemon/daemon.go` 的 `defaultJournalRetention = 30 * 24 * time.Hour`）。否：明示提示（多一套 UI 与文案，大部分情况是噪声）；否：直接覆盖不留副本（改动真丢） |
| 6 | 本机路径不参与双向同步，只上报；`projects.path` 的结构与语义不动 | 用户裁决（2026-08-07）：「项目路径是不是不应该同步，windows 和 linux 这种，项目路径肯定不同」。它是本轮**唯一**不属于账号的对象。不同步它就不会串，跨操作系统的路径格式差异从不相遇，因此**不做收编**：`projects.path` 的读写与既有使用点的分流保持原样，也不需要迁移历史数据。使用点共 6 处——`project_svc/cwd.go`（`ResolveSessionCwd` 与 `ResolveProjectCwd` 两个入口，后者由 `internal/app/terminal.go:20` 的终端调用）、`chat_svc/cwd.go`（含 `ResolveSessionWorkspace`，`bootstrap/cago.go:140` 注给会话文件面板的 `workspace_fs_svc`）、`chat_svc/chat.go`、`ctl_svc/gateway.go`、`project_svc/project.go:81` 的 `os.Stat` 存在性校验、以及 `project_entity.Project.Check` / `IsGitRepo`。唯一的例外是决策 21 为「本机未配置路径」新增的那些分支（R10、R11）。否：把本机路径收编进 `project_locations` 并一同同步（要重构 `ResolveSessionCwd` 与迁移历史数据，换来的是一份没人读的副本） |
| 7 | agentred 上的路径归属账号，键里带那台机器的指纹 | 用户裁决（2026-08-08）。问题 3：这个路径描述的是那台执行机，不是配置它的那台桌面端；A 配好之后 B 配对同一台机器就该直接可用。它有天然复合键（项目同步标识, agentred 指纹），**不需要另造 ULID 身份之外的东西**，冲突与墓碑复用项目那套。否：单向上报（B 要为每个（项目, agentred）重输一次路径，服务端上真正干活的那台机器名下还是空的） |
| 8 | 下行用轮询，不新建 websocket | 配置数据不需要实时，30s 级延迟对本规格的全部用户故事都够；桌面端到 server 今天只有请求-响应，与一条**按需拨给某台 daemon 的中转 WS**（问题 8），没有账号维度的常驻连接，加轮询是最小改动。否：桌面端开一条到 server 的**账号级**出站长连接——连接管理、重连与在线态会把复杂度提高一档，且那条链路属于块 2 的范围；复用既有的中转 WS 也不成立，它按目标 daemon 指纹寻址，账号下没有 agentred 时根本不存在 |
| 9 | 删除落墓碑，保留 30 天 | 问题 7。墓碑是双向同步下删除生效的唯一机制。30 天与决策 5 一致，超期由服务端与本地各自回收。否：硬删除（旧副本会把已删的行推回来复活）；否：墓碑永不回收（同步载荷随使用时长单调增长） |
| 10 | **Agent 带一个有序的执行目标列表，取代「绑定单个 backend」** | 用户裁决（2026-08-08）：「可以为 agent 做一个运行机器的排序，例如优先在本地跑，其次是 agentred……而不是我还需要选择机器；另外也可以手动选择执行的机器」。问题 4：今天 `agents.agent_backend_id` 是硬绑定，机器不在就只能改配置。改成有序列表后，新建会话时按顺序取第一个可用的（R15），用户也可以为单次对话手动指定（R15a）。这一条同时解掉了问题 3 的另一半——Agent 不再需要「属于某台机器」，因此账号下只有一个「开发」（决策 14）。代价：**`chat_svc` 的派发逻辑必须改**（从「取 backend 直接派发」变成「按序找第一个可用」），且必须明确会话粘性（决策 16）。否：保留单绑定 + 一个全局「默认执行机器」（改不了「这个 Agent 优先本地、那个优先构建机」这类差异）；否：保留单绑定、离线时报错让用户手改（今天的行为，正是用户要消除的） |
| 11 | 同步范围只限工作区配置，不含会话与消息 | 用户裁决（2026-08-07）：「server 层的对话应该是只记录由 server 发起的，除非从设备里面拿对话出来，指定同步某个设备的某个对话」。会话内容的所有权是「发起方即所有者」，与配置数据的「全端共享」是两套语义，不能混在一轮里。否：连 `chat_sessions` / `chat_messages` 一起同步（代码与 diff 长期留存在 server，是另一个量级的隐私承诺） |

## 跨机身份与引用

账号级的每一行获得一个在账号内全局唯一、终身不变的**同步标识**。同一个对象在任意桌面端上的本地自增主键各不相同，同步标识相同；跨机的一切引用都以同步标识或指纹表达。行还携带所属账号、同步版本号（决策 27）、最后修改时间、最后修改来源设备与删除时间五项同步元数据。

这五项里，**同步标识终身不变，同步版本号却只在一套 server 序列内有意义**——它由 server 的账号级序列分配，换一套序列（库重建、或指向另一套自建 server）之后，旧的版本号既比不了大小也不代表任何历史，必须整体作废，否则下行的版本守卫会反过来把新序列的正确数据挡在门外（R6b）。同步标识不随之作废：它的唯一性由 ULID 保证，与 server 无关。

**R1 — 跨机身份稳定。** 任一账号级对象在任一端被创建后，它在其余各端落地时保持同一个同步标识；本地自增主键的差异对用户不可见，也不参与任何跨机判断。

**R2 — 跨机引用解析到同一对象。** 同步载荷里的引用一律不带本地自增 ID 过机：

| 引用 | 上行翻成 | 落地翻回 |
|---|---|---|
| 项目的父项目 | 父项目的同步标识 | 接收端的本地 `projects.id` |
| 部门的父部门、Agent 的部门归属 | 部门的同步标识 | 接收端的本地 `departments.id` |
| Agent 的父 Agent、部门的负责人 Agent | 该 Agent 的同步标识 | 接收端的本地 `agents.id` |
| Agent 执行目标列表里的每一项 | 它所属 Agent 与它指向的 backend **两个**同步标识 | 接收端的两个本地 ID |
| 成员关系的项目与 Agent | 双方的同步标识 | 接收端的两个本地 ID |
| backend 与路径记录指向的 agentred | 该 agentred 的**指纹**（决策 20） | 接收端 `paired_agentreds` 里同指纹那行的本地 ID |
| backend 的 LLM provider | `llm_providers.provider_key` 原样（它本就是字符串键） | 接收端同 key 的本地 provider |

在任意端上，这些引用解析出的对象与源端一致。指纹是**账号级唯一**的，不是本规格新造的约定：前置规格已让 agentred 用 `rpc.DaemonFingerprint(instance uuid)` 登记进 server 的 `devices.fingerprint`（`cmd/agentred/login.go:126`），与桌面端 TOFU 配对存进 `paired_agentreds.daemon_fingerprint` 的是**同一个字符串**（`server_svc/login.go:238`：「matches the LAN pairing fingerprint byte-for-byte」）。因此服务端可以直接把它 join 到 `devices`，web 控制台不需要额外的映射表就能说出「这条配置属于哪台机器」。

**`device_id` 为空的 backend 不翻译成任何机器**——它表示「当前这台桌面端」，是个**相对**引用（决策 14）：同一个 backend 在 A 上指 A、在 B 上指 B。这正是「优先在我面前这台跑」想要的语义，也让「新增一台桌面端」不必回头去改每个 Agent 的目标列表。

**R2a — 引用目标未到达时不写悬空引用。** 引用的目标尚未到达（乱序）时，该行暂缓落地并在目标到达后完成。暂缓的行保留 30 天（与墓碑窗口一致）；超期仍未等到目标则丢弃，并以「引用丢失」为原因进入 R5 的「没能同步的改动」列表。

**R2b — 本机没有配对某台 agentred 时，指向它的那一档不可用，它上面的项目路径不呈现。** 判据是**本地配对表里有没有这个指纹**，而不是有没有配对令牌：前置规格已让账号凭据可以替代失效的配对令牌（`conn_pool.go` 在读不到令牌时改出示 `auth.account`），但连接仍然要求本地有那一行——`Borrow` 在 `row == nil` 时直接 `ErrDeviceNotFound`，因为行里还带着 `URL` / `TLSMode` / `TLSCertPEM`。

具体表现：

- **Agent 照常可见可用。** 它的执行目标列表里指向那台机器的那一档被视为不可用，按 R15 自动跳到下一档。只有当**所有**档都不可用时，才提示「这个 Agent 现在没有可用的执行机器」。
- **backend 本身照常存在**（它是账号级配置），只是在本机解析不出可用的执行机器。
- **那台机器上的项目路径记录**在本机不参与工作目录解析，也不出现在项目的路径列表里。

本机取得该指纹的配对行后，以上一切**自动生效**，用户不需要做第二件事；解除配对时退回，数据不丢。**不为这些状态做「待配对」的列表、提示或角标**——用户还够不着那台机器时看到一堆待处理项没有价值，而配对本身是比这些配置重得多的一步，要用那台机器时自然会先做。

## 双向同步的行为

本节约束全部账号级对象。

**R3 — 改动最终到达所有端。** 在任一已登录桌面端上新增、修改或删除账号级对象后，该改动最终出现在同账号的其余全部已登录桌面端与 server 上。上行由编辑当场触发（不可达时按 R7 入队），下行按 30 秒周期轮询；因此「最终」的上界是一个轮询周期加一次网络往返。

**R4 — 并发修改必然收敛。** 两台桌面端在互不知情的情况下修改同一行时，所有端最终收敛到同一个版本：**同步版本号较大者胜**；理论上相同时按来源设备标识的字典序决定。任意到达顺序下结果相同。

同步版本号由 server 在收到上行时分配，取自一个**账号级单调递增序列**（决策 27），客户端提交的时间戳一律不采信；`sync_updated_at` 仍然落库，但只用于展示与 30 天窗口计算，不参与胜负比较。序列单调保证了任意两个版本都可比，字典序那条平局规则因此实际上永不触发，仅作兜底保留。胜负比的是**到达 server 的先后**而非编辑发生的先后：一端离线数小时后补推的编辑，会赢过在线端在这段时间里做出的更晚编辑。被它覆盖的版本按 R5 进入「没能同步的改动」列表。

**R4a — 上行携带基版本，冲突可判定。** 每次上行都带上该行**本端最后一次见到的同步版本号**（本端新建、server 从未见过的行，基版本为空）。server 比对：

- 基版本等于该行当前版本 → 正常接受，分配新版本号。
- 基版本与当前版本不符 → **判为冲突**。仍按 R4 让后到者胜（本次上行照常生效），但 server 在应答里明确回报被覆盖的是哪一版、来自哪台设备，上行端据此按 R5 落一条「被覆盖」记录。
- 基版本为空但该同步标识在 server 上已存在 → 同样按冲突处理，避免两端各自「新建」出同一个标识。

没有基版本这一维，「我的改动被他端覆盖」与「他端后来又正常改了一次」在数据上完全同形（决策 27），R5 的追回承诺就无从兑现。

**R4b — 路径记录按自然键去重。** `project_locations` 的账号内自然键是（项目同步标识, agentred 指纹）（决策 26）。两端在互不知情的情况下各自为同一台 agentred 配了同一个项目的路径时，两行带着不同的同步标识落在同一个自然键上——**由 server 在上行时合并成一行**：按 R4 判出胜者并沿用它的同步标识，落败的那份落墓碑并按 R5 进入列表。合并在 server 做而不是让每台桌面端各自做，是因为 server 已经是唯一时钟源，一次合并的结果对所有端一致。

**R5 — 没能生效的本地改动可追回。** 本地的一次改动最终没能生效时，那个版本写入本地留存 30 天，并出现在桌面端设置的**「没能同步的改动」**列表里。三种路径共用这一份列表（决策 12），每条标明**原因**：

- **被覆盖**（本条）——本端的修改被他端更新覆盖，判据是 R4a 的基版本不符；记录覆盖发生的时间、对象与来源设备。R4b 里被合并掉的那一份也记在这里。
- **引用丢失**（R2a）——依赖的对象超期未到达，整行被丢弃。
- **超时未上传**（R6a）——设备离线超窗口，重同步后该条与全量快照冲突。

每条都可展开查看内容并恢复成当前值。**发生时界面不弹出提示、不出现横幅，也不改变任何角标**——用户只在主动去看这份列表时才会知道。恢复是一次普通的本地修改，按 R3 正常上行。

**R5a — 恢复一个已被删除的对象时明确拒绝，并可另建。** 恢复的目标若已在别处被删（server 上是墓碑），这次恢复按 R4a 的基版本判定被拒绝，界面明说该对象已被删除、恢复不会让它回来（决策 29），并就地提供一个**「按这份内容新建」**的动作——分配新的同步标识、作为一个新对象正常上行。

**R6 — 删除不会被复活。** 在任一端删除某个账号级对象后，该删除最终到达所有端；持有旧副本的端不会把它重新推上来。删除记录保留 30 天后由各端自行回收。

删除一个项目时，它名下的路径记录与成员关系一并落墓碑并随之上行；删除一个 Agent 时，它的成员关系与执行目标列表项一并落墓碑；删除一个 backend 时，引用它的执行目标列表项一并落墓碑（Agent 本身不删——它可能还有别的档，全没了就按 R15 提示没有可用机器）。

**这三条级联与删除由哪一端发起无关。** 控制台的「解除授权」（以及机器上的 `agentred unclaim`，它走同一条服务端路径）按 R14 把只属于那台机器的 backend 与路径记录落墓碑时，backend 那一条的级联**同样由服务端补齐**。少了它，backend 成了墓碑而引用它的执行目标行还活着：账号里既有的桌面端靠本地兜底看不出问题（解析不到 backend 的那一档按 R15 判为不可用并跳过），但**一台新登录的桌面端**会在全量快照里收到这条存活的行、按 R2a 暂缓、30 天后以「引用丢失」记进 R5 的列表——用户在一台全新机器上莫名收到一条追回记录，而那个对象其实是被正当删除的。

级联的判据是**引用关系本身**（执行目标载荷里的 backend 同步标识等于被删的那个），**不是 agentred 指纹**——执行目标属于账号、身上没有指纹，引用其它仍然活着的 backend 的那些档一律不动。路径记录落墓碑不产生级联（没有东西引用它）。载荷读不懂时按「不引用」处理：漏删最坏是接收端按 R2a 暂缓一次，多删的却是用户还在用的配置。

**R6a — 超窗口离线的设备先重同步再上行。** server 记录每台设备最近一次成功同步的时间。距今超过墓碑保留窗口的设备，其上行一律被拒绝，桌面端必须先拉取一份全量快照并以之为准。重同步之后，队列里的每一条按 R4a 的基版本判定去留：

- **基版本为空**（本端在离线期间**新建**的行，server 从未见过）→ **照常上行**。它不是复活，拦下来只会白白丢掉用户离线期间建的东西。
- **基版本非空、且与快照里该行的当前版本不符** → 拦下，以「超时未上传」进入 R5 列表。
- **基版本非空、但该同步标识在快照里已不存在**（墓碑都回收了）→ 拦下，同上。这一条正是复活风险本身。

首次登录的设备在 server 上没有「最近一次成功同步」的记录，**不算超窗口**，照常走正常上行。

**R6b — server 不认识本端游标时，重建并把它没见过的行重推上去。** 本端游标超过该账号同步版本序列的当前头部时，server 明确回报**「游标未知」**，桌面端据此丢弃旧序列的版本号、从头拉一份全量快照，并把快照没送来的存活行重新上行。

判据是**序列头**，不是 `MAX(version)`：墓碑被回收干净的账号 `MAX` 会掉回 0，用它会把游标合法的设备误判成要重建。序列才是「这个账号的历史走到哪」的权威。

这条要覆盖的是「server 那边换了一套序列」——库被重建、或用户把同一台机器指向了另一套自建 server。此时本端每一行都自称属于本账号、带着旧序列的版本号，而 server 一行都不认识：上行没有触发源（认领只捡从未归属过的行），下行永远拉回空页（游标高于新序列的全部版本），**两个方向同时静默失效，而界面一切正常**。

- **处置与 R6a 恰好相反，两条不可共用一条代码路径。** R6a 是「server 认识这段历史、但你落后太多」，所以拦下上行、以快照为准；R6b 是「server 不认识这段历史」，所以必须把本端还活着的行推回去。因此两者用**不同的错误码**区分，而不是靠「哪个端点回的」推断——推断能work，但把区别编进线上协议才挡得住下一次重构把两条路合并。
- **硬边界：不得复活墓碑。** 重推的对象只能是「快照落地之后版本号仍为空」的**存活**行。次序不可换——先丢弃旧版本号（否则下行的版本守卫会把整份快照挡在门外：本地是旧序列的 500，快照是新序列的 3），再落快照（墓碑在这一步生效，server 认识的行同时拿到新版本号），最后才挑重推对象。反过来任何一步，都会把 server 已正当删除的行当成「它不认识的行」推回去。
- 重推一律以**空基版本**上行：新序列确实没见过这个标识。若它其实见过（另一台桌面端已先推了同一个同步标识），按 R4a 正常判冲突、后到者胜，被覆盖的那一版按 R5 进列表——不静默丢。
- **已知限制**：快照落地并存好游标之后、重推入队之前若进程崩溃，本轮重推丢失，而 server 此后不再回报「游标未知」（游标已经合法），那台设备会重新回到静默状态。窗口是毫秒级，本轮不为它引入「重建进行中」的持久标记。

**R7 — 离线照常编辑，联网后补齐。** 桌面端未联网或 server 不可达时，本地对账号级对象的增删改照常生效并进入待同步队列；恢复连通后队列内容按序上行，不丢失、不重复应用。同步失败按退避重试，且不影响任何本地功能。离线期间对本机路径的编辑同样照常生效，恢复后由下一次快照上报带上（R16）。

**R8 — 同步不阻塞本地操作。** 上行与下行都在后台进行；用户的任何一次编辑都不因同步未完成而被阻塞或回滚。

## 项目路径

路径的两套存放方式保持不变：本机路径住在 `projects.path`，agentred 上的路径住在 `project_locations`。前者只上报（决策 6），后者属于账号、键里带指纹（决策 7）。

**R9 — 本机路径不串机。** 项目同步到桌面端 B 后，B 上该项目不带 A 的本机路径；B 在自行指定之前，该项目在 B 上处于**未配置本机路径**状态。Windows 与 Linux / macOS 之间的本机路径格式差异因此从不跨机相遇。

**R10 — 未配置是显式状态，不是空字符串。** 「未配置本机路径」由 `projects` 上的一个独立状态承载（决策 21），项目行照常落地、照常出现在项目树里（名称、图标、颜色、层级、排序都在），只是标注为本机未配置。**不存在 `path` 为空却被当作已配置项目的情形。** 处于该状态时：

- **会话照常可以起**（决策 34）——只是「本机」那一档按 R15 判为不可用，会落到某台配了这个项目路径的 agentred 上。换新机器登录后不必先配完所有路径才能干活。**只有当全部档都不可用时**（本机没路径、且没有任何一台在线的 agentred 配了它）才起不来，此时界面按 R15 逐档说明原因，并就地提供指定本机路径的入口。
- 落到远端档的会话，其工作目录是那台机器上的路径；本机的这个「未配置」状态不参与它的解析。
- 工作目录解析对这种状态返回一个**专用的、与「远端设备未配置路径」和「自由会话无 cwd」都可区分**的确定错误，而不是空字符串加 `nil`。
- 该错误会同时出现在**会话文件面板**上——文件面板经 `chat_svc.ResolveSessionWorkspace` 拿 cwd（`bootstrap/cago.go:140` 注入给 `workspace_fs_svc`），今天空 cwd 一律报 `WorkspaceFsNoCwd`。本状态**不复用**那个错误码：三种「没有 cwd」混成同一个提示，用户看不出该去哪里修。
- 用户指定路径后该状态解除，项目此后与本机创建的项目无任何差别。

「未配置」的语气因此是**「本地跑不了，远端可以」**而不是「这个项目坏了」——项目树里的角标与文案都按这个定。

**R11 — 已配置项目的工作目录解析逐字节不变。** `projects.path` 的读写路径、`ResolveSessionCwd` 的分流逻辑与 `project_locations` 的既有查询语义都不因本轮改变；单机场景与任何已配置路径的项目，其解析结果与本轮之前逐字节一致。本轮按决策 6 清点的 6 个使用点分两类各加一条分支：

- **解析点**（未配置时返回上述确定错误，而不是空串）——`project_svc.ResolveSessionCwd`（会话）、`project_svc.ResolveProjectCwd` 的本机分支（终端，`app/terminal.go:20`）、`chat_svc.ResolveSessionWorkspace` 经由的那条链（文件面板）。
- **读取点**（未配置时按状态位表达，不再依赖 `path` 是否为空）——`project_svc/project.go:81` 的 `os.Stat` 存在性校验、`Project.Check`、`Project.IsGitRepo`、`ctl_svc/gateway.go:81` 的项目清单。`chat_svc/chat.go` 经 `ResolveSessionCwd` 取值，随解析点自动生效。

既有的九例回归用例——`chat_svc` 侧 6 个 `TestResolveSessionCwd_*` 函数（5 个在 `chat_internal_test.go`，1 个在 `cwd_external_test.go`）加 `project_svc/cwd_test.go:31` 的 3 个 Convey 子例——全部保持原样通过。

**R11a — 登录前已有的项目可手动合并。** 桌面端登录后，账号里的项目与本机登录前已存在的项目各自独立存在，系统不做任何自动匹配（决策 22）。项目界面提供「合并到已有项目」动作，作用于**任意两个本地项目行**：用户为其中一个选定另一个，合并后只剩一个项目——沿用账号里那一个的同步标识（两边都没有时沿用先创建的那个的），保留本机项目的本机路径。

合并必须改挂**全部** `project_id` 引用，一处不落：`chat_sessions`、`project_agents`、`projects.parent_id`、`issues`（`issue_entity/issue.go:41`）与 `project_locations`。最后一处按 R4b 的自然键处理：两边对同一台 agentred 各有一行时按 R4 取胜者、落败者按 R5 记录；只有一边有的直接改挂。合并后不允许留下任何指向已消失项目的引用。

## 账号绑定与生命周期

**R12 — 未登录的桌面端行为不变。** 桌面端未登录账号时，本规格引入的一切都不存在：不产生网络请求、不改变任何既有界面、不改变任何既有数据的读写路径。新增的同步元数据列在本地写入，但不产生可观察差异。

**R12a — 登录前已有的行首次登录时照常带自己的同步标识上行。** 同步标识在行创建时就地生成，未登录期间也照常写入（R12）。首次登录时，这些**尚未属于任何账号**的行归入当前账号并带着自己那个标识正常上行——它们不是别人的数据，只是还没上过云。因此双机办公的用户两边各有一份同一个仓库的项目、各建过一个「开发」时，账号下会各出现两份，由 R11a 的手动合并收拾（项目）或用户自行删掉多余的那个（Agent）。这与 R13a 的**换**账号是两码事：那里的行属于另一个账号，标识必须丢弃。

**R13 — 登出不删数据。** 桌面端登出后停止同步；本地数据与 server 上的副本都保留。再次登录同一账号后恢复同步，期间双方的改动按 R4 收敛。

**R13a — 换账号登录不把上一个账号的数据带过去。** 同步元数据记录所属账号（`server_state.ServerUserID`，登出时被 `ClearLoginFields` 清空，同步元数据不受影响）。登录的账号与本地行记录的账号不同时，这些行**不上行、也不携带原同步标识**。上一个账号的同步标识与「没能同步的改动」记录留在本地，不发往新账号。

**R14 — 解除授权即停止同步，并清掉只属于那台设备的行。** 用户在 web 端解除某台设备的授权后，该设备的上行被拒绝、下行停止。拒绝的时机受前置规格 R4 的吊销延迟约束。

**工作区本身不随解除授权消失**：`projects`、`departments`、`agents`、成员关系一行不动——它们属于账号，不属于任何一台机器。

**但按指纹归属的那两类跟着消失**（用户裁决 2026-08-16）：`agentred_fingerprint` 命中该设备的 **agent backend** 与 **项目路径记录**。它们的意义完全依附于那台机器——机器不在账号里了，一个指向它的 backend 只会作为「永久不可用的一档」挂在执行目标列表里，一份它上面的路径记录再也不会被任何人用到。

- **落墓碑，不是硬删。** 每台桌面端都持有副本：硬删的话它们永远学不到，而其中任何一台一旦编辑那一行，就会被当成新对象重新推上去——**复活**，直接违反 R6。落墓碑并分配新版本号，走正常下行传播。
- **级联按 R6 执行**：backend 落墓碑时，引用它的执行目标列表项一并落墓碑。
- **失效方向与撤销一致**：撤销本身（拉黑 jti、吊销令牌链、设备置删）已经生效，这一步是它的从属后果——失败只记日志，不回滚、不让撤销报错。
- **对任何 kind 的设备都适用**：桌面端在 R13 认领后同样带着自己的指纹，撤销一台桌面端会清掉指向它的那几档。
- `agentred unclaim` 走的是**同一条服务端路径**（它 best-effort 调用同一个撤销接口，见前置规格 `2026-08-03-account-relay.md` 的 R19），因此不需要第二套实现，也不会与本条产生行为差异。

## Agent 的执行目标

**R15 — Agent 带一个有序的执行目标列表，新建会话时取第一个可用的。** 列表的每一项是一个 backend（决策 10）；backend 的 `device_id` 决定它指向哪台机器：**空 = 当前这台桌面端**（相对，R2），**非空 = 那台 agentred**。可用性判据：

- 指向当前桌面端的档：本机可用，除非该 backend 自身不可用——判据是既有的 `BlockReason`（决策 37），不是本轮新造的东西。
- 指向某台 agentred 的档：本机**已配对**该指纹（R2b）**且**该 agentred **在线**才可用。在线态取自既有的 `remote_device_svc`，前端 `AgentView` 已带 `online`，不新造。
- **会话绑定项目时再加一项**：该档所在的机器上，这个项目**配了路径**才可用（决策 34）。本机档看 `projects.path`，agentred 档看 `project_locations` 里该指纹那一行。不绑项目的会话不受这一项约束。

按列表顺序取第一个可用的。全部不可用时不静默失败，明确告诉用户「这个 Agent 现在没有可用的执行机器」并列出每一档为什么不可用（未配对 / 离线 / **这台机器上没配这个项目的路径** / 既有的各类 `BlockReason`——绑的供应商在本机找不到、未激活、类型不匹配、或远端那台机器上没有）。

列表为空的 Agent 不能起会话——界面在保存时就要求至少一项。

**列表内的档可以是不同的 backend 类型**（决策 32）；由此对技能目录产生的呈现要求见 R15e。

**R15a — 可以为单次对话手动指定机器，时机是发第一条消息之前。** 建会话本身不多一步：三个既有入口（`agentList.newSession`、`commandPalette.newChat`、`chatPage.add.newChat`）都是一键直接建，**不引入任何前置的选机器表单**。改选发生在空会话态（`chat-panel.tsx:2624` 的 `showNewSessionPrompt`）——会话行已建、一轮都没跑、什么都还没在任何机器上执行，此时改机器零成本。手动指定只作用于这一次会话，不改动 Agent 的列表本身（用户故事 4）。当前不可用的档列出但不可选，并说明原因。

**选中结果在起轮前是活的**：还没发第一条消息期间，可用性变化会重新算并更新提示（措辞随之从「将在 X 上运行」变成「改为在 Y 上运行」并给出原因）。否则用户看着「将在本机运行」按下回车、实际跑到了别处。

**R15b — 会话粘在它起初落到的那一档上；「落到」发生在第一轮。**（决策 36）钉住的是**档**而不是机器：同一台机器上可以有多档，续轮要沿用的不只是「在哪跑」，还有那一档的 backend 配置与**技能授权**（决策 33）。

会话行上记**它落到的那一档的同步标识**，与既有的 `exec_device_id` / `exec_daemon_fingerprint` 并列，由 `UpdateExecDaemon` 那条专用单列更新（`chat_repo/session.go:426`）**一并写入**，并一并加进 `Update` 的 Omit 清单（`:390-394`）——三列同生共死，不拆成两个写入点。既有那两列的语义与用途一个字不动：它们是启动补齐按设备分组的取材条件（`ListRemoteExecSessions`）与「daemon 实例换了就清事件游标」的判据（`:432-435`）；新列只回答「哪一档」。

派发链路随之反转：**有值就按它解析 backend 与技能，没值才按顺序挑第一个可用的并写回。** 没值涵盖首轮与全部老会话，因此不需要数据迁移。这一反转是必须的——`chat_svc` 今天每轮都从 `a.AgentBackendID` 重新解析（`chat.go:665`、`:1555`、`ask_user_question.go:101`），不改的话换成列表后会自动变成「每轮重挑」，正是决策 16 禁止的中途漂移。

**落到远端档的会话同时占着两台机器**：会话行、标题与消息都在发起它的那台桌面端上（会话不同步，决策 11），执行、cwd 与 `provider_session_id` 在那台 agentred 上。这不是两份数据，是一件事的两头。其余桌面端要看这条会话，走「指定把某个设备的某个对话拿出来」那条显式路径（块 4，本轮非目标）——**拿过去之后它仍然钉在原来那一档上**：若那一档是发起端的「本机」，接收端跑不了它（桌面端不可被寻址，见非目标），只能读。

 排序只在**新建会话**时生效（决策 16），具体是第一轮实际起在哪台——建会话行本身不选定机器。此后会话的 cwd、`provider_session_id` 与全部历史都在那台机器上，续轮一律回到同一台，**不因为它离线就改派**。那台机器不可用时该会话明确报错（与今天远端离线的表现一致），并提供「用同样的开头新建一个会话」作为出路——把第一条消息带过去，新会话重新按顺序挑机器。

**R15c — 跨机时执行目标以指纹表达。** 同步一个 backend 时，`device_id` 沿 `paired_agentreds` 解析成指纹（决策 20），落地时翻回接收端的本地 ID；空 `device_id` 原样保持为空（相对引用，R2）。**服务端与对端只见指纹与空值，不见任何桌面端的本地自增设备 ID。**

**R15d — 从 web 派发时跳过「当前桌面端」这一档。**（块 3 的接口约定，本轮只定语义、不实现。）浏览器不是执行器，「当前这台桌面端」在 web 语境下没有指代对象，因此 server 按列表顺序挑选时跳过 `device_id` 为空的档，只在 agentred 里选。这意味着桌面端开着、用户却从 web 派活时，会落到 agentred 而不是那台桌面端——从浏览器派活时用户本来就不在那台机器前。

**R15e — 技能授权挂在单个执行目标上。** 执行目标列表可以混用不同的 backend 类型（决策 32），添加时不做类型限制；每一档**各自持有一份技能授权**（决策 33）。

- **存放位置从 Agent 行下沉到执行目标行。** `agents.skills_json` 不再被读取（列保留，与 `agent_backend_id` 同批由后续轮次删除），授权改存在 R15 新增的那张执行目标表上。迁移把每个 Agent 现有的 `skills_json` 原样复制进它那唯一一行，语义不变。
- **每一档只有一种后端、一台机器、一套包 ID。** 因此发现直接从这一档的机器发起（本地进程内调 CLI，远端走 daemon `skills.list`），「继承」明确指**这一档所在机器的 CLI 全局态**，`caps?.has("skills")` 也只对这一档判定——不支持技能的档显示既有的 `skillsGate` 提示，不影响别的档。**不需要并集、不需要「几台装了」的分母、不需要按类型分节。**
- **界面上有几档就并排堆几块，不做档位选择器。** 每块是一份既有的 `GrantedChips`（标题行带档位序号与「机器 · 后端」、自己的计数、自己的「管理技能」），点开仍是既有的 `CapabilityPicker`，只改 `subtitle`。**不采用「顶部选择器 + 只显示选中档」**：那是一个隐形的模式，用户无从确认眼前这份列表只作用于一档，而本条要求的全部目的就是让「各配各的」被看见。只有一个执行目标时序号不出现（R20）。
- **`device_id` 为空的「本机」档是相对引用**（R2）：它的授权跟着账号同步，但「装没装」与「全局态」由**当前这台桌面端**回答。同一档在两台桌面端上显示不同的继承态是正确的——「本机」本来就指各自那台。
- **档所在的机器离线时，授权照常可编辑，发现不可用。** 授权是配置（按包 ID 增删不需要目录），发现要真机。因此离线只**禁用「管理技能」按钮**并给出原因，**不禁用整块、不隐藏已授权项、不阻塞保存**；「继承」计数一并隐去而不是显示 0——它取决于那台机器的全局态，此刻不可知，**猜一个比不显示更坏**。
- **提供「复制自 ①」。** 决策 33 的代价是 N 份配置；三台都跑 Claude Code 的用户配一次然后复制即可。做成**拉取**（放在需要它的那一块上）而非推送。只在**同后端类型**的档之间可用——跨类型的包 ID 复制过去一个都对不上，置灰并说明原因。
- **删除一档时它的技能授权随之消失**，与该档一并落墓碑（R6）。

**R15f — 数据导出 / 导入跟上执行目标列表。**（决策 35）`data_svc` 的 bundle 里，Agent 增加一个**执行目标数组**，每项含它指向 backend 的稳定 key、`sort_order` 与该档的 `skills_json`；导入侧据此建目标行。`agents.skillsJSON` 与 `agentBackendKey` 两个字段**保留在 bundle 里但不再被导入侧读取**，与库里那两列同批由后续轮次移除。

读到**不含该数组的老 bundle** 时，按 `agentBackendKey` + `skillsJSON` 落成**单元素列表**（`sort_order = 0`）——与迁移是同一套转换，实现上共用一份代码。`agentBackendKey` 为空的 Agent 落成空列表（与迁移对 `agent_backend_id = 0` 的处理一致）。

**导出再导入必须保住执行目标与按档技能**，这是本条的验收判据：本轮之前它是隐性成立的（只有一个 backend、一份技能，字段直接搬），本轮之后必须显式实现，否则备份恢复会静默丢配置。

## 本机路径的上报

本机路径（`projects.path`）是本轮**唯一**归属单台桌面端的对象。每台已登录的桌面端把「本机为哪些项目配了路径」作为一份完整快照上报给 server，按设备分命名空间存放。条目由**项目的同步标识**与**设备**确定，其值是该机器上的真实绝对路径。

**R16 — 上报是本机路径在服务端的唯一来源。** 桌面端登录后，其本机路径清单出现在 server 上并标明所属设备；本地新增、修改或删除后，下一次上报使服务端的这份清单与本地一致。上报失败时保留服务端上一次的清单，按退避重试，不影响任何本地功能。

**上报的节奏是 30 秒一轮**：每个周期算一次整份快照的内容指纹，与上次成功上报的指纹不同才发，相同则跳过——本地编辑**不即时触发上报**。这与账号级对象「上行由编辑当场触发」（R3）刻意不同：上报是单向投影、没有对端在等，30 秒级的延迟对它的消费者足够。判据用内容指纹而不是时间戳，因为本机路径的修改不触及任何一张表的 `Updatetime` 之外的痕迹。

**那份指纹是一份「相对当前 server」的缓存，随 R6b 的重建一并作废。** 换一套序列之后 server 那边一条路径都没有，而本地内容并没有变——不作废指纹，这一轮乃至以后每一轮都会判定「与上次相同」而跳过，server 的清单永远是空的，web 端把每个项目都显示成「本机未配置路径」。这条失效尤其隐蔽：上报是纯投影、没有对端在等，**跳过和成功在任何界面上都长得一样**，谁都不会报错。

**R16a — 自定义头像按内容哈希单独传。** 同步载荷里的 Agent 只带 `AvatarDataURL` 的**内容哈希**，不带正文（决策 28）；接收方（对端或 server）尚未持有该哈希时才单独取一次那份正文。哈希参与内容比较，因此换头像照常触发同步。服务端按哈希存一份，被任何 Agent 引用即保留，无人引用即可回收。头像取不到或传输失败时，该 Agent 照常同步，只是暂时退回色块 + 图标呈现。 取正文失败或超时时**降级为占位字母头像**（既有 `AgentAvatar` 的 `initials` 分支），不阻塞该 Agent 的落地，也不重试到无限；下一次同步周期再试。

**R17 — 上报不改变本地数据。** 上报是纯读取：它不向本地库写入任何内容。服务端不存在向桌面端回写本机路径的路径。

**R18 — 设备的本机路径清单随设备存续。** 桌面端登出或被解除授权后，它上报的清单在服务端保留；该设备重新登录并上报后清单被新快照替换。用户在 web 端删除某台设备的记录时，该设备的这份清单一并消失（账号级对象里，**除按指纹归属的那两类之外**——agent backend 与项目路径记录，见 R14——不受影响：其余那些属于账号，不属于任何一台机器）。

## 界面与交互

### 桌面端

**同步状态**在设置中呈现：上次成功同步的时间、待同步条目数、以及不可达时的原因。不新增「正在同步」这类解释性横幅。

**「没能同步的改动」**是同步状态下的一份列表，承载 R5 的追回：每条显示发生时间、对象、**原因**（被覆盖 / 引用丢失 / 超时未上传）与来源设备（仅「被覆盖」有），可展开查看内容并恢复。列表为空是常态，空态如实说明「所有改动都同步成功了」。目标已被他端删除时，恢复按钮改为**「按这份内容新建」**并说明原对象已被删除（R5a）。

**组织架构 → Agent 详情里「选一个后端」改成「一列有序的执行目标」**（R15）——这是本轮唯一需要重做的既有控件，位置是 `org/org-detail-agent.tsx:462-515` 的 `data-slot="agent-section-backend"`（今天是一个单选 `Select`，`onValueChange` 直接 patch `agentBackendId`）。改成可增删、可拖拽排序的列表，每项显示它是哪个 backend、指向哪台机器（「这台电脑」或某台 agentred 的名字）与当前是否可用；不可用的标出原因（未配对 / 离线 / 项目在那台机器上没配路径 / 既有 `BlockReason` 的各类供应商问题）。至少一项，否则保存被拒。添加面板按机器分组列出账号下的全部 backend——**包括本机未配对的那些**（执行目标是账号级配置，在这台电脑上配、给另一台用是正常场景），只把与当前类型不符的档置灰（R15e）。拖拽排序**必须有键盘等价物**（聚焦后 `↑`/`↓`）：除可访问性外，e2e 里 dnd-kit 的 PointerSensor 对合成鼠标事件无反应，键盘是唯一能自动化的路径。

**只有一项时这个控件退化成今天的样子**（R20）：不显示序号、拖拽柄、「当前生效」徽标与排序说明——它们对单档而言都是零信息量。加入第二项时才出现。同理，R15a 的「选择运行机器」控件在单档 Agent 上整个不出现。

**技能一节（`data-slot="agent-section-skills"`）从渲染一份 `GrantedChips` 变成渲染 N 份，一档一块。** 授权下沉到单个执行目标（决策 33 / R15e）之后，**有几档就并排堆几块**：每块自带档位序号（与上面执行目标列表一一对应）、自己的计数、自己的「管理技能」按钮，点开的仍是既有的 `CapabilityPicker` 对话框，只在 `subtitle` 里写明「第 N 档 · 机器 · 后端 —— 只影响这一档」。

**不做「顶部一个档位选择器 + 下面显示选中那一档」**：那是一个**模式**，而模式是隐形的——用户看到一份技能列表，没有任何视觉线索告诉他这份只作用于一档，也无从确认自己正在编辑第几档；本节的全部目的恰恰是让「各配各的」被看见。堆叠把这件事交给布局本身表达。代价是纵向空间，但执行目标的现实条数是 2–3，每块只有一个标题行加一行 chips。

只有一个执行目标时**序号与「复制自」都不出现**，整节与今天逐像素一致（R20）。

每块的「管理技能」旁给一个**「复制自 ①」**（只在同后端类型的档之间可用，跨类型置灰并说明「包 ID 对不上」）——这是决策 33「N 份配置」那个代价的唯一对冲。做成**拉取**而非推送：需要它的人正盯着那个空块，一次点击就地解决。

### agentre-server（MySQL）

两组表，语义不同：

- **同步组**：项目、部门、Agent、backend、Agent 的执行目标、成员关系、agentred 路径，以账号与同步标识为主键，携带同步版本号、最后修改时间、最后修改来源、删除时间。backend 与路径另存它指向的 agentred **指纹**（空 = 桌面端本机），可直接 join 到 `devices`；agentred 路径在 `(账号, 项目同步标识, 指纹)` 上加唯一约束，R4b 的重复由 server 在这里一次性合并掉。
- **上报组**：只有本机路径一类，按上报设备分命名空间，以账号、设备与项目的同步标识为主键。整份快照替换（决策 18），因此不需要删除时间与冲突元数据。

另有一张**按内容哈希存放的头像表**（R16a），以账号与哈希为主键、与设备无关。

另需两处账号维度的状态：一个**单调递增的同步版本序列**（决策 27，同步组的每次写入取下一个值；账号内并发写极低，原子递增即可），以及每台设备**最近一次成功同步的时间**（供 R6a 判定，无记录 = 首次登录，不算超窗口）。

序列的**当前头部**另需一个只读取值口，供 R6b 判定游标是否已经超出这个账号的历史。它必须与下行分页读同一个库：将来若引入只读副本，这一读要强制走主库，否则副本滞后会把游标合法的设备误判成要重建（后果不是丢数据，是一次多余的重建加若干条 R5 记录）。

新增迁移追加到既有迁移列表末尾。`agentre-server/migrations/` 同样压缩过基线（`93ea7a5`），**当前最末一条是 `202605200005_device_flow_codes.go`**（`migrations.go:114` 的 `migration202605200005()`），本轮的迁移接在它后面。

## 安全、隐私、兼容性与可访问性

- **路径含个人信息。** 项目路径通常包含系统用户名与目录结构。本机路径不在桌面端之间流动（决策 6），agentred 路径在桌面端之间流动（决策 7）；两者都按用户裁决**带真实值到达服务端**，也都不得在 web 端呈现（R19）。自托管时风险有限；官方托管时这属于「服务端持有但不展示」的数据，需在隐私政策中如实说明。
- **Agent 的 prompt 长期留存在服务端。** `ToolsJSON` 是 `[]{Key, Enabled}`，Key 只可能是 `org` / `subagent` / `hook`（`internal/pkg/agenttool` 注册表）；`skills_json`（决策 33 之后住在执行目标行上）是 `[]{ID, Enabled}`，ID 是包标识加开关——Claude Code 形如 `name@marketplace`，Codex 是裸 `pluginId`（决策 32）。两者都无隐私分量。**`PromptJSON` 是用户逐行撰写的自由文本，是这里唯一敏感的一项。**

  它今天已经会离开桌面端：`wire.RunParams.SystemPrompt` 使远端执行的每一轮都把它传给 daemon，走中转时明文经过 server（前置规格决策 6）。本轮的增量因此不是「服务端能看到」而是「服务端长期存着」。用户裁决（2026-08-07）接受这一点，理由是块 3 要在桌面端关机时也能从 web 用自己的 Agent 发起对话。**这必须写进隐私政策。**

- **`agent_backends.EnvJSON` 是本轮新增的凭据扩散面。** 它是用户自填的透传环境变量（保留键拒入，但用户完全可以把某个服务的密钥放进一个自定义键）。决策 24 让 backend 整行跨机共享并到达服务端，这份内容随之扩散。本轮的处置：**照常同步与留存**（不同步它会让对端跑出与本机不同的行为，共享 backend 的意义打折），但**不发往浏览器**（R19）、**不进日志**，并在隐私政策与该输入框的说明文案里如实写明「这里的值会随账号同步到你的其他设备并留存在服务端」。
- **自定义头像会留在服务端。** R16a 把 `AvatarDataURL` 按内容哈希单独传并在 server 上留一份正文。分量比 prompt 低，但仍是用户上传的二进制，与 prompt 同属「服务端长期持有」，一并写进隐私政策；无人引用时回收。
- **凭据不上报。** 与 `wire.RunParams` 刻意不带 `Provider` 的既有判断一致（该结构注释：「Provider 含明文 APIKey，desktop 不该每个 turn 越线漂移到远端 daemon」），`llm_providers` 整表（含 `APIKey`）、配对凭据与钥匙串内容都不出本机。跨机只传 `provider_key` 这个字符串引用（决策 24）。
- **换账号不串数据。** 同步元数据记录所属账号，登录另一个账号时本地既有行不上行（R13a）。这是一条隐私边界而不只是数据正确性问题：一台共用机器上换账号登录，不应把上一个账号的项目名、Agent 与路径发到新账号下。
- **不进日志。** 路径、prompt 内容、`EnvJSON` 与同步载荷遵循既有日志红线，不写入日志。
- **兼容性。** 老桌面端（无同步能力）与新桌面端共存于同一账号时，老端不上行也不下行，本地照常工作；新端之间正常同步。两个方向都不需要强制升级。本规格不改变任何既有的 daemon 握手、中继信封或 wire 帧结构。**设备能力模型正由用户另行删除，本规格不依赖它**——设备连上账号即拥有完整权限，同步与派发都不做任何设备级权限判断。
- **可访问性。** 「本机未配置路径」「未配对」「离线」以及各类 `BlockReason` 状态不能仅靠颜色区分，均带文字。

- **桌面端作为可被调用的执行端。** 中继上只有 daemon 登记为可寻址（`/v1/relay/daemon`），桌面端是纯出站调用方（`/v1/relay/client`）；`agentre` 二进制是 GUI-only，daemon 在 `agentred` 里。因此「从 web 或从另一台桌面端派活到某台桌面端」本轮做不到，也不做——R15d 的跳过规则正是这个事实的直接后果。要做的话属于块 2/块 3 的架构范围。

- **backend 的每设备字段覆盖。** 见决策 24。`CLIPath` / `EnvJSON` 整行共享，本机不适用时软降级，不做「账号级一份 + 每设备覆盖」的两层结构。

- **会话中途改派执行机器。** 见决策 16 与 R15b。
- **设备级权限模型。** 用户裁决（2026-08-08）：连上账号即完整权限。相关的 `capabilities` 字段正由用户另行删除，本规格不新增任何设备级权限概念。
- **会话与消息的同步。** 见决策 11。
- **服务端向桌面端回写本机路径。** 见 R17。
- **主设备概念。** 见决策 2。
- **字段级冲突合并。** 见决策 4。

**本地端到端的三个前置条件**：

1. **server 跑在开发者环境里，不用容器。** 直接 `go run ./cmd/server`，MySQL 与 Redis 复用开发者已有的实例（由 `agentre-server/configs/config.yaml` 指定）。因此这套端到端**依赖开发者环境**：数据库不可达时它应当明确失败并说明缺什么，而不是静默跳过或伪装成通过。数据库版本可能与部署环境不同（CI 的 `agentre-server/e2e/docker-compose.ci.yml` 钉的是 mysql:9.7.2），跨版本差异属于人工验证的范围。
2. **绕过 GitHub OAuth 取得设备凭据。** 桌面端登录走 RFC 8628 设备流，终点是 GitHub OAuth，e2e 里无人可点。改为在 server 的 MySQL 里直接种入已授权的设备与令牌行——与 e2e 已在用的 `node:sqlite` 直读桌面端 DB 做 oracle 是同一类手法。每次运行使用独立的账号与设备指纹并在结束时清理。
3. **Go 模拟对端。** 走与桌面端同一套同步接口，可指定自己的设备指纹、平台、路径风格，以及**它配对了哪些 agentred 指纹**（R2b 与 R15 的可用性判定要验的正是这一维）。它不是第二个 Wails 实例——`e2e/README.md:100` 明写「本地一次只能跑一个 e2e」，bridge 端口 34216 与临时 data 目录都是固定值。本轮不做那项改造。

第 2、3 项属于本轮工作量，不是既有能力。

**刻意的取舍：**

- **对端不是第二个真桌面端。** 被验的是同步语义，不是对端的界面；用 Go 模拟对端可以省掉 e2e 骨架的端口与目录参数化。代价：对端一侧的 UI 状态（它那边的「本机未配置路径」、执行目标列表的可用性渲染）不在端到端覆盖内，由组件测覆盖。
- **靠人工验证**：真实两台物理机长时间使用下的收敛、断网数小时后的补推、真实 Windows 桌面端，以及 **R15 的完整回路**——在桌面端 A 上建一个「优先本机、其次构建机」的 Agent，关掉 A、在 B 上打开同一个 Agent 并确认它落到构建机上真的跑得起来。按 `docs/verification.md` 留证据到 `e2e/scratch/2026-08-07-workspace-sync/`。
- **覆盖较弱**：30 天留存与回收的边界（墓碑、R2a 的暂缓行、R6a 的超窗口判定）只能靠注入时间验「未到期保留」与「已到期回收」两点。决策 19 之后桌面端时钟不再影响冲突胜负，但 `last_sync_at` 与各类 30 天窗口仍以 server 时钟为准，server 自身的时钟异常不在本轮覆盖范围。
