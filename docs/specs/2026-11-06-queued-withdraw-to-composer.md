# 排队消息撤回到输入框

> Status: Approved（2026-11-06 修订：撤回被拒按宿主现有处理）
> Owner: 桌面端 + 共享 UI 包（agentre-ui），agentre-server 控制台跟随抬钉
> Last updated: 2026-11-06

**Objective:** 用户能把一条还没被 AI 取走的排队消息撤回到输入框，改完再发，原文不丢。

**Hard invariant:** 同一段文字不会既进了转录（被 AI 取走）又被放回输入框；撤回或恢复都不会覆盖用户正在写的草稿。

## Problem

1. **排队消息只能删，不能改。** 已核实：每条排队消息后面那颗 ✕ 的无障碍名叫「撤回这条排队消息」，点了只调 `CancelQueuedChatMessage` 把它从队列移走（`frontend/src/components/agentre/chat-panel/use-chat-actions.ts:484`），原文就没了。用户想改一个字，只能删掉再从头打一遍。
2. **桌面端「恢复为草稿」实际放回的是排队队列。** 已核实：`restoreDropped` 把轮末没发出的条目追加回原会话的队列（`frontend/src/stores/queued-messages-store.ts:150`）。这时这一轮已经结束，队列里不会再有人来取，按钮文案和结果对不上。server 控制台已经改成回到输入框（`agentre-server/frontend/src/components/session/SessionDetailView.tsx:1377`）。
3. **server 控制台「恢复为草稿」会覆盖已有草稿。** 已核实：它调的是 `restoreDraft`，这个接口会整体替换输入框内容，用户当时写了一半的字会丢。

## Actors and user stories

1. 作为桌面端用户，AI 还在跑的时候我发现刚排进去的消息写错了，我想把它撤回到输入框改完再发。
2. 作为桌面端或 server 控制台用户，回合结束时还有排队消息没发出去，我点「恢复为草稿」，希望它们回到输入框，而且不吞掉我正在写的内容。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | 每条可撤回的排队消息上有两个按钮：「撤回到输入框」（↶）和「删除」（✕） | 用户已决定（2026-11-06）。否决：把 ✕ 直接换成撤回，因为只想删掉的话要多一步 |
| 2 | 两个按钮一直显示，颜色弱化，悬停时高亮 | 用户已决定（采纳推荐）：和现在常显的 ✕ 一致，不用找。否决：只在悬停时出现 |
| 3 | 后端确认移除之后才回填输入框 | 已核实：后端对已被取走的条目返回 `ChatCancelNotFound`（`internal/service/chat_svc/chat.go:1741`）。先回填的话，AI 已取走时同一句话会出现两次。否决：乐观回填，失败再收回 |
| 4 | 回填是追加：输入框为空就直接填入；不为空就接在现有草稿后面，中间空一行 | 用户已决定（「接在后面、换行分开」）。用空行分隔，和 server 现有「恢复为草稿」把多条之间拼成空行的做法一致。否决：替换草稿（会丢字）、插到草稿前面 |
| 5 | 桌面端「恢复为草稿」改为把这些条目按排队顺序追加进输入框（规则同决策 4），不再放回队列 | 用户已决定（2026-11-06）。否决：保持放回队列——这一轮已经结束，没人会来取 |
| 6 | server 控制台的「恢复为草稿」也改成追加，不覆盖草稿 | 由不变式推出。否决：维持覆盖——会丢用户正在写的字 |
| 7 | 撤回和删除的状态迁移由两个宿主共用一份逻辑，「撤回到输入框」作为共享排队条组件上的一个**可选**回调；宿主没接这个回调时不显示撤回按钮 | 已核实：排队条和它的状态归约已经在共享包里，两个宿主都在用（`frontend/packages/agentre-ui/src/composer/queued-messages-bar.tsx`、`steer-queue.ts`）。设成可选的话，server 抬钉之前行为不变。否决：各宿主自己画按钮 |

## 排队消息条

**前提**：会话正在跑一轮，排队条里至少有一条消息，而且对端支持撤回（`cancellable` 为真）。

- **撤回到输入框**：用户点某条的 ↶。这一条的两个按钮立刻变成忙碌态（↶ 转圈、两个都不可点）。宿主请求后端撤回这一条：
  - 后端确认移除了，这条从排队条上消失，原文按决策 4 追加进输入框，输入框获得焦点，光标停在末尾。
  - 后端拒绝（已被 AI 取走、这一轮已结束，或其他错误），输入框不变，按各宿主现有的「撤回被拒」处理把后端原话告诉用户（用户已决定，2026-11-06）：
    - 桌面端：显示「撤回失败：原因」提示条，这一条的按钮回到可点状态。
    - server 控制台：和它现有的删除被拒一样，这一条转成锁图标、悬停显示后端原话，撤回和删除都不再提供。server 没有提示条可用；代价是非「已取走」原因（如网络错误）被拒时，这一条会一直锁到本轮结束。

    如果这条确实已被取走，它照常经由「已消费」事件离开排队条，进入转录。
- **删除**：用户点 ✕，行为和现在的单条撤回一样：后端移除，内容不进输入框，失败时显示同样的提示。
- **清空**：表头的「清空」和现在一样，整批删除，内容不进输入框。
- **对端不支持撤回** 或这条还没拿到句柄（`cancellable` 为假）：只显示锁图标，没有 ↶ 也没有 ✕，和现在一样。
- **没接撤回回调的宿主**：只显示 ✕，和现在一样。
- 排队消息的文字照旧可以选中复制；点文字本身不会触发撤回。
- **文案与无障碍**：↶ 的无障碍名和悬停提示是「撤回到输入框」/「撤回到输入框编辑」，✕ 是「删除这条排队消息」/「删除（不放回输入框）」。中文和英文都走共享包的 i18n。两个按钮都能用键盘聚焦，有可见的焦点样式。

**输入框处于「编辑历史消息」状态时**：排队条照常显示，但 ↶ 不可点，悬停提示「先完成或取消编辑」。因为这时输入框里是那条历史消息，撤回下来的文字混进去会被当成对它的修改。✕ 和「清空」不受影响。如果用户点了 ↶ 之后、后端还没应答就进入了编辑状态，撤回照常完成，文字等编辑结束后再追加进输入框，不会丢。

## 轮末未发出的消息

**前提**：一轮结束时还有排队消息没被 AI 取走，输入框上方显示「回合结束时 N 条消息未发送」横幅。

- **恢复为草稿**（两个宿主）：这些条目按排队顺序拼起来，条目之间空一行，再按决策 4 追加到输入框；横幅消失，输入框获得焦点。桌面端不再把它们放回排队队列。
- **丢弃**：和现在一样。

## Out of scope

- 排队消息带图片：流式进行中带图发送会被拒绝（`imageWhileStreaming`），队列里只有文字。
- 在排队条里直接编辑。
- 撤回或删除后的「撤销」。
- 已发图片的查看与复制：另见 `docs/specs/2026-11-06-image-viewer-and-copy.md`。

## Testing decisions

| Seam | What it verifies | Prior art |
|---|---|---|
| 共享排队条组件（Vitest + RTL） | 可撤回的条目显示 ↶ 和 ✕，各自回调收到正确的 id；忙碌态下两个都禁用；没接撤回回调时只有 ✕；不可撤回时只有锁 | `frontend/packages/agentre-ui/src/composer/queued-messages-bar.test.tsx` |
| 共享输入框句柄（Vitest） | 追加草稿：空输入框直接填入；有草稿时接在后面并空一行；光标在末尾 | `frontend/packages/agentre-ui/src/composer/chat-composer.test.tsx` |
| 桌面端撤回动作（Vitest，mock Wails 绑定） | 后端确认移除才追加进输入框；后端拒绝时输入框不变并显示失败提示 | `frontend/src/components/agentre/__tests__/chat-panel.test.tsx`（已覆盖撤回 RPC） |
| 桌面端排队 store（Vitest） | 「恢复为草稿」不再把条目放回队列，交出的文字按顺序用空行拼接 | `frontend/src/stores/__tests__/queued-messages-store.test.ts` |
| server 控制台（agentre-server Vitest） | 接上撤回回调；「恢复为草稿」追加而不覆盖草稿 | `agentre-server/frontend/src/__tests__/session-detail.test.tsx` |

无法自动化的部分：真实后端下「点撤回的同时 AI 正好取走」这个竞态。收尾时用验证台加 fake runtime 观察一次桌面端：撤回成功 → 回填；对已被取走的条目撤回 → 失败提示、输入框不变。
