# LLM 供应商与模型绑定的界面重构

<!-- File: docs/specs/2026-08-13-provider-binding-ux.md -->

> Status: Approved
> Owner: LLM configuration / chat runtime（前端）
> Last updated: 2026-08-13

**Objective:** 让「这次会跑哪个模型」和「这个操作能不能做」在供应商管理、Agent 后端绑定与会话/路由的模型选择器里一眼可见，并补上模型的批量选择与批量删除。

**Hard invariant:**

1. 不改动 [2026-08-11 LLM Provider 多模型与统一 ModelTarget](./2026-08-11-llm-provider-models.md) 已批准的领域语义：ModelTarget 三态、引用保护、默认模型动态跟随、切换自下一轮生效、凭证执行侧本地化、远端目录门控与显式同步。
2. 不新增后端服务方法或 Wails 绑定；本轮只重排前端已能拿到的数据。例外一（2026-08-13 经用户批准）：`ProviderItem` 增加只读 `modelCount` 字段，由 `ListLLMProviders` 一次 GROUP BY 按 provider 计数填充（新增 `llm_provider_repo.CountModelsByProvider` 仓储方法，不新增服务方法 / Wails 绑定），用于左栏供应商行显示模型数。例外二（2026-08-14 经用户批准）：`peer_svc.RunFreshRequest` 增加 `ProviderKey` / `ModelKey` 两个字段，让派到对端桌面的会话带上自己的模型目标；不新增服务方法 / Wails 绑定。
3. 不把界面上的状态说得比后端能证明的更确定：后端不持久化的信息不得渲染成持久状态。

## Problem

现状证据来自一次驱动真实桌面应用的取证（中文 locale，1280×860 与 860×640 两种窗口）。截图是本地 `e2e/scratch/` 产物、不进入提交，下文按文件名引用；每条问题同时给出对应的源码位置。

1. **供应商页套了三层容器。** 页面标题「LLM 供应商」下面还有一层卡片头「已配置的供应商 / 共 4 个 / 新增供应商」，再往里才是左栏 + 工作区；中间那层只重复了标题与计数，白占约 70px 纵向空间（`03-providers-list.png`）。
2. **同一个入口出现两次且叫法不一致。** 卡片头是「新增供应商」，左栏底部是「添加供应商」，两者行为相同（`llm-providers.tsx` toolbar.add 与 nav.add）。
3. **供应商启用状态被表达三次。** 左栏行尾「已启用」、工作区 header 的绿点「已启用」、开关旁边再写一次「已启用」（`provider-workspace.tsx` header）。
4. **Provider header 五个操作平级并排。** 启用开关、测试、删除、编辑连接、发现模型挤成一排，其中破坏性的「删除」常亮 `status-error` 红色，与常规操作抢注意力（`03-providers-list.png`）。
5. **模型行把机器用的稳定引用当成主信息。** 行内第二显眼的位置是 UUID `modelKey`（如 `db558221-4618-4e6b-a4b3-583fc562dfa0`），而用户维护的 display name 根本不显示；旁边的「已启用」又与行尾 switch 重复表达同一状态（`provider-workspace.tsx` 模型表 + `06-providers-list-openai.png`）。
6. **「能不能做」只有做了才知道。** 被引用的模型删不掉、默认模型停不掉都是后端已实现的规则，但界面事前既不显示引用数也不给原因，用户点下去才收到错误。
7. **发现并导入的结果不可读。** 弹窗把远端模型平铺成一列，没有分组、没有「新 / 已存在」区分、没有全选；拉取失败时把上游原始 JSON（`http 401: {"type":"error","error":{...,"request_id":"..."}}`）整段铺给用户（`05-provider-discover-dialog.png`）。
8. **Agent 后端列表把绑定混在一串元数据里。** 行的第二行是 `类型 · CLI 路径 · 供应商名 · 模型 · 使用数` 的等宽拼接（`agent-backends.tsx:794-805`）：绑定与 CLI 路径同权重，没有品牌标识；`llmModelKey`（空即跟随默认）已在 DTO 中却未被使用，因此看不出该目标是动态跟随还是固定；`llmProviderActive` 同理，失效只降级成一个整行警示色；行上也没有直接更换绑定的入口，必须先进编辑弹窗。未绑定时该段退化成「走 CLI 自身登录」（`08-backends-list.png` 中两个后端均为此态）。
9. **绑定字段名与它选的东西不符。** 编辑器里叫「LLM 供应商」，实际选的是 Provider + Model 组合；触发按钮只显示「CLI 自身登录态」，不显示解析出的真实生效模型 —— 而 2026-08-11 spec 的「Backend and Route flow」明确要求展示当前解析出的生效模型（`09-backend-editor.png`）。
10. **三个模型来源平级堆叠。** 主绑定、模型分级路由、自定义模型在同一个长表单里并列，没有主从关系，也不说明「自定义模型只在 CLI 登录态下生效」；「严格匹配 · anthropic」是实现术语（`09-backend-editor.png`）。
11. **选择器的顶部特殊项等于盲选。** 「跟随 Agent 绑定」只有一行光秃秃的文字，不告诉用户它会解析成哪个供应商/模型，或是走 CLI 登录态（`13-chat-model-picker.png`）。
12. **两种目标语义在视觉上不可区分。** provider-default（动态跟随默认，会随默认变化）与 fixed-model（锁定，不随默认变化）在弹层里长得完全一样 —— 而这正是 2026-08-11 决策 5/7 的核心分歧（`13-chat-model-picker.png`）。
13. **供应商名在一屏内重复四次。** 弹层有 sticky 组头「ANTHROPIC 官方」，其下每一行又各写一遍「Anthropic 官方」（`model-target-picker/index.tsx` 选项行 + `13-chat-model-picker.png`）。
14. **模型只能一条一条删。** 供应商下动辄十几个模型（发现导入一次可以进四个以上），清理时只能逐行点删除、逐次确认。

## Actors and user stories

1. 作为供应商管理者，我希望一眼看到某个供应商的连接、默认模型和被引用情况，并且在动手之前就知道哪个模型删不掉、为什么。
2. 作为供应商管理者，我希望批量勾选模型并一次删掉，同时不会误删默认模型或还在被引用的模型。
3. 作为 Agent 后端配置者，我希望在列表上直接看到每个后端绑到了哪个供应商与模型、是动态跟随还是固定，并能一步进入更换。
4. 作为 Agent 后端配置者，我希望编辑时能看到这套配置最终真的会怎么执行，而不是自己在三个字段之间推演。
5. 作为会话用户，我希望在选择模型前就知道「跟随 Agent 绑定」到底会跑什么，以及我选的是会随默认变化的还是锁死的。
6. 作为使用最小窗口的用户，我希望 860×640 下这些界面仍然不换行、不横向溢出。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | 保留「左栏供应商导航 + 右侧模型工作区」两栏，删掉外层重复卡片，计数并入页头。 | 用户在方案评审中选定两栏去噪方向。拒绝改成单列可展开卡片（多供应商时纵向过长、切换成本高），也拒绝只做视觉降噪（补不上信息缺口）。 |
| 2 | 供应商启用状态与开关合成一个控件，留在工作区 header 的操作区首位。 | 状态与操作是同一件事，分开表达制造了三处重复。拒绝把启用状态做成只读 chip、把「停用」塞进溢出菜单（丢失可直接操作的可见开关）。 |
| 3 | 操作按权重分档：`测试连接` / `发现模型` 常驻，编辑连接、复制 Provider Key、删除收进「更多」菜单。 | 破坏性操作不应与常规操作同权重常亮。拒绝保留删除按钮常亮红色。 |
| 4 | 模型行主信息用 display name，为空时回落显示模型 ID；模型 ID 降为副行；`modelKey` 移入编辑模型弹窗。 | `modelKey` 是跨实体稳定引用，用户日常不需要读它。拒绝在表格里保留 UUID，也拒绝彻底隐藏它（运维排查需要可复制）。 |
| 5 | 模型表新增「引用」列，只显示数量。 | 数量可由已有的 `LLMProviderRefCounts` / `LLMModelRefCounts` 绑定得到。拒绝显示受影响配置的名字清单——没有对应的只读查询，本轮不加后端接口。 |
| 6 | 测试结果只做会话内瞬时反馈，不渲染成持久徽标。 | 后端 `TestLLMProvider` 是即时调用，结果不落库。拒绝沿用上一版 mockup 里的持久「已验证 / 未测试」状态列——那会让界面声称一个后端无法证明的事实。 |
| 7 | 批量删除由前端逐条调用现有单删接口完成，中途失败即停并报告已删/未处理数量。 | 后端只有单条 `DeleteLLMModel`。拒绝假装它是事务，也拒绝为此新增后端批量接口（超出本轮边界）。 |
| 8 | 批量操作中只有默认模型不参与删除，在勾选时即行内标注原因；被引用的模型参与删除，勾选时行内标注引用影响。 | 2026-08-19 修订（原文：默认模型与被引用模型都不参与删除），随 2026-08-11 决策 17 一并放开。默认模型仍把失败前置成可见约束。拒绝先提交再由后端逐条报错。 |
| 9 | Agent 后端列表行直接显示绑定摘要并提供「更换绑定」直达。 | 绑定是这一行最重要的配置。拒绝维持"必须打开弹窗才能看见"。 |
| 10 | 绑定字段更名为「模型绑定」，触发按钮两行：主行是所选目标，副行是当前解析出的生效模型。 | 2026-08-11 spec 已要求展示解析结果。拒绝继续用「LLM 供应商」这个与实际选择内容不符的名字。 |
| 11 | 主绑定、分级路由、自定义模型收进同一个「模型绑定」区块并建立主从：分级路由默认折叠带摘要，自定义模型仅在 CLI 登录态下出现。 | 三者是同一件事的不同层级，不是三个并列字段。拒绝平级堆叠，也拒绝把分级路由拆成独立弹窗（多一跳）。 |

## 供应商管理页

页面由标题、一句说明、供应商计数与唯一的新增入口构成，其下直接是两栏工作台。说明文案只描述用途，不出现内部实现名词。左栏按供应商类型分组列出供应商，每行显示品牌标识、名称、端点与模型数；只有停用的供应商额外带停用标记，启用是常态不再标注。左栏不再重复新增入口。

工作区顶部分两行。身份行显示品牌标识、名称、协议类型，右侧依次是启用开关（含状态文字）、`测试连接`、`发现模型` 与「更多」菜单；编辑连接、复制 Provider Key 与删除供应商在该菜单内。元信息行以等宽小字依次给出端点、掩码 API Key、当前默认模型与被引用情况。当供应商没有合法的启用默认模型时，启用开关禁用并说明必须先指定默认模型。

模型表的列依次为选择框、模型、上下文、最大输出、引用、默认、启用与行操作。模型列主行显示 display name（为空时回落显示模型 ID）与默认标记，副行显示模型 ID。引用列显示该模型被引用的数量，无引用时显示占位符。默认列是单选控件；当前默认模型的启用开关禁用并说明必须先更换默认模型。行操作提供测试、编辑与「更多」（含删除）；被引用模型的删除项禁用并给出原因。

供应商级测试与模型行内测试是同一能力的两个入口，结果以会话内瞬时反馈呈现（成功/失败与耗时），刷新后消失，不作为持久状态存储或展示。

## 模型的批量选择与批量删除

模型表的表头选择框选中当前筛选结果中的全部模型。存在选中项时，模型工具栏原地替换为选择态操作条，显示已选数量与总数，并提供全选、取消选择、批量启用、批量停用与批量删除；选择态不额外占用新的一行。

处于选择态时，每个被选中的模型行内直接标注它能否被删除：默认模型标注为默认模型不可删除，有引用的模型标注引用数量与「删除后失效」，其余标注为可删除。

批量删除的确认界面把选中项分成「将被删除」与「被保护（保持不动）」两组分别列出，被保护项标注原因，主按钮明确写出实际会删除的数量。当选中项全部被保护时主按钮禁用并说明没有可删除的模型。

执行时逐个删除并汇总结果。全部成功时反馈删除数量；中途失败时停止后续删除，并明确报告已删除数量与未处理数量，不留下用户无法察觉的半完成状态。批量启用与批量停用遵循同样的前置约束与结果汇报方式：默认模型不参与停用。

## 模型的发现、添加与编辑

发现并导入按模型族分组呈现远端结果，每项显示模型 ID 与上下文/最大输出，并区分「新」与「已存在 · 跳过」；已存在项保持不可勾选，全选只作用于新模型。界面同时给出远端总数、新增数与已存在数，底部说明本次将导入多少个新模型、以及已存在项的名称、上下文、默认与引用配置保持不变。

拉取失败时给出可理解的失败原因与可执行的下一步（前往编辑连接、重试），上游原始响应默认折叠、按需展开，不作为主文案直接呈现。

手动添加模型接受模型 ID，并在内置目录命中时自动填入上下文窗口与最大输出且允许修改；显示名称可留空，留空即以模型 ID 显示。

编辑模型可修改显示名称、模型 ID、上下文窗口与最大输出。当该模型存在引用时，修改模型 ID 前展示受影响的后端与会话数量，并说明当前回合不受影响、下一轮起使用新 ID。`modelKey` 在此以只读形式呈现并可直接选中复制，说明它是后端、会话与分级路由的稳定引用。

## Agent 后端绑定

后端列表每行在名称与类型之下显示绑定摘要：绑定 Agentre 供应商时显示供应商标识、供应商名、模型 ID 以及该目标是跟随默认还是固定；未绑定时显示走 CLI 自身登录态；目标失效时以警示样式说明失效原因。行上提供「更换绑定」直达选择器；目标失效的行把它提升为主按钮。

编辑器把模型相关配置收进一个「模型绑定」区块。区块首项是选择器触发按钮，两行呈现：主行是所选目标与其模式标记，副行是当前解析出的生效模型，并说明该模式的后果（跟随默认会在下一轮随默认变化，固定则不受默认变化影响）。选择「CLI 自身登录态」时副行说明模型由该 CLI 自身的登录账号决定，同时区块内出现自定义模型输入，并说明它只在这一档下生效、绑定 Agentre 供应商后保留但被忽略。

Claude 的分级路由收在同一区块内，默认折叠并在标题行给出摘要（三档各自继承主绑定或固定到了哪个模型）。展开后每档使用同一个选择器，顶部特殊项是继承主绑定，副行显示继承后的实际生效模型。

编辑器内提供「生效配置摘要」，随编辑实时反映运行位置、模型来源、生效模型及其模式、分级路由三档结论、引用数量，以及当前配置是否可保存。校验不通过时摘要给出不能保存的原因。

没有任何与当前后端类型兼容的供应商时，界面给出一句说明与前往供应商设置的入口；除此之外不常驻展示兼容性术语。

## 共用的模型目标选择器

会话、Agent 后端与 Claude 分级路由共用同一个选择器，差异只在顶部特殊项：会话是「跟随 Agent 绑定」，后端是「CLI 自身登录态」，分级路由是「继承主绑定」。顶部特殊项以副行写出它会解析成什么——供应商与模型，或说明由 CLI 登录态决定。会话场景在新建会话时，副行只承诺跟随该 Agent 绑定的供应商，不写出具体模型。

特殊项之下是最近使用，呈现为单行横向 chip，每项可单独移除，超出宽度时横向滚动，不换行。其下按供应商分组，组头为 sticky 并承载品牌标识与供应商名。

每个供应商组内先呈现「跟随该供应商默认」：使用强调底色与动态图标，副行写出当前解析到的默认模型（「当前 / Currently」+ 等宽模型标识，标识永不截断）。「默认变化时会自动跟随」这句后果说明**不在界面上出现**，由动态图标与「固定到具体模型」分段标题隐式承担（见决策 26）。其后是「固定到具体模型」分段小标题，再列出该供应商下的具体模型；模型行显示 display name 与模型 ID，右侧显示上下文窗口与最大输出，不再重复供应商名，也不带品牌标识——供应商身份由 sticky 组头承载。选中的模型行用中性强调，强调底色不与「跟随该供应商默认」共用（见决策 27）。

不可选的项一律禁用并在行内给出原因：模型已停用、目标设备上没有该供应商、目标设备不支持固定模型。远端场景在顶部说明以目标设备的配置为准，并对本机独有的供应商提供显式同步入口，同步入口说明会把 API Key 复制到该设备且需要用户确认。

当前目标失效时，选择器顶部给出警示：写出失效的供应商与模型、说明下一轮会被阻止、且不会自动改用其它模型，要求重新选择；失效的原目标以禁用项保留在列表中，不被清除。

会话场景的弹层底部常驻说明切换自下一轮生效、正在进行的回合不受影响。

Composer 上的 pill 呈现四种状态：跟随 Agent 绑定时显示跟随标识与解析出的模型；跟随供应商默认时显示供应商标识、模型与动态图标；固定模型时显示供应商标识与模型、无动态图标；目标失效时使用警示样式并标注已失效。切换成功后写入 transcript 的旁白沿用现有 `switch` notice，其措辞与 pill 使用同一套说法（固定 / 跟随默认 / 跟随 Agent）。

## 状态、可访问性与窗口

供应商工作区与选择器覆盖加载中、空、错误、禁用、失效、远端离线与旧协议状态。禁用原因通过行内文字或 tooltip 表达，不只依赖颜色。选择框、开关、单选与选择器均可键盘操作，保留可见焦点环；选择器支持搜索聚焦、方向键、Enter 与 Esc。

所有新增静态文案进入中英文 i18n；供应商名、模型 ID、端点等动态内容不翻译。品牌标识一律由现有 logo 组件渲染：供应商位按协议类型、名称与端点判定，模型位先按 model id 判定、认不出再回落供应商品牌，认不出品牌时使用文字回落。

在 860×640 最小窗口下，供应商两栏结构保持可用：左栏收窄，模型表隐藏上下文与最大输出两列并让位瞬时测试反馈，其余列保留；不出现横向溢出与主信息换行。不引入移动端断点。

批准的本地 mockup 作为设计证据（本地 `.dev-kit` 产物，不进入正式提交）：`.dev-kit/artifacts/2026-08-13-provider-binding-ux/mockups/index.html`。

- 新增任何后端服务方法、DTO 字段或 Wails 绑定，包括受影响配置的名字清单查询、事务化的批量删除接口、以及给 `ChatAgentItem` 补 model key。

- OpenClaw 的模型语义与界面。
- Agent 后端类型选择器（两列单选卡片）的形态。
- 供应商页顶部再加一层类型 / 状态筛选。
