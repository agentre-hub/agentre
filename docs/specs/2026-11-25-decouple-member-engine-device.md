# 组织成员与执行位置解耦：引擎配置、设备情况、派发与凭据租用

> Status: Approved
> Owner: desktop app、agentred、agentre-server 维护者（同步契约 `pkg/syncwire` 与协议 `pkg/wire` 成对交付）
> Last updated: 2026-11-28（修订：设备情况与租约走 syncwire HTTP/JSON）

**Objective:** 组织成员只描述「是谁、用什么引擎干活」，不再写死「在哪台机器上跑」；新会话在哪台设备上跑，由建会话时根据项目、设备自己上报的情况和用户偏好算出来，并钉在会话上；LLM 供应商的 API key 不再常驻在 agentred 上。

**Hard invariant:**

- 真实 API key 不出现在任何 agent 子进程的环境变量、参数或配置文件里，不出现在任何 RPC 响应、日志、agrctl 输出里；本轮之后也不再写进 agentred 的磁盘。
- 迁移前已经钉在某台设备上的会话，迁移后仍在同一台设备上用同样的模型、力度、权限继续对话（含 `--resume` 续接）。
- 不创建、不修改用户全局的 CLI 配置（`~/.claude`、`~/.codex`、`~/.gemini` 等），与现状一致。

## Problem

证据标注：【已验证】= 读过完整路径；【推断】= 机制确认、后果未实测。

1. **成员和机器绑死在一起。** Agent 持有一个有序的「执行目标」列表，每一项指向一条后端（`internal/model/entity/agent_entity/exec_target.go:17-27`），而一条后端本身带着 `device_fingerprint`（`internal/model/entity/agent_backend_entity/agent_backend.go:62-135`），即一条后端 = 引擎配置 × 一台机器。新配对一台 agentred 要给每个成员加一档；删掉一台机器，相关成员变成「这个 Agent 还不能对话」。【已验证】
2. **同一份引擎配置按机器复制成多份，会漂移。** 「Claude Code · Anthropic · claude-opus-4.5」在本机和 build-server 上是两条独立的后端，改模型、力度、权限要逐条改；技能授权也按档各存一份（`exec_target.go:13-16` 的 `skills_json`），派到哪台机器，成员的能力就跟着变。【已验证】
3. **「在哪跑」的偏好用补丁表达。** 本端顺序覆盖表 `agent_exec_target_overrides` 只存在于一台桌面端（`exec_target_override.go:15-23`），无覆盖时再把本机那几档提到最前（`exec_target_svc/order.go:75-105`）；控制台另有一份账号级 `sort_order`（`agentre-server/internal/service/workspace_svc/workspace.go:138-149`）。同一个成员在桌面端和控制台上的派发顺序可以不同。【已验证】
4. **派到另一台桌面端时，用户选的那一档会丢。** 发起方只带 agent、项目、模型类覆盖（`frontend/src/hooks/use-chat-actions.ts:194-210`），接收方 `RunPeerSession` 不带执行目标调 `send`（`internal/service/chat_svc/peer_session_controls.go:156-170`），按它自己的顺序重新挑后端。【已验证】
5. **API key 在三处明文常驻。** 桌面端 SQLite `llm_providers.api_key`（`llm_provider_entity/llm_provider.go:57`）；账号同步把它带上 server（`pkg/syncwire/guard.go:92` 只放行 `llm_provider`），server 的 `sync_objects.payload` 是普通 JSON 列，`internal/` 下没有任何加密代码（`agentre-server/migrations/202609120101_initial_schema.go:316`）；agentred 连上中继或收到账号信号时拉 `/v1/engine/snapshot`，**全部**供应商连同 key 写进 `state.json`（`agentre-server/internal/service/engine_svc/engine.go:533`，`internal/daemon/enginesnapshot/manager.go:187-209`），桌面「同步到设备」也写同一处（`internal/service/remote_device_svc/sync_provider.go:58`）。后果：任何登录过账号的 agentred 磁盘上都有账号全部 key；设备被移除后 key 仍留在它的盘上；server 被读库即全部泄露。【已验证】
6. **Pi 拿到真实 key。** 其它 CLI 后端只拿会话网关 token、真实 key 由网关在转发时换上（`internal/pkg/httpgateway/llmforward.go:123,213`），Pi 却把真实 key 放进进程环境变量 `AGENTRE_PI_API_KEY_*`（`internal/pkg/agentruntime/piagentprovider.go:181-189`），子进程（subagent）同样继承。【已验证】
7. **设备上报的情况不够、也不持久。** 桌面端每 5 秒 ping 已配对的 agentred，`health.ping` 带回供应商摘要与能力，只缓存在内存（`internal/service/remote_device_svc/svc.go:55-58`）；server 的设备表只有类型、平台、版本、在线（`agentre-server/internal/api/device/device.go:116-124`）；CLI 是否安装只能按需探测（`internal/daemon/handlers/cli.go:41-64`），没有任何接口报告 CLI 原生登录态。控制台和其它桌面端因此只能靠「这台机器上有没有建过那条后端」来猜它能不能跑。【已验证】
8. **规则没有成文。** 定义执行目标规则（R13–R15）的原始 spec 已删除（`docs/specs/2026-08-07-workspace-sync.md`、`2026-08-14-exec-target-order-ux.md` 不存在），规则只剩代码注释。【已验证】

## Actors and user stories

1. 作为**组织的搭建者**，我想给成员配人设、工具、技能和一份引擎配置（或直接跟随部门），不用关心有几台机器，这样新增、删除机器时不用回头改成员。
2. 作为**多设备用户**，我想新会话自动落在合适的设备上：项目在哪台机器上有代码、哪台装了需要的 CLI、哪台在线，并且这台电脑优先，这样我平时不用选机器。
3. 作为**多设备用户**，我想偶尔手动指定一次在哪台设备上跑，只影响这一次；想长期固定时，把某台设备设为项目默认设备。
4. 作为**管理引擎的人**，我想改一份引擎配置（换模型、调力度）就让所有引用它的成员同时生效，每台设备上都一样。
5. 作为**设备的所有者**，我想看到每台设备上装了哪些 CLI、登没登录、能连哪些端点、有哪些项目，并且只在这里改「只对这台设备生效」的设置。
6. 作为**账号所有者**，我想 agentred 不在磁盘上保存我的 API key，设备被移除后立即拿不到 key，server 被读库也拿不到明文。
7. 作为**用 agrctl 的外部工具**，我想用 `--device` 直接指定设备、用 `--engine` 临时换一份引擎配置，不必知道成员背后有哪些后端。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | 数据分三类：**意图**（用户配置，账号级同步）、**事实**（设备自己上报，只读）、**决策**（建会话时算出，钉在会话上）。意图里不放事实和决策 | 用户认可（2026-11-25）。Problem 1–3 都是三类混在一起造成的。Rejected: 在现有执行目标上加「任意设备」开关——设备事实仍然无处可放 |
| 2 | 后端改为**引擎配置**：去掉设备字段，类型创建后不可改（与现状一致），一份可被任意多个成员、部门引用 | 用户认可。Rejected: 保留后端 × 设备、只在界面上合并显示——漂移问题（Problem 2）还在 |
| 3 | 成员引用**一份**引擎配置；不引用时跟随所在部门的「成员默认引擎」，沿上级部门向上找，最后是账号默认引擎配置 | 用户认可（选项「一对一 + 部门继承」）。Rejected: 成员持有有序回退列表——同一成员在不同设备上用不同模型，正是要消除的漂移 |
| 4 | 成员可选「在哪跑」约束：任意设备（默认）/ 带标签 / 指定设备。约束只做过滤，不做排序 | 用户认可。Rejected: 成员上保留设备顺序——顺序属于用户和项目，不属于成员 |
| 5 | 设备顺序账号级一份；每台桌面端另有一个本地开关「在这台电脑上，本机始终排第一」，默认开 | 用户认可。Rejected: 每台桌面端各存一份任意顺序——Problem 3 |
| 6 | 派发优先级：本次会话手动指定 › 项目默认设备 › 设备顺序 | 用户认可 |
| 7 | 派发判定是共享 Go 模块里的一个纯函数，桌面端、server（控制台、agrctl 账号模式）调用同一份，并对每台设备给出结果与原因 | Problem 3、4。界面上「现在能跑在」「各设备上」「无处可跑」都显示它的输出。Rejected: 两端各写一份——已经出现过顺序不一致 |
| 8 | 设备事实由设备自己上报给 server 并持久化（server 新建按设备存的表）；不走 `sync_objects`；未登录账号时桌面端直接向已配对的 agentred 读取 | Problem 7。事实不是用户编辑的数据，不该参与冲突合并。Rejected: 继续按需探测——控制台和其它桌面端拿不到 |
| 9 | 技能授权挂在成员上，按引擎配置的运行时类型校验；某台设备没装授权的技能包时照常派过去、不带那个包并提示，不阻塞 | 用户认可。技能包 ID 按运行时区分（Claude 插件与 Codex 对不上），与机器无关。Rejected: 缺包即判该设备不可用——会让「装没装插件」决定会话落在哪 |
| 10 | 会话建立时钉住**设备**与**引擎配置**；之后改引擎配置的模型、力度等，按现有「跟随」规则影响该会话后续轮次；会话不能换设备 | CLI 续接状态在那台设备上。引擎配置类型不可改，跟随不会换运行时。Rejected: 建会话时拷一份快照——与现有「跟随 Agent 绑定」的模型胶囊语义相反 |
| 11 | 派到另一台桌面端时带上设备与引擎配置，接收方照此执行；它算出来跑不了时报原因，不再自己重挑 | Problem 4 |
| 12 | 外部服务型引擎（Hermes、OpenClaw）的地址属于引擎配置；某台设备「有没有这个端点的凭据、能不能连上」是那台设备的事实。builtin 与 OpenClaw 只能在桌面端运行，是运行时自身的限制 | 设备本地凭据规则沿用 `2026-09-17-device-local-backend-credentials.md`，凭据槽位从后端 `sync_id` 改为引擎配置 `sync_id`。agentred 拒绝 builtin / OpenClaw 的现状（`internal/daemon/handlers/runtime.go:486-491`）不变 |
| 13 | 按设备覆盖 CLI 路径从「后端 × 设备」改为「运行时类型 × 设备」 | 一台设备上同一种 CLI 只有一个可执行文件；覆盖属于设备设置 |
| 14 | 供应商可选「谁能连到」：任何设备（默认）/ 只有这些设备；派发和供应商测试都遵守它 | 本地端点（localhost 的 Ollama、内网中转）只在特定机器上可达。Rejected: 让用户在每台设备上标「可用供应商」——维护量与 Problem 1 同形 |
| 15 | agrctl：`--device` 直接按设备指定；去掉 `--backend`，新增 `--engine <引擎配置>`（仅新会话、仅本会话）；`get device` 改为列出设备上报的运行时 | 用户决定（2026-11-28）。改掉 `2026-11-25-agrctl-account-peer.md` 决策 9 里「只在该 agent 的执行后端中选」——那里依附的执行目标概念本轮取消。Rejected: 保留 `--backend` 映射成引擎配置——名字与新概念不符 |
| 16 | agentred 不再常驻 API key，改为**按需租用**：用设备凭据向 server 申请某个供应商的 key，只放内存，到期前续租；直连或未登录账号时由派活的桌面端随请求附带一份租约 | 用户认可。Problem 5。Rejected: 保持常驻——设备移除后 key 仍在；Rejected: key 永不出 server、LLM 请求经 server 代理——延迟、带宽、server 看到全部提示词 |
| 17 | 桌面端继续常驻 key（离线也要能用），但从 SQLite 明文挪进系统钥匙串 | 用户认可。用户自己的电脑，离线使用是基本需求 |
| 18 | server 对供应商 key 做应用层加密存储 | Problem 5。与 16 独立，但同一轮交付 |
| 19 | Pi 改走网关：拿会话网关 token 与网关地址，不再拿真实 key | Problem 6；与其它 CLI 后端一致 |
| 20 | 不做旧格式兼容：桌面端、agentred、agrctl、server 一起升级；跨代对端在握手期被协议版本拒绝 | 沿用 `2026-09-17-backend-config-sync.md` 决策 6 与现有协议窗口规则；项目未正式发布 |

## 概念与归属

| 概念 | 回答的问题 | 内容 | 谁改、存在哪 |
|---|---|---|---|
| 成员（Agent） | 是谁、能做什么 | 名字、头像、描述、部门、汇报关系、提示词、工具、记忆开关、技能授权、引用的引擎配置（可空＝跟随部门）、「在哪跑」约束 | 用户；账号级同步 |
| 部门 | 组织结构 | 现有字段 + 成员默认引擎（可空＝跟随上级） | 用户；账号级同步 |
| 引擎配置 | 用什么、怎么干活 | 名称、运行时类型、模型来源（CLI 原生登录 / 某供应商的默认模型 / 某供应商的固定模型）、Claude 模型分级路由、思考力度、权限模式或沙箱与审批、环境变量、类型专属设置（ACP 命令与参数、Hermes 地址、OpenClaw 网关地址与 agent） | 用户；账号级同步。其中一份标为「账号默认」 |
| LLM 供应商 | 能调谁家的 API | 名称、协议类型、端点、key、模型目录、「谁能连到」 | 用户；元数据账号级同步，key 见「凭据」 |
| 项目 | 在哪份代码上干活 | 现有字段 + 默认设备（可空） | 用户；账号级同步 |
| 设备 | 能在哪干 | 名称、标签、在账号设备顺序中的位置、仅此设备的覆盖（各运行时的 CLI 路径） | 用户；账号级（覆盖按设备） |
| 设备情况 | 这台设备现在能干什么 | 见「设备情况上报」 | 设备上报；只读 |
| 会话执行位置 | 这次在哪干 | 设备、引擎配置，以及会话级的模型 / 力度 / 权限覆盖（现有） | 建会话时决定；钉在会话上 |

参与派发的设备只有**桌面端**与 **agentred**；`cli`、`web`、`mobile` 类型的设备不出现在任何设备顺序、设备列表或选择器里（与 `2026-11-25-agrctl-account-peer.md` 「`cli` 设备不出现在任何选择执行设备的列表里」一致）。

未登录账号时，以上「账号级」数据只存在这台桌面端上，规则不变；能派发的设备是本机与已配对的 agentred。

## 引擎配置

- 设置导航的「引擎」组依次为：LLM 供应商、引擎配置、设备。原「Agent 后端」页改名「引擎配置」；原「集成 › 远端」页挪到这里改名「设备」。
- 列表行显示：运行时图标、名称、运行时类型、模型来源（供应商 › 模型，或「走 CLI 自身登录态」）、引用它的成员数。不再显示任何设备名。「账号默认」那一份在行上带标记，可在行菜单里改设。
- 编辑框沿用现有后端编辑框的字段与校验（类型、名称、模型绑定、模型分级路由、权限模式、思考力度、环境变量、类型专属设置），**去掉**「运行设备」与「CLI 路径」两个字段；末尾增加只读的「各设备上」一节：每台参与派发的设备一行，显示该运行时在那台设备上的版本，以及「可运行（经 <供应商> / 原生登录）」或不可运行的原因（同「派发规则」的原因措辞）。点一行打开设置 › 设备并展开那台设备。
- 新建时默认名称为运行时名；同名允许存在。
- 删除：被成员或部门直接引用时，删除确认列出受影响的成员与部门，它们改为跟随上一级；账号默认那一份不能删，要先把别的设为账号默认。已钉在被删配置上的会话按它最后的设置继续对话；新会话不能再选它。
- 「测试连接」在一台能运行它的设备上执行：桌面端优先本机，本机不能运行时用派发规则选出的第一台。

## 成员与部门

### 成员详情「执行」栏

自上而下四块，替代现在的执行目标列表：

1. **引擎**：一张卡，显示引擎配置名、运行时、模型来源与力度；跟随部门时卡上标「跟随 <部门名>」（CEO 等无部门成员标「跟随账号默认」）。点开是选择弹层：第一项「跟随 <部门> · <配置名>」，下面列出全部引擎配置及各自被多少成员引用，最后是「新建引擎配置」（打开设置 › 引擎配置的新建）。
2. **技能**：技能授权芯片（继承 / 强制开 / 强制关三态，沿用现有规则）加「管理技能」。技能目录按引擎配置的运行时取：从一台能运行它的在线设备读取（本机优先）。授权的包在某台参与派发的设备上没装时，芯片带警示色并写「<设备名> 未装」。运行时不支持技能包时，这一块只显示一行原因。换到另一种运行时的引擎配置时，与新运行时对不上的授权显示为失效并可一键移除。
3. **在哪跑**：三段切换「任意设备 / 带标签 / 指定设备」。带标签时显示标签芯片与「+ 标签」（候选来自设备已有标签），设备须带全部所选标签；指定设备时显示参与派发的设备芯片，可多选。
4. **现在能跑在**：只读列表，按派发顺序列出每台参与派发的设备、派发规则对这名成员（不带项目）的判定结果：能跑的显示模型来源，第一台能跑的带「默认」标记与左侧色条；不能跑的变灰并写原因。点一行打开设置 › 设备并展开那台设备。标题行右侧有「调整顺序」，打开设置 › 设备。

保存规则沿用成员页的自动保存。成员不再因「没有执行目标」而无法保存或无法对话；只要它（或继承到的）引擎配置存在即可保存。

### 部门

部门详情在「归属 / 负责人」下增加「成员默认引擎」：同一张引擎卡与选择弹层，第一项为「跟随上级部门」（顶层部门为「跟随账号默认」）。

### 组织索引

成员行尾显示它生效的引擎配置名（跟随时同样显示名字）。

## 设备与设备情况上报

### 设备页

- 列出账号下参与派发的全部设备：这台电脑、其它桌面端、agentred（未登录账号时：这台电脑与已配对的 agentred）。列表顺序即账号设备顺序，可拖动排序；「在这台电脑上，本机始终排第一」开关在列表上方，开着时本机行固定在第一位、不可拖动。
- 每行显示：在线状态、设备类型图标、名称、标签、类型与版本、系统、装有的运行时摘要；离线时写「离线 · 上次在线 <时间>」。行菜单保留现有设备操作（改名、删除、升级、端口转发、TLS 信任、登录等）。
- 展开一行显示该设备上报的情况：运行时（每种一行：版本与路径，或「没找到」；原生登录态「已登录 · <方式>」/「未登录」/「未知」）、可达端点与凭据状态、项目路径、技能包，以及最后上报时间与「刷新」。
- 可编辑的只有：标签；仅此设备的覆盖（各运行时的 CLI 路径，空＝自动探测）；项目路径（与项目设置里同一份数据）。
- 新配对或新登录的设备追加到设备顺序末尾。

### 上报的内容

每台桌面端与 agentred 报告自己的：

- 在线；桌面端另报 Agentre 应用是否在运行（现状已有区分）。
- 每种已知运行时（Claude Code、Codex、Pi、Antigravity）：是否找到可执行文件、版本、路径、版本是否低于下限；Claude Code 与 Codex 的原生登录态（已登录 / 未登录 / 无法判断时为「未知」）。
- 账号下每份 ACP 类引擎配置的命令在这台设备上能否解析。
- 账号下每份 Hermes / OpenClaw 引擎配置：这台设备上是否存有凭据、上次连接是否成功。
- 已装的技能包（按运行时）。
- 这台设备的本机项目路径（现状桌面端每 30 秒上报，沿用）。

上报时机：设备连上账号中继时报一次全量；本机探测结果变化时报增量；用户在设备页点「刷新」时立即重探并上报。server 持久化最后一次上报及上报时间；设备离线后界面仍显示最后一次上报并标出时间。上报内容不含任何凭据、token 或环境变量值。

## 派发规则

输入：成员（得出生效引擎配置；本次会话手动换了引擎配置时用那一份）、项目（可空）、成员约束、账号设备顺序与本机优先开关、项目默认设备、本次手动指定的设备。

对每台参与派发的设备依次检查，第一条不满足的作为原因：

| 检查 | 原因措辞 |
|---|---|
| 设备在线 | 离线 · <上次在线时间> |
| 桌面端的 Agentre 在运行 | 那台电脑上的 Agentre 没开 |
| 本机配对了这台 agentred（从桌面端派发时） | 这台电脑未配对它 |
| 满足成员约束 | 不带标签 <标签> / 不在指定设备里 |
| 这类设备支持该运行时 | <运行时> 只能在桌面端运行 |
| 装了该运行时且版本够 | 没装 <运行时> / <运行时> 版本过低 |
| 模型来源可用：原生登录时已登录（「未知」视为可用）；用供应商时这台设备在供应商的「谁能连到」范围内 | <运行时> 未登录 / <供应商> 连不到这台设备 |
| Hermes / OpenClaw：这台设备存有该端点的凭据 | 这台设备没有 <配置名> 的凭据 |
| 绑定了项目时，这台设备上有该项目的路径 | 没有 <项目> 的路径 |

排序：本次手动指定的设备 › 项目默认设备 › 账号设备顺序（本机优先开关开着时本机提到最前）。结果是排序后第一台全部通过的设备；同时返回每台设备的结果与原因供界面显示。技能包是否装齐不参与判定（决策 9）。

## 会话

- **新会话空态**：「将在 [设备名] 上运行」，设备芯片可点。是项目默认设备时芯片用项目图标。弹层标题「在哪台设备上跑」、右侧「只影响这一次」，按派发顺序列出每台设备，能跑的显示项目路径（无项目时显示模型来源），不能跑的变灰、写原因、不可选；绑定了项目时弹层底部为「<项目> 总在这台跑？ 设为项目默认设备」。手动选的设备之后变得不可用时，回落到自动结果。
- **换引擎配置**：新会话的模型胶囊弹层顶部增加「引擎配置」一节，默认是成员生效的那份，可为本会话换一份；第一轮发出后锁定。
- **无处可跑**：所有设备都不通过时，空态显示「「<成员名>」现在没有能跑的设备」与逐设备原因；能就地修复的原因带按钮（「添加路径」打开项目设置并聚焦该设备；「去登录」「安装」打开设置 › 设备并展开那台设备）。另一份引擎配置能跑时，显示「这次改用「<配置名>」」，点击只改本会话。发送按钮禁用。
- **钉住**：第一轮发出时，会话记录设备与引擎配置，此后不再改变。设备离线时沿用现有的离线横幅；引擎配置被删按「引擎配置 › 删除」处理。
- **派到另一台桌面端**：随请求带上设备、引擎配置与会话级覆盖；接收方按派发规则复核这台设备（它自己），通过就执行，不通过就把原因返回给发起方显示，不重挑。

## 项目

项目设置的「机器与路径」每一行增加「设为默认」；默认那台显示「默认」标记，再点一次取消。默认设备只能是有路径的设备；移除默认设备的路径时一并清除默认设置。

## 看板任务

任务上的「执行后端」改为可选的「引擎配置」与可选的「设备」两项：从任务开会话时，分别作为本会话的引擎配置与手动指定的设备，规则同新会话。任务卡上的执行目标胶囊改为设备胶囊。

## 控制台（agentre-server web）

控制台与桌面端共用同一套共享组件与派发函数：组织页的「执行」栏与部门「成员默认引擎」、设置里的引擎配置与设备页（控制台没有「这台电脑」，也没有本机优先开关，设备顺序即账号顺序）、新会话设备芯片与无处可跑。控制台派发使用 server 侧的派发函数与 server 持久化的设备情况；控制台能派发的设备范围不变（agentred，以及按现有规则可承载的桌面端）。

## agrctl

- `agrctl send --agent <a> [--device <设备>] [--engine <引擎配置>] [--project <p>] …`：
  - `--device`：名字或指纹，`本机` 指当前桌面端（桌面模式）。设备不存在或不是可派发设备时用法错误，退出码 2，并列出可派发设备；设备存在但派发规则不通过时报该设备的原因，退出码 1。
  - `--engine`：名字或 id；只用于新会话，与 `--session` 同用是用法错误。
  - 两者都不给时按派发规则选设备、用成员生效的引擎配置，与控制台相同。
  - 去掉 `--backend`。
  - `--model` / `--cli-model` / `--effort` / `--permission-mode` 覆盖规则不变，按最终的引擎配置校验。
- 资源命令里的 `backend` 改为 `engine`（list / get / create / update / delete engine）；`get device` 列出这台设备上报的运行时、端点与项目路径，不再列「绑定在这台设备上的后端」。
- 无论桌面模式还是账号模式，agrctl 输出仍不含任何 key 或掩码（沿用 `2026-11-25-agrctl-account-peer.md`）。

## 凭据

### 桌面端

供应商 key 存在系统钥匙串里，SQLite 不再保存明文；升级后首次启动把已有明文迁入钥匙串并清空该列。钥匙串不可用时，保存供应商报错「无法写入系统钥匙串」，不退回明文存储。账号同步照旧把 key 交给账号下的**桌面端**设备。

### server

供应商 key 以应用层加密后存储，加密密钥来自 server 配置，不进数据库；已有明文在升级迁移中原地加密。任何接口都不向 agentred、`cli`、`web` 设备或个人 token 返回 key 明文，唯一的出口是下面的租约（发给 agentred）与账号同步（发给桌面端）。

### agentred：按需租用

- `/v1/engine/snapshot` 只下发供应商元数据（名称、类型、端点、模型目录、「谁能连到」），不含 key。agentred 不再把任何供应商 key 写入磁盘；升级后首次启动清除 `state.json` 里已有的 key。
- agentred 需要某个供应商的 key 时（转发一轮对话的请求、执行供应商测试或模型发现），用自己的设备凭据向 server 申请该供应商的租约。server 只在以下条件同时满足时发放：设备类型为 agentred、未被移除、属于该账号；这台设备在该供应商的「谁能连到」范围内。租约包含 key 与到期时间（30 分钟）。
- 租约只在内存里；仍在使用时于剩余三分之一寿命时续租；进程重启后重新申请。设备被移除、供应商被删除或改了 key 时，server 拒绝续租或给出新值，并经账号中继通知 agentred 立即丢弃已缓存的 key。
- 桌面端直连 agentred（局域网直连、未登录账号的配对）派发时，桌面端随这一轮附带一份同样形状的租约（同样只在内存）。
- 拿不到有效租约时，这一轮以「凭据租约过期，账号服务器连不上」失败；供应商测试 / 模型发现报同样原因。
- 「同步到设备」（把供应商连 key 推给某台 agentred）入口取消。
- 在 agentred 上用 `agentred llm add` 本地添加的供应商仍存于那台设备（用户在那台机器上的明确操作），不受租约约束。

### Pi

Pi 与其它 CLI 后端一样，只拿会话网关 token 与网关地址；真实 key 只在网关里（桌面端或 agentred 的网关）。

## 同步契约与协议

同步契约（`pkg/syncwire`）：

- `agent_backend` → `engine_profile`：去掉设备指纹；`config` 规则沿用 `2026-09-17-backend-config-sync.md`。
- 删除 `agent_exec_target`。
- `agent_backend_cli` → 按（运行时类型，设备指纹）存的 CLI 路径覆盖。
- `agent` 增加引擎配置引用、「在哪跑」约束、技能授权（从执行目标挪来）。
- `department` 增加成员默认引擎；`project` 增加默认设备。
- `llm_provider` 增加「谁能连到」。
- 新增设备偏好（按设备指纹：标签、在账号设备顺序中的位置）。
- 引擎配置里「账号默认」的标记。
- 设备情况上报与租约申请、续租的 HTTP/JSON 类型（设备 ↔ server）。

协议（`pkg/wire`）：

- 开一轮的请求带引擎配置（而不是后端）。
- 派到桌面端的请求带设备与引擎配置。
- 直连时随开一轮的请求附带的租约。
- ctl 消息里 `backend` 改为 `engine`，`send` 增加 `engine`、去掉 `backend`。

租约吊销通知经账号中继的账号通道下发。

协议版本升一档，`MinSupported == Protocol`。桌面端、agentred、agrctl、server 同一批升级；跨代对端在握手期被拒，提示升级较旧的一端（沿用现有措辞规则）。

## 迁移

桌面端（追加在 `migrationList()` 末尾的新迁移）与 server（对 `sync_objects` 的同规则转换）按同一套规则转换，保证账号下各端得到同样的 `sync_id`：

1. **后端 → 引擎配置**：把除设备与 CLI 路径外配置完全相同的后端归为一组，合并成一份引擎配置，沿用组里 `sync_id` 字典序最小的那条后端的 `sync_id` 与名称。
2. **成员**：
   - 引用其执行目标第一档所在组的引擎配置。
   - 执行目标覆盖了该组的全部设备时，约束为「任意设备」；只覆盖一部分时为「指定设备」那几台。
   - 技能授权取第一档的。
   - 没有执行目标的成员跟随部门。
3. **部门**：成员默认引擎为空（跟随上级）。账号默认引擎配置取 CEO 助手引用的那份；CEO 没有执行目标时取引用最多的一份。
4. **设备顺序**：本机第一，其余设备按配对时间排序。本端顺序覆盖表与控制台的执行目标 `sort_order` 丢弃。
5. **CLI 路径覆盖**：按（运行时类型，设备）取各组里第一条非空的覆盖。
6. **会话**：已钉的执行后端换成它所在组的引擎配置；钉住的设备不变。
7. **看板任务**：执行后端引用换成引擎配置引用。
8. **设备本地凭据**：Hermes / OpenClaw 凭据槽位从后端 `sync_id` 换到引擎配置 `sync_id`。
9. **key 的存放**：桌面端明文 key 迁入钥匙串；server 明文 key 原地加密；agentred 清除 `state.json` 里的 key。

server 侧 DDL（设备情况表）须兼容 MySQL 8.4（生产）与 9.7（dev）。

## Out of scope

- 成员持有多份引擎配置、按设备回退。
- 会话在设备之间迁移。
- key 永不出 server、LLM 请求经 server 代理。
- Antigravity 的 Google 账号登录（`2026-11-25-antigravity-backend.md` 决策 8 另开）。
- Hermes / OpenClaw 凭据之外的设备本地 secret 机制变化。
- 设备情况的历史与趋势，只保留最后一次上报。
