# server 持有会话：账号里保存的对话在机器离线时照样读得到

<!-- File: docs/specs/2026-08-18-server-session-mirror.md -->

> Status: **Approved**（2026-08-18，用户裁决「可以，继续」；测试接缝表同批确认）
> **同日修订**：补决策 16（执行端一视同仁，桌面端与 agentred 都镜像、删除都生效，用户裁决
> 「两种端一视同仁，都删」）、决策 17（镜像身份用发起端指纹）与决策 18（总览页一并改读镜像）。
> Owner: web 控制台 / 会话（`agentre-server` + `agentre` 的 agentred）
> Last updated: 2026-08-18

**Objective:** 让账号里保存的对话（自己在 web 上发起的，以及从某台机器上保存过来的）连同标题、状态与
完整转录一起住在 agentre-server 上，执行机离线、关机、甚至被撤销之后仍然读得到。

**Hard invariant:** R19 不放宽——项目在某台机器上的绝对路径、`agent_backends` 的 CLIPath 与 EnvJSON
**不出现在发往浏览器的任何响应里**。server 这一轮开始**存**会话的 `cwd`（镜像的一部分），但它只用于
服务端判定项目归属，不外发。中继既有的转发行为、GitHub 登录、RFC 8628 设备流不得回归。

## 这份规格推翻了什么

[`2026-08-10-web-session-access.md`](./2026-08-10-web-session-access.md) 的**硬不变量**——「agentre-server
不持有任何会话内容」「本轮不新增任何存放会话、消息或转录的服务端表」——以及它的用户故事 6
（「我不想因为开了网页，就让对话内容被 server 存下来」）与「官方托管下标题**不经过 server 落盘**」
这句承诺，**本规格全部推翻**（用户裁决，2026-08-18）。

推翻的理由是那份规格自己留下的代价：会话只住在发起端与执行端，因此**执行机不在线时账号里就什么都
没有**。今天的 web 控制台在那种情况下只能列出一行灰字。

推翻之后新的边界不是「什么都存」，而是**范围即同意**：见决策 2。

## Problem

1. **机器一离线，账号里那条对话就只剩一行灰字。**（已核实，读码得出）关注名单只存指向
   （`agentre-server/internal/model/entity/follow_entity/follow.go`：设备指纹 + 会话标识 + 关注时间），
   会话本体要逐台机器经中继 `runtime.session.list` 实时解析（`agentre-server/frontend/src/pages/Chat.tsx:514`
   那一支按关注名单逐条去各机器的解析结果里找）。目标机器离线、不可达或尚未回话时，那条会话在索引里
   退化成「暂时看不到」的三种灰行之一（[`2026-08-17-web-session-index.md`](./2026-08-17-web-session-index.md)
   决策 6）——**标题、最后一轮说了什么，一个字都读不到**。
2. **索引的首屏要等中继。**（已核实，读码得出）行是浏览器侧逐台解析出来的，`Chat.tsx` 为每台在线目标
   设备挂一个解析器，连上中继后才 `session.list`。机器多或网络慢时，索引先空后填。
3. **转录只在执行端，而执行端会回收它。**（已核实）agentred 的通知日志有留存窗口：一条会话安静满 30 天，
   它高水位以下的行会被收掉（`agentre/internal/daemon/daemon.go:1990` 的 `defaultJournalRetention`，
   判据由 `TestDaemon_CollectJournal_NeverReclaimsARangeThatCouldStillBeCaughtUp` 钉住）。所以「回到那台
   机器上就能翻到」这件事本身也有期限。
4. **「关注」这个词已经配不上它做的事。**（已核实）`followed_sessions` 存的是指针，所以「关注 / 取消关注」
   说得通。一旦 server 持有内容，移除动作的真实语义是**删除**，而「关注 ↔ 删除」不成对。

## Actors and user stories

1. 作为**在外面用手机看对话的用户**，我希望家里那台机器关着的时候，我照样能读到它上面那些我保存过的
   对话，而不是一行「这台机器当前不在线」。
2. 作为**换过机器的用户**，我希望旧机器退役、设备被撤销之后，那些对话仍然留在我的账号里读得到。
3. 作为**看到一条别人机器上的对话想留下的用户**，我希望有一个明确的「保存」动作把它收进账号，也有一个
   明确的「删除」动作把它从账号和机器上一起清掉。
4. 作为**注重隐私的用户**，我希望没有被我保存过的对话，一个字都不会到 server 上。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | **server 持有会话内容**：账号里保存的对话，其摘要与完整转录镜像在 agentre-server 上。 | 用户裁决（2026-08-18）：「要推翻 server 要记录的，这样机器离线也可以看到之前的会话内容」。这直接推翻 `2026-08-10-web-session-access.md` 的硬不变量与用户故事 6，见「这份规格推翻了什么」。拒绝：维持现状——问题 1 无解，账号在机器离线时什么都不是。 |
| 2 | **镜像的范围 = 账号里保存的对话，一条不多**：从 web 发起的（发起即保存）与用户显式保存的。**范围本身就是隐私开关**，不另做账号级设置。 | 用户裁决（2026-08-18）：「只记录和同步 server 关注或者发起的」「是只有由 server 发起的对话/关注的对话，才存」。这条今天已经有现成的边界：`2026-08-10` R12 明写「关注是一个**显式动作**，`session.attach` 那种『打开就接管』不构成关注——**桌面端上自己发起的会话同样不自动进入名单**」，而从 web 发起的对话派发成功即入名单（`agentre-server/frontend/src/pages/Chat.tsx:873`）。因此「保存的集合」= 今天的 `followed_sessions`，桌面端上自己跑的对话默认一个字都不上行。拒绝：账号级「不要保存对话」开关——用户判定范围已经表达了同意，多一个总开关反而让「我到底存了什么」更难说清。 |
| 3 | **写入路径 = server 作为常驻中继客户端**：像桌面端那样对目标 agentred `attach`，收实时通知，并按 seq 游标 `pull` 补齐断连期间的缺口，把帧重放进服务端存储。 | 用户裁决（2026-08-18）：「执行端主动上行」+「这个路径是会走中继的」。桌面端已经把这条路跑通了：它经账号中继拨号（`agentre/internal/service/server_svc/relay.go` 的 `DialDaemonRelay` → `GET /v1/relay/client`，设备 JWT），会话整条住在本地库，靠「接入期间收实时 + 重启后按游标拉 journal 增量并**用与实时同一套 handler** 重放」保持同步（`agentre/internal/pkg/agentruntime/runtimes/remote/catchup.go` 的 `CatchUpSessions` 三步）。照搬它意味着 **daemon 侧的读取路径一行都不用改**——`session.list` / `session.attach` / `session.pull` 已经全在。拒绝：daemon 新开一条 HTTP 端点直接 POST 给 server——不走中继，与用户裁决相悖，且要新造一套鉴权与重试；拒绝：中继旁路落盘（server 在转发时顺手解析）——`relay_ctr` 今天只有 `ForwardDaemon` / `ForwardClient` 两个动作、一个字节都不解析，让它认识帧语义会把这条干净边界弄脏，而且没人接入时 daemon 根本不发帧，覆盖面反而不全；拒绝：浏览器读到哪回写到哪——只有开着网页才更新，用户没打开过的轮次离线后仍然看不到。 |
| 4 | **存的是原始 journal 帧**（`{seq, method, params}`），不是解析后的转录行。 | 本规格提议（读码得出）。`wire.JournaledNotification` 就是这个形状，浏览器今天也正是按 method 把 params 解成对应帧、盖上 seq、喂进与实时同一套 handler（`agentre-server/frontend/src/lib/relayClient.ts:319` 的 `pullUntilCaughtUp`）。存原始帧因此**不需要第二套解析**，也不会因为渲染层演进而让老数据解不出来。拒绝：存解析后的行——server 要认识每一种工具卡片的语义，且渲染层一变老行就废。 |
| 5 | **「关注 / 取消关注」概念取消**，换成**保存 / 删除**。 | 用户裁决（2026-08-18）：「应该没有取消关注的逻辑，应该就是删除的逻辑」；动作命名同日裁决为「保存」。一旦 server 真的持有内容，「关注」说的是「我留意这条」，而实际发生的是「把整条对话存进我的账号」——词轻于事。「保存 ↔ 删除」成对，且如实说出了发生的事。拒绝：沿用「关注」——与已定的「删除」不成对；拒绝：「收进账号」「添加到账号」——行尾窄按钮上表达不了，且没说出「内容会被存下来」。 |
| 6 | **删除同时清掉 server 与执行端两份**；执行机离线时**立即删 server 那份**，给那台机器记一条待办，机器回来时补删。 | 用户裁决（2026-08-18）：「两边一起删」+「立即删 server，机器回来再补删」。判据是「删了就是删了」这个直觉：本轮的主场景恰恰是机器离线，要求两边都成功才算删等于在最常见的情形下删不掉东西。**已知代价**：机器回来之前那一份还在它本地；待办可能永远执行不了，收口见决策 7。拒绝：两边都成功才算删；拒绝：只删 server 不向执行端传播——与用户裁决相悖。 |
| 7 | **设备被撤销后，该机器上那些已保存的对话留在账号里、读得到、只读**；挂在这台机器上、永远执行不了的删除待办随之清掉。 | 用户裁决（2026-08-18）：「设备被撤销时，应该是保留会话，但是只读」。这正是用户故事 2 —— 旧机器退役之后账号里那些对话不该跟着消失。只读是事实而非策略：没有执行端，发不出消息。待办清理是本规格提议：那台机器已经不归这个账号管，留一条永远执行不了的删除指令没有意义。 |
| 8 | **两端都永久保存**：server 不设保留期，**agentred 的 journal 回收一并去掉**；清理逻辑留给后续。 | 用户裁决（2026-08-18）：「daemon 的删除也去掉，也永久保存，后续可以在 server 加清理逻辑」。与决策 5「只有删除这一个减法」一致：用户删了才少，别的什么都不会让内容悄悄消失。**已知代价**：`agentre/internal/daemon/daemon.go` 的 `collectJournal` 去掉之后 **agentred 本地库无上限增长**，而 agentred 常跑在小机器上；server 侧同样无上限。两者都需要后续单开一轮做清理。拒绝：摘要永久、转录跟 daemon 同口径 30 天回收——老对话点进去是空的，与「离线也读得到之前的内容」这个目标自相矛盾；拒绝：账号配额——多一套计量与回收，且要向用户解释「为什么这条看不到了」。 |
| 9 | **统一会话索引改读镜像**：`/chat` 左栏那四轴索引的行来自 server 的镜像，不再逐台机器经中继实时解析；实时状态仍由中继推。 | 用户裁决（2026-08-18，回答「#1 是哪个索引」后确认）。它解掉问题 2（首屏不再等中继）与问题 1（机器离线照样列得出来）。索引本身四个轴、分组规则、筛选与搜索沿用 [`2026-08-17-web-session-index.md`](./2026-08-17-web-session-index.md)，本规格只换数据源。 |
| 10 | **「暂时看不到」整组删除**（推翻 `2026-08-17-web-session-index.md` 决策 6）。 | 本规格推导（用户已确认 #1）。那一组存在的唯一理由是「名单里有指向、机器上取不到本体」；本体现在在 server 上。机器离线只影响**能不能发新消息**，不影响读——离线因此退化成行上的一个状态，不再是一类看不见的行。 |
| 11 | **机器轴选中一台机器时列的是「那台机器上有、账号里还没有的」**，行尾动作是**保存**（推翻 `2026-08-17-web-session-index.md` 决策 9 的「关注」口径）。 | 用户裁决（2026-08-18）。这条路仍是「发现一条对话并把它收进账号」唯一的去处，只是动作改名、语义变重（从记一个指针变成开始镜像内容）。它要求那台机器**在线**——机器离线时列不出它上面还没保存的对话，这是事实而非降级。 |
| 12 | **项目归属判定整个移到服务端的镜像上**：浏览器不再上送 `(机器指纹, cwd)` 探针。 | 本规格提议（读码得出）。`2026-08-17-web-session-index.md` 决策 4 把判定放在服务端、让浏览器上送 cwd，是因为 server 手里没有会话。镜像之后 server 自己就有 `cwd`，判定不需要任何来自浏览器的输入。**已知后果**：`POST /v1/workspace/session-projects` 这条端点与它的探针协议随之作废。R19 不受影响——cwd 存在 server 上，但不出现在任何发往浏览器的响应里。 |
| 13 | **执行机离线时那条对话只读**：读得到全部历史，发不出新消息，也不排队。 | 用户裁决（2026-08-18）：「不要排队，离线时只读」。发消息要有执行端，没有执行端就没有这一轮——把消息先收在 server 上等于替一台可能再也不回来的机器许下承诺，且需要一整套待发队列、投递顺序、撤回与作废语义。**已知代价**：想到一句话时只能等机器回来。拒绝：离线排队、机器回来自动投递——本轮范围显著变大，且 server 从只读镜像变成持有写入意图的一方。 |
| 14 | **转录渲染不留保真度例外**（推翻 `2026-08-10-web-session-access.md` R8 的那句免责）。 | 用户指出，读码核实：共享包 `@agentre-ai/agentre-ui` 已经导出整套转录渲染（`TranscriptRowView` / `CanonicalToolRouter` / `ToolApprovalCard` / `buildTranscriptRows` 等），`agentre-server/frontend/src/components/session/Transcript.tsx:124` 就在用它。R8 那句「渲染的保真度不在本轮承诺范围内」写于共享包抽离之前，今天已不成立。 |
| 16 | **执行端一视同仁：桌面端与 agentred 都是镜像目标，删除对两者同样生效。** | 用户裁决（2026-08-18）：「两种端一视同仁，都删」。桌面端作为对端**已经注册了同一族补齐方法**（`agentre/internal/peer/inbound.go:90-93`：`session.list` / `attach` / `pull` / `pendingWaiters`），镜像器因此不需要区分两种端；web 的机器列表本来就同时含两者（`agentre-server/frontend/src/pages/Chat.tsx:256`）。**已知代价**：在桌面端上执行的删除清掉的是**用户本机那条对话本体**（`chat_sessions` 与它的消息），而不是一份执行日志——同一个动作在桌面端上的破坏力远大于 agentred，删除确认必须说明这一点。拒绝：只镜像 agentred——用户故事 2 / 3 对桌面端就不成立，而机器轴上桌面端那些行会没有「保存」可用；拒绝：镜像含桌面端但删除不传播到它——同一个动作在两种机器上语义不一致。 |
| 17 | **镜像的身份是「发起端指纹 + 它那边的会话标识」**，不是承载它的那台机器。 | 本规格提议（读码得出）。`wire.SessionSummary.PeerFingerprint` 说的就是发起端，而一条对话在桌面端与 agentred 上各有一份副本是常态（`agentre-server/frontend/src/lib/sessionMerge.ts` 今天正是按这个键合并两份）。用承载机器做身份会让同一条对话在索引里出现两次。副本之间选跟哪一份、以及只读到部分历史时如实标注（R20），由服务端承担——浏览器不再做这件事。 |
| 18 | **总览页的「等你处理」统计一并改读镜像。** | 本规格提议。`agentre-server/frontend/src/pages/Overview.tsx:256-302` 有一份与 `Chat.tsx` 同构的实时解析器；只改索引会在 web 侧留下第二处逐台机器解析，机器离线时总览照样空一块，也与索引规格「web 侧没有第二处会话行实现」的收尾复核相抵触。 |
| 15 | **桌面端仍读它自己那一份**，不从 server 拉镜像。 | 用户确认（2026-08-18）。桌面端作为发起端本来就持有整条会话，让它改读 server 等于给一个已经完整的端换数据源，只增加不一致的机会。镜像这一份只服务 web 控制台。 |

## 镜像的范围与写入路径

**范围**是账号里已保存的对话（决策 2）。一条对话进入这个集合只有两条路：在 web 上发起它，或者在机器轴上
对它按「保存」。桌面端上自己发起的对话不自动进来。

**写入**由 server 侧一个常驻的中继客户端完成（决策 3）。对每台承载着已保存对话且当前在线的机器
（**agentred 与桌面端一视同仁**，决策 16），
它保持一条中继连接，并对那些对话：

- **接入期间**收实时通知，按 seq 落库；
- **连接建立或断而复连时**，按自己存的游标 `pull` 增量，按序重放补齐缺口；
- **已中断的会话不 attach，只 pull**——daemon 对 `LifecycleState = interrupted` 的会话直接回 `ErrNoActiveTurn`
  （R10：那一轮的子进程随上个 daemon 进程消亡了），但它的历史仍然可以拉（`agentre/internal/daemon/handlers/session_catchup.go:206`）。

同一条对话在任何时刻只被镜像一次——多副本部署时由既有的分布式协调承担，见
[`agentre-server/docs/specs/2026-08-07-multi-instance-safety.md`](../../../agentre-server/docs/specs/2026-08-07-multi-instance-safety.md)
定下的约束（定时任务不每副本各跑一遍）。可观察的要求是：不会因为部署了多个副本而出现重复的转录行，
也不会因为某个副本重启而漏掉一段。

**未升级的 agentred**（`session.list` 的应答里没有 `supportsSessionMetadata`）照旧镜像，只是它的会话缺标题与
Agent 同步标识，如实留空、不猜、不填占位名——与今天索引里的退化显示同一条口径。

## 存什么

镜像分两层，都以**发起端指纹 + 它那边的会话标识**为身份（决策 17）：

- **摘要** —— 与 `wire.SessionSummary` 同构：标题、所属 Agent 的同步标识、provider 会话身份、`cwd`、后端类型、
  生命周期状态、是否在等用户、最后活动时刻、最新 seq。索引的四个轴全部由它供给。
- **转录** —— 原始 journal 帧（决策 4）：seq、method、params 原样。浏览器读到之后按 method 解帧并交给与
  实时同一套渲染路径。

`cwd` 存下来但**不外发**（本规格的硬不变量）。它的用途是服务端判定项目归属（决策 12）。

## 索引与详情读到什么

**索引**（`/chat` 左栏，四个轴照旧）的行来自镜像：机器在线与否都列得出来，标题、状态、最后活动时间、
项目与 Agent 归属一应俱全。机器离线只在行上表现为一个**状态**（这台机器不在线），不再让整条行变灰、
不可点（决策 10）。

**详情**读镜像里的转录。机器在线时实时流照旧经中继推过来，两者按 seq 拼在一起——这与浏览器今天的
行为一致，只是补齐的来源从 daemon 换成了 server。

**机器轴选中一台在线机器**时，索引额外列出那台机器上还没保存进账号的对话，行尾是「保存」（决策 11）。
机器离线时列不出这些——它们从来没有进过账号，server 手里没有它们的任何东西。

## 保存与删除

**保存**：对一条尚未保存的对话按下它之后，那条对话进入账号，镜像随即开始；索引里它从「那台机器上的」
变成账号里的一条。

**删除**：删除的是**账号里的这条对话，连同执行端上那一份**（决策 6）。删除需要一次确认，确认文案要说清楚
两边都会被清掉。

- 执行机**在线**：两边一起清掉。执行端是**桌面端**时，被清掉的是那台电脑上这条对话本身，
  确认文案必须说明这一点（决策 16）。
- 执行机**离线**：server 那份当场清掉，对话立即从索引里消失；那台机器记一条待办，它下次上线时执行。
  界面上不留「已删除但还在」这种中间态——从用户视角这条对话已经没了。
- 待办**永远执行不了**（设备被撤销）：随设备撤销一并清掉（决策 7）。

执行端的删除需要 daemon 侧一个**新方法**：今天 wire 上的 `runtime.session.*` 只有 `list` / `pull` /
`pendingWaiters` / `attach`，没有删除（已核实，`agentre/internal/pkg/agentruntime/runtimes/remote/wire/wire.go:48-59`）。

## 机器离线时只读

执行机不在线时，那条对话的**全部历史照常读得到**——这正是本规格的目的。能做的到此为止：

- 发送入口如实**不可用**，并说明在等哪台机器，而不是让用户打完字才发现发不出去。
- **不排队**（决策 13）：消息不会被先收在 server 上等机器回来。
- 已经删除的对话不受影响：删除在离线时照样生效（决策 6）。

设备被撤销之后同理，且是永久的——那条对话此后只读（决策 7）。

## 隐私与承诺的变更

这一轮把 `2026-08-10-web-session-access.md` 的隐私承诺换成一条新的，必须一并更新那份规格与所有对外说明，
不留两套说法：

- **旧**：agentre-server 不持有任何会话内容；官方托管下标题不经过 server 落盘。
- **新**：**你保存进账号的对话，其内容存在 agentre-server 上**；没有保存过的对话（包括桌面端上自己发起的
  全部对话）一个字都不上行。删除一条对话会把 server 上那一份连同执行端那一份一起清掉。

「保存」这个动作因此**同时是同意的表达**。界面上第一次保存时要让用户看得懂这一点，而不是把它藏在一个
图标里。

## 兼容性与已知代价

- **未升级的 agentred** 照旧工作，会话按今天的退化形态镜像与显示。
- **daemon 的 journal 回收去掉之后 agentred 本地库无上限增长**（决策 8），server 侧同样。两者都要后续单开
  一轮做清理，本轮不做。
- **server 从无状态帧转发变成有状态参与者**：`relay_ctr` 今天只有转发两个动作，之后 server 要常驻连接、
  认识帧语义、并在多副本下协调谁来跟。这是本轮最重的一块。
- **`POST /v1/workspace/session-projects` 与浏览器上送 cwd 的探针协议作废**（决策 12）。
- **整条删除会抹掉执行端的 seq 高水位**，而会话标识是各端本地自增、会被复用。桌面端已经踩过同类
  事故（`agentre/internal/daemon/daemon_test.go:1287` 的回归测试与它点名的那次修复：高水位被抹掉后
  日志从 1 重排，而客户端游标停在旧高水位，此后每条实时通知都被当成重复丢弃——不跳号、不报错，
  会话就是再也不出字）。镜像客户端必须实现与桌面端 `dropCursorAboveHighWater` 同一条复位规则。
- **新增一个中继方法会连带改前端**：wire 的方法名表与 TS 代码生成清单都有机械守卫，
  `frontend/packages/agentre-wire/src/codec.gen.ts` 要重新生成。
- **`2026-08-17-web-session-index.md` 的决策 6 与决策 9 被本规格推翻**，那份规格需要相应修订。

## Out of scope

- **server 侧与 agentred 侧的清理 / 保留期 / 配额。** 决策 8 明确留给后续。
- **桌面端改读 server 的镜像。** 决策 15。
- **账号级隐私开关。** 决策 2。
- **把镜像当作跨机器的会话迁移能力**（在另一台机器上接着跑一条对话）。镜像只保证读得到与发得出，不改变
  一条对话钉在哪台机器上执行。
- **机器离线时排队发消息。** 决策 13。
- **组织 / 团队维度的共享。** 镜像属于账号。
