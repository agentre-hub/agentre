# 加下一台设备的引导：随时可达，不只在空态

<!-- File: docs/specs/2026-08-14-add-device-guidance.md -->

> Status: Draft
> Owner: 桌面端「远端设备」页 + web 控制台「设备」页
> Last updated: 2026-08-14
> 实施：跨 `agentre` 与 `agentre-server` 两个仓库，各开一条同名分支 `feat/2026-08-14-add-device-guidance`，**分别提交、不混 commit**（工作区根 AGENTS.md）。本规格文件只存放在 `agentre/docs/specs/`，server 侧文档引用它。两半互不依赖，可并行也可只做一半。

**Objective:** 让「怎么把下一台机器接进来」在桌面端和 web 控制台都是一条随时可达、且第一次与第 N 次完全一样的路径；用户不必记住上一次是在哪儿看到那些命令的。

**Hard invariant:**

1. 不改任何后端。桌面端只改 `frontend/`，控制台只改 `frontend/`；配对协议、TLS 信任、Device Flow 端点、撤销授权、设备列表接口与轮询/在线状态一行不动。
2. 不新增第二份授权确认界面。控制台的批准动作（风险说明、核对代码、允许/拒绝、过期倒计时）继续只由既有的设备授权确认屏承担。
3. 配对/授权的校验契约不变：桌面端地址正则与 6 位配对码规则、控制台 6 位设备码规则均沿用现有实现。
4. 加载失败仍不得被渲染成「还没有设备」，两端都不得在加载失败时展开引导。
5. 新增可见文案一律走 i18n，两端各自的 zh-CN / en 两套 locale 齐备，不硬编码中文。

## Problem

桌面端与控制台的证据均取自源码（未跑真机取证；mockup 为按源码重建，见「相关链接」）。

### 桌面端「远端设备」页

1. **引导只在零设备时存在，配对第一台之后整块消失。** `devices.length === 0` 才渲染 `AgentredOnboarding`（`frontend/src/components/agentre/remote-devices/remote-devices-panel.tsx:191-197`）。这不是实现疏漏，而是前置规格 [2026-08-11 agentred 安装引导](./2026-08-11-agentred-onboarding.md) 决策 1（`:38`）与设计段（`:52`）「有设备时完全走现有设备列表，不出现引导」的直接后果 —— 用户故事 4（`:32`）「老用户不希望引导打扰我」被实现成了「老用户找不到引导」。
2. **第二次能拿到的只剩「已经会的那一步」。** 有设备后两个入口都指向 `AddDeviceDialog`，而它只给一句「在远端执行 `agentred pair`」加三个输入框（`add-device-dialog.tsx:63-88`）；安装命令、`service install`、系统切换、服务自检清单全都不在。第二台机器上真正缺的恰好是被删掉的前两步。
3. **零设备时两条入口并存，一条完整一条残缺。** 页头「添加 agentred」按钮无条件渲染（`remote-devices-panel.tsx:184-188`），与同屏展开的三步引导（`:191-197`）并列；点按钮直接开弹窗，跳过安装与服务两步。
4. **列表底部按钮渲染出两个加号。** 按钮同时有 `<Plus>` 图标与文案里硬写的 `+`（`remote-devices-panel.tsx:237` + zh-CN `remoteDevices.actions.continueAddLan` = `"+ 继续添加 agentred（LAN）"`，en 同形）。
5. **配对成功后的后续引导只有第一台能看到。** 「远端已连接 → 配置 Agent 后端」提示由引导路径的提交回调设置（`remote-devices-panel.tsx:192-197`），弹窗路径的提交回调不设置（`:348-355`）；而第二台机器同样需要配置它自己的 Agent 后端。

### web 控制台「设备」页

6. **整页没有任何添加设备的入口。** 页面全部动作都是对已有设备的：展开详情、查看对话、解除授权（`agentre-server/frontend/src/pages/Devices.tsx:644-714`）。用户在这里看得见设备，却无从得知怎么再接一台。
7. **空态只陈述事实，不给下一步。** `EmptyState` 只传了 icon 与 title（`Devices.tsx:686-689`，文案 `device.manage.empty` = 「还没有任何设备。」），而该组件本身支持 `body` 与 `action`（`components/console/EmptyState.tsx:16-25`）。新用户第一次进来看到的就是这一句话。
8. **输入设备码那一屏已经实现，但导航到不了。** 路由 `/device` 存在且支持 `?user_code=` 预填（`App.tsx:26-33`、`pages/Device.tsx:33-36`），但侧栏只有总览/对话/设备/审计四项（`components/AppShell.tsx:95-110`）。今天只有客户端打印或自动打开的那个链接能进去 —— 链接丢了就没有第二条路。

## Actors and user stories

1. 作为**已经接了一台机器、要接第二台的用户**，我希望在同一个地方拿到和第一次完全一样的安装与启动命令，不必回忆或去别处翻。
2. 作为**已经很熟的用户**，我希望一步就跳到真正要填的那一格，不必为了拿到输入框而点完前面所有步骤。
3. 作为**只想看看设备状态的用户**，我希望引导不要常年占着页面 —— 我不点它，它就不出现。
4. 作为**在浏览器里管理账号的用户**，我希望设备页自己就能告诉我怎么把一台机器接进这个账号，而不是只能看着已有的几台。
5. 作为**手里已经有一串设备码的用户**，我希望在控制台里找得到输入它的地方，而不是必须依赖客户端弹出来的那个链接。
6. 作为**刚注册、一台设备都没有的用户**，我希望空态直接把第一步摆在我面前，而不是告诉我「还没有任何设备」然后停在那里。

## Design decisions

| # | Decision | Basis and rejected option |
|---|---|---|
| 1 | 两端一致：引导的出现条件从「零设备」改为「零设备自动展开，或用户从唯一入口打开」。 | 用户裁决（2026-08-14）。问题 1/2/6/7 同源于把「不打扰老用户」实现成了「老用户不可达」；正确的做法是让它可召唤而非常驻。Rejected：列表上方常驻可折叠区 —— 页面常年多一段与当下无关的区块，且添加仍有两条入口、两份表单要各自维护。Rejected：把三步塞进弹窗 —— 2026-08-11 决策 1 当初正是以「塞不下命令 + 清单」否掉弹窗方案，该理由至今未变。 |
| 2 | 本轮推翻前置规格 [2026-08-11 agentred 安装引导](./2026-08-11-agentred-onboarding.md) 决策 1 的「有设备时不出现引导」与用户故事 4 的实现方式，并同时提交对该文件的修订。 | 代码与已提交规格不得对不上。该轮的其余决策（后台服务闭环、发布资产、版本、Windows IPC、加载错误态）全部不变，只修订与本轮冲突的那一句与那条用户故事的措辞。Rejected：只改代码、留着那份规格 —— 下一个读规格的人会把本轮的实现当成 bug 改回去。 |
| 3 | 桌面端删除 `AddDeviceDialog` 与列表底部的第二个入口，全页只留页头一个「添加 agentred」。 | 一个概念一条路径；顺带消掉问题 3（双入口）与问题 4（双加号）。配对表单本身（`DevicePairingForm`）不动，只是唯一宿主变成引导第 3 步。Rejected：保留弹窗当快捷方式 —— 那正是「第二次拿到残缺版本」的根源。 |
| 4 | 引导展开在设备列表**上方**，列表保持可见。 | 正要照着已有机器的地址与命名规律加下一台时，列表是有用的上下文。Rejected：展开时隐藏列表 —— 平白丢掉上下文，且收起后位置跳动。 |
| 5 | 步骤条三格改成可点的按钮，任意步骤间可直接跳转。 | 用户故事 2：熟手要的是输入框，不是流程。三格本来就并排显示，做成导航不增加任何界面元素。Rejected：只给「跳到最后一步」的快捷链接 —— 多一个只服务一种人的控件，而可点步骤条同时服务两种人。 |
| 6 | 完成标记 ✓ 只在用户点过该步自己的「下一步」时出现，不再由「序号小于当前步」推断。 | 决策 5 之后，跳步会让 `number < activeStep` 把没做过的步骤标成「已完成」/「正在运行」—— 那是界面在断言一件假事。点「我已安装」是用户的一次真实断言，跳步不是。Rejected：取消 ✓ —— 顺着走的首次用户会失去进度反馈。 |
| 7 | 桌面端「远端已连接 → 配置 Agent 后端」改为每一台配对成功都出现。 | 决策 3 之后只剩一条配对路径，问题 5 自动消失；且第二台机器同样需要配置自己的后端，这条衔接对它并不多余。Rejected：只在账号下第一台配对成功时显示 —— 那要新加一个「是不是第一台」的条件，去换一个对用户没有好处的区别。 |
| 8 | 控制台在设备页新增「添加设备」入口 + 同形的页内三步引导（装上并登录 → 输入设备码 → 让它常驻后台）。 | 问题 6/7/8。三步与桌面端同形，两端一套心智；步骤内容按控制台的真实路径写，不照抄桌面端的 LAN 配对。Rejected：只在空态加一句「去桌面端加」 —— 把用户推去另一个程序，且控制台本就具备完成授权的全部能力。 |
| 9 | 入口放在设备列表上方的动作行，不放进 52px TopBar。 | TopBar 右槽现有内容是信息（设备数、桌面端已连接），移动端还要放账号头像；在 52px 高度里混入主动作既拥挤又与既有语义打架。动作行在桌面与移动端形状一致，且不必改动 `AppShell`。Rejected：TopBar 右槽 —— 拥挤且移动端会与账号区争位。 |
| 10 | 控制台引导第 2 步收集 6 位设备码后，跳转到既有的设备授权确认屏（带上该设备码），不在设备页内嵌批准动作。 | 硬不变量 2。批准屏的风险说明、代码核对、过期倒计时已实现且经过评审（`device.approve.*`），复制第二份是纯负债且是安全相关界面。既有路由已支持预填设备码，衔接成本接近零。Rejected：在引导内直接完成批准 —— 两份安全界面必然漂移。 |
| 11 | 控制台命令里的服务器地址取当前控制台自己的地址，直接渲染进命令文本。 | 用户是在这个控制台上看这条命令的，地址不该让他手抄。与桌面端的差别是有依据的：桌面端不可能知道远端机器的地址，而控制台一定知道自己的。Rejected：渲染成占位符让用户自己替换 —— 一条本可以直接粘贴的命令被改成一道填空题，且填错的表现是「登录到了别的服务器」这种难查的错。 |
| 12 | 控制台的设备类型切换只有「计算节点（agentred）」与「桌面端」两种。 | 浏览器（`kind=web`）在用户打开控制台时就已经是列表里的一行，没有「添加」这件事；`kind=mobile` 今天没有可安装的客户端，给它一个入口就是承诺一个不存在的东西。Rejected：把四种 kind 都摆出来 —— 其中两种没有可执行的下一步。 |
| 13 | 两端各自实现、各自提交，不抽公共组件。 | 两个仓库、两套设计系统实例、两条完全不同的接入协议（LAN 配对 vs 账号 Device Flow），共享的只有信息结构。**已知重复**：步骤条这一视觉模式在两端各有一份；若将来出现第三处再评估抽取。Rejected：本轮抽公共包 —— 跨仓依赖的成本远大于一个步骤条。 |

## 桌面端：远端设备页

**唯一入口。** 页头保留一个「添加 agentred」按钮；设备列表底部不再有第二个添加入口。当引导正在展开时，页头这个按钮不渲染 —— 它的唯一职责就是打开引导，引导开着就不该有第二个入口。

**引导的出现条件。** 判断依据是**整页有没有设备行**，而不只是 LAN 配对行 —— 账号清单里的桌面端（含本机自己那一行）同样是页面上实打实的一行。整页一行都没有时，引导默认展开且不提供收起（没有可回退的地方）。只要页面上还有任何一行设备，引导就默认收起，绝不自作主张展开；用户点「添加 agentred」后它展开在设备列表上方，列表保持可见，并可通过步骤条右端的收起按钮关掉。加载中与加载失败沿用既有形态，两种情况下都不渲染引导。

**第一次与第 N 次完全一样。** 展开后呈现的就是既有的三步引导本身：安装（系统切换 + 安装命令 + 版本验证）、启动服务（后台/前台切换 + 服务命令 + 自检清单）、配对（配对命令 + 地址/配对码/名称表单 + TLS 信任入口）。内容、命令、文案不因「这是第几台」而改变。

**步骤条即导航。** 三格步骤都是按钮，可用鼠标点击也可用键盘聚焦激活，任意步骤之间可直接跳转；熟练用户由此一步到达配对表单。完成标记只加在用户点过该步「下一步」按钮的步骤上；直接跳过去的步骤不显示完成标记，其副标题保持未完成时的措辞。

**配对结果。** 提交沿用既有配对流程与校验：地址与配对码不合法时按现有规则就地提示且提交按钮不可用；配对失败时错误就地显示、已填内容全部保留、引导停在第 3 步。配对成功后引导收起，新设备出现在列表，并显示「远端已连接 → 配置 Agent 后端」的衔接提示 —— 每一台配对成功都显示，不再只有第一台。

**窄面板。** 设置页内容区在窄视口下步骤条堆叠为三行，命令区内部横向滚动，页面整体不得横向溢出。

## web 控制台：设备页

**入口与展开条件。** 设备列表上方新增一行动作，其中只有一个「添加设备」按钮；引导展开时该按钮不渲染。设备列表为空时引导默认展开（取代今天那句孤立的「还没有任何设备。」），且不提供收起；已有设备时默认收起，点按钮后展开在列表上方并可收起。设备列表加载失败时只显示既有错误提示，不展开引导、也不改口说没有设备。

**三步。** 装上并登录 → 输入设备码 → 让它常驻后台；三格都是可点按钮，完成标记的规则与桌面端一致。

**这个顺序不可调换**，它由 `state.json` 的所有权决定：`agentred login` 会一直阻塞轮询，直到用户在授权屏批准，那一刻才把账号凭据写进 `state.json`。daemon 只要在这之前起来，手里拿的就是旧的、未认领的那一份，它下一次写盘会不声不响地把认领覆盖掉——症状是设备看着授权成功、却永远连不上。因此**注册后台服务必须排在批准之后**，把服务注册放在登录之前（或与仍在轮询的登录并行）都会踩中这个覆盖。`agentred` 侧另有一道闸门在 daemon 运行时直接拒绝 `login`，但它拦不住这条路径——login 是在 daemon 起来之前过的闸。

- **第 1 步 · 装上并登录。** 顶部先选要接入哪种设备：计算节点（agentred）或桌面端。选计算节点时再选那台机器的系统，给出对应的安装命令，另给手动下载的退路；选桌面端时给出下载入口。界面同时说明浏览器不需要添加 —— 用户正在用的这个已经在列表里。装完紧接着给出登录命令，**命令里的服务器地址是当前控制台自己的地址**，可直接复制使用；并说明命令会打印 6 位设备码、会尝试自动打开浏览器、而没有浏览器的机器需要把码带回这里。桌面端一支给出同样的服务器地址与「设置 → 远端 → 登录」的路径说明。两支都说明设备码会过期、过期就重新发起一次，但**不写死具体时长**（有效期可配置，权威剩余时间由授权确认屏的倒计时呈现）。安装命令留在本步而不随登录上移——没有二进制就没有 `agentred login` 可跑。
- **第 2 步 · 输码。** 6 位设备码输入，形状与校验规则与既有的设备码输入屏一致。填满后提交即跳转到既有的设备授权确认屏并带上该设备码，由那一屏完成核对与批准。设备码不存在或已被使用时，沿用既有错误文案就地提示，已填内容保留。因为提交会跳走，本步另需一句把用户引回来的话——批准完还有最后一步。
- **第 3 步 · 常驻。** 计算节点给出「注册成后台服务」的命令，并说明它为什么必须排在批准之后（上面那条 `state.json` 的理由，用用户能懂的话）。桌面端一支说明它自带 agentred，没有第二个后台服务要注册。本步是末步，动作词是「完成」而不是「下一步」。

**不新增第二份批准界面。** 风险说明、代码核对、允许/拒绝、过期倒计时全部继续由既有授权确认屏承担；本轮不在设备页内复制其中任何一项。

**响应式与可达性。** 移动布局沿用设备页既有断点：动作行按钮占满宽度，步骤条堆叠为三行，命令区内部横向滚动；底部导航不变。步骤条按钮可键盘聚焦，当前步骤对辅助技术可识别。

## 跨端语义

两端各自实现、各自提交；共享的只有信息结构（一个入口 → 三步 → 第一次与第 N 次一致）与「引导可召唤、不常驻」这一条原则。桌面端加的是局域网直连的 agentred，控制台加的是账号下的设备，两者互不替代，也不因本轮产生任何新的跨端依赖。

## Out of scope

- **控制台里增删/编辑设备的其它能力**（改名、调整、批量操作）：本轮只解决「怎么加进来」。
- **`kind=mobile` 的接入引导**：今天没有可安装的移动客户端（决策 12）。
- **桌面端从控制台一键远程部署 agentred（SSH 推送）**：沿用 2026-08-11 规格的非目标。
- **两端共用一套引导组件 / 抽公共包**：决策 13。
- **控制台侧栏新增「授权设备」导航项**：本轮由设备页的引导承担这个入口；是否再给一个全局入口留待有真实需求时再评估。
