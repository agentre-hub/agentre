## 问题与目标

**目标：让远端 agentred 上执行的会话，其事件流以 agentred 为权威永久落库；任何客户端断开都不再终止会话，重连后能完整补齐断连期间产生的全部内容与待决策。**

**硬不变量：一个远端会话产生的每一条通知都以单调递增、无洞的 `seq` 落库；客户端凭 `seq` 游标补齐后收到的通知序列，必须与全程不断连时收到的序列逐条相等（method 与 payload 均相等，顺序相同）。**

### 问题

1. **事件出口绑死在单条连接上，连接一死事件就丢。** `internal/daemon/handlers/runtime.go:212-244` 的 `fanout` 把 backend 事件 channel 抽干后逐条推给 per-conn notifier（:224），推送失败只 `log.Printf` 一行然后继续下一条。没有持久化、没有缓冲、没有重放——那条事件就此消失。同一函数末尾的 `runtime.runResultDone` 终态帧（:239）与 `forwardAutonomousTurn` 的三类自主续轮通知（:264-291）走的是同一条路径，同样会丢。
2. **断连不杀子进程，只杀 PTY。** `internal/daemon/daemon.go:300-305` 在 `c.Done()` 后只调 `termH.CloseAll()` 与 `d.clearActiveNotifier(n)`；`internal/daemon/sessions/registry.go` 里的 chat session 不在清理范围内，agentruntime 子进程继续运行。所以断连期间事件确实在持续产生，且确实被第 1 条丢弃——"会话还在跑，但它说的话没人记"。
3. **桌面端把断连当作会话终止。** `remote.Runtime.watchClose`（`internal/pkg/agentruntime/runtimes/remote/runtime.go:104-140`）在 conn close 时把所有在飞 session 从 map 里摘掉，注入 `ErrDaemonDisconnected`（:133）并 `close(sess.events)`；日志措辞是"哪几个 session 是被 daemon 断连兜底关掉的"（:122）。即便 daemon 侧还在跑，桌面侧这一轮已经终结，且无法恢复。
4. **agentred 没有任何持久化。** `internal/daemon/state/state.go` 只维护一个 `state.json`（instance UUID / 配对 / provider 快照），`sessions.Registry` 是纯内存 `map[string]handlers.SessionHandle`。daemon 上根本不存在"会话历史"这个概念，因此也无从补齐。
5. **待决策的可见性依赖同一条死连接。** tool approval / ask 的 waiter 活在 daemon 进程内存里，按 `requestID` 定位（`internal/pkg/agentruntime/runner.go:187`、`:233`），决策经 `SubmitToolPermission` / `SubmitAnswer` "投回该 session 当前阻塞的 control 协议"（:213、:252）。断连**不会**解阻塞，但宣告"我在问你"的那条事件走第 1 条的路径被丢了。净效果是子进程无限期等待一个没有任何客户端知道存在的问题。
6. **桌面端无法在重启后定位会话跑在哪台 daemon 上。** `chat_entity.Session`（`internal/model/entity/chat_entity/session.go:33-63`）没有任何字段记录执行位置，也没有事件游标。即使 daemon 侧有了日志，桌面端进程重启后也不知道该连谁、从哪一条接着拉。
7. **断连后内置工具的隧道没有目标，且报错不可读。** MCP 反向隧道把 daemon 上 CLI 子进程的工具请求隧道回桌面执行——工具的实现与数据在桌面那一侧（`internal/daemon/handlers/mcpproxy.go:20-25`、`:77-101`）；隧道目标取自 `daemon.go:63-80` 的全局 `activeNotifier`，而连接断开时 `daemon.go:304` 立即把它清空，此后隧道一律返回 `503 mcp tunnel: no active desktop connection`（`mcpproxy.go:85`）。今天这条路径几乎撞不到——断连已经把会话终结了。**本规格让会话在断连后继续运行，于是它从死路变成常见路径**，而 LLM 收到的是一句没有任何语义的 503。
8. **（弱证据）缺口已被文档承认。** `docs/architecture.md:48` 写着 "A disconnect aborts the entire chat"；`internal/daemon/rpc/transport_hub.go` 整个文件只有一段注释，把 Hub 中转标为未实现的扩展点。这两处只证明缺口被承认过，不证明它造成了代价——代价由第 1、2、5 条给出。

## 用户流程

### 正常一轮（全程不断连）

用户在桌面端向一个远端会话发消息，事件实时流回、界面逐字更新，轮末收到终态帧。**这条路径的可观察行为与今天完全一致**：新增的落库发生在推送之前，用户看不出差别，除了通知帧里多了一个 `seq` 字段。

### 断连期间

网络中断、桌面 App 退出、或用户手动断开配对连接。daemon 侧子进程继续运行，产生的每一条通知先写入本地日志、再尝试推送；推送失败被忽略。会话的生命周期状态照常推进（`running` → `idle`）。桌面端侧会话**不**被终结，进入重连态；转录流里原本的打字指示器换成断连形态，告诉用户通道断了而远端仍在跑。

### 断连期间 agent 调用内置工具

会话继续跑，agent 调到一个需要隧道回桌面执行的内置工具。隧道此刻没有目标，返回一条说明「该工具需要发起端在线」的工具错误。agent 读到后自行调整——换个做法，或把这件事留到最后。会话不中断、不挂起。

### 重连补齐

桌面端重新连上同一台 daemon 后，对每条它还认得的会话按顺序走：先在本地钉住游标并以 `instance_uuid` 校验是同一个实例（只读桌面库，不发 RPC），再**显式接管**认领这条会话的推送流与控制面，然后按游标翻页拉取增量通知并按序重放，最后取该会话的待决策清单。重放走的是实时通知的同一套客户端 handler，因此界面最终状态与从未断连时相同。补齐完成后会话回到实时推送。

会话清单**不在**这条路径上：重连时本进程还认得自己那几条会话，逐条接管即可，问一遍全量清单只是白花一次往返。它用在另外两处——桌面 App **重启后**的补齐（本进程内一轮都没有在跑，只有清单说得清哪几条落下了内容、哪几条已被 daemon 标成中断），以及开轮前读一眼这条会话此刻的日志高水位（见「四个新 RPC」）。

### 待决策在断连期间产生

远端 agent 在无人连接时请求工具授权或提问。waiter 在 daemon 内存中阻塞等待，宣告事件写入日志。任何客户端重连后：该会话在清单里显示为等待输入，补齐时那条宣告事件被重放出来（审批卡片 / 提问卡片自然出现在会话里），待决策清单也会列出它。用户回答后，决策投回仍在阻塞的 waiter，会话继续。

### daemon 进程重启

daemon 重启会杀死所有 agentruntime 子进程——它们是 daemon 的子进程。日志在磁盘上完好保留。daemon 启动时把库里所有非终态会话标记为已中断。客户端重连后看到这些会话为中断态，能读到中断前的全部历史，但不能续跑，也不能回答中断前的待决策。

### 重连彻底失败

重连在退避重试超过上限后放弃（或用户主动解除配对），此时才向在飞会话注入 `ErrDaemonDisconnected`，行为回落到今天的语义。

### 老 daemon / 老桌面端

agentred 是独立部署的二进制，与桌面端版本不同步是常态，两个方向都必须可用：新 daemon 对老桌面端多发一个 `seq` 字段，老客户端忽略未知字段，行为与今天一致；新桌面端连老 daemon 时，新增的四个 RPC 返回方法不存在，桌面端据此判定该 daemon 不支持持久化，回落到今天的断连即终止行为，并在配对设备的状态里说明原因。

## 非目标

- **会话跨 daemon 重启存活。** 子进程随 daemon 进程消亡，为此设计意味着引入子进程托管与接管，是另一个量级的工作。
- **多客户端同时接入同一台 daemon。** 一条会话在任一时刻只有**一个**推送目标，daemon 不把同一条会话的通知向多个客户端扇出；`bindConn` 仍然每条连接把 `runtime.*` 重新注册进共享 registry。同一条会话被多个客户端同时消费，以及跨对端的可见性边界（见 R16），仍属下一轮（账号与中转）。

  **但推送目标本身不再是一个全局单值**——这一处围栏由 R4 推着落在了本规格范围内，不是下一轮的欠账。桌面端断连后是在**另一条**连接上重连的，而且它同时握着 2-3 条同指纹连接（连接池那条承载会话，设备状态心跳与刷新探测各占一条）。推送目标若仍是 `bindConn` 里静态捕获的那一个槽，重连补齐完成后通知只会推给一条已死的连接、或推给那条心跳连接（daemon 侧「成功」，发起会话的那条一条也收不到，既没有错误也没有 `seq` 跳号）——会话补齐了却一个字都不出，R4「断连不终止会话」形同虚设。所以 daemon 改为在**发送那一刻**按会话解析属主连接（`connRegistry`：`live` 记已鉴权的活连接，`claims` 记每条会话的属主连接）；接管的授权是**同指纹**，接管的动作是显式的 `runtime.session.attach`（以及任何被受理的 `runtime.*`，见 `trackSessionOwner`）。属主连接断开则该会话的登记随之撤销，通知照常落库、暂不推送。

  MCP 反向隧道的目标同理不再是全局单值。隧道请求来自 daemon 本机的 CLI 子进程（是 HTTP 不是 RPC），身上只有一个不透明 MCP token、没有会话标识，因此按「最近被认领的那条会话的属主连接」定目标；一条会话都还没被认领时回落到最近完成鉴权的那条活连接（桌面侧的隧道 handler 无状态，同一台设备的哪条连接送达都等价）；表空则无目标，按 R17 返回面向 LLM 可读的工具错误。
- **账号体系与经由 server 的中转接入。** `transport_hub.go` 保持为空的扩展点。下一轮（`2026-08-03-account-relay`）承接。
- **web 客户端。** 再下一轮。
- **桌面端本机会话的持久化改造。** 本机会话的真相源仍是桌面 SQLite，不受本规格影响。
- **待决策超时 / 自动决策。** 见实现决策 5。
- **日志脱敏收窄。** `runtime.go:231` 现在会把非高频事件的完整 payload 打进 daemon 日志，这先于本规格存在；本规格不扩大它，也不在本轮修它（属无关改动）。

## 行为要求

### R1 — 先落库，后推送

产生一条本该发给客户端的通知时，daemon 先以下一个 `seq` 把它写入日志，写入成功后才尝试推送。适用于全部五类通知：`runtime.event`、`runtime.runResultDone`、`runtime.autonomousTurn.started`、`runtime.autonomousTurn.event`、`runtime.autonomousTurn.done`。

### R2 — 推送失败不影响事实

推送返回错误（连接已死、写超时）时，该条通知已经落库，`seq` 已经推进，daemon 记一条日志后继续处理下一条通知。不重试、不阻塞、不回滚。

### R3 — 落库失败不推进 seq

落库返回错误时，`seq` **不**推进，该条通知也**不**推送。daemon 记 error 级日志。这保证日志中不会出现空洞：客户端拉到的连续 `seq` 就是完整序列。

### R4 — 断连不终止会话

客户端连接关闭时，daemon 不做任何会话级清理（现有的 PTY 关闭与 MCP 隧道撤销保持不变）。桌面端 `remote.Runtime` 不再注入 `ErrDaemonDisconnected`、不再 `close(sess.events)`，会话转入重连态并按退避策略重连。

### R5 — 补齐序列与不断连等价

给定同一次会话执行，"全程连接"收到的通知序列，与"中途断开若干次、每次重连后按游标补齐"最终收到的通知序列，必须逐条相等：method 相同、payload 字节相同、顺序相同、无重复、无遗漏。

### R6 — 推送帧携带 seq，跳号触发补洞

每条推送的通知帧携带其 `seq`。客户端收到 `seq == 本地游标 + 1` 时直接消费并推进游标；收到更大的 `seq` 时不消费该帧，转而从本地游标发起一次增量拉取，拉平后再继续；收到不大于本地游标的 `seq` 时丢弃（重复投递）。

游标只在两种情形下**倒退**，两种都是「本地游标指向 daemon 那边根本不存在的位置」，不复位则闸门会把此后每一条通知都判成跳号或重复，会话没有错误、没有跳号地冻住：

- 增量拉取交回的现存最老 `seq`（`oldestSeq`）大于「本地游标 + 1」——那段区间已经不在了，拿不回来。（~~原因是留存回收（实现决策 7）~~；决策 8 之后 agentred 不再回收，这一支只可能由库被从外部恢复或截断触发。**客户端这一侧的处理一字不改**：它无从分辨老前缀为什么没了，也不该分辨。）客户端把游标复位到 `oldestSeq - 1`，从现存最老的一行接着补，并留一条 Warn。复位必须发生在这一页重放**之前**，否则这一页的第一条当场被判成跳号丢弃，一条也交付不出去。
- 显式接管交回的高水位小于本地游标——那台 daemon 的通知日志退了（库被恢复 / 截断，而实例标识还在，R12 的校验因此照常放行）。客户端把游标归零、从头补齐，并把库里那份一并作废——只作废内存里那份的话，下次进程启动会把越界的老值原样读回来，同一个冻结再演一遍。

**已知限制：硬杀进程可能在转录里留下一段可见的重复。** 游标在内存里逐条推进，落库按 2 秒窗口合并写（一轮的终态帧那一条例外——它当场落库，否则用户拿到答案随手关窗就会让库里的游标停在这一轮中段）。正常退出、断连、放弃重连、游标作废都会主动落一次；但 `kill -9`、掉电、OOM 会丢掉最后那个窗口里的推进。而助手消息在一轮当中是**边跑边落库**的（抗 abort 的中途快照），于是下次启动的补齐会把那几条已经落过库的通知再重放一遍，用户看到同一段内容出现两次。

要精确去重，光有 `seq` 不够：日志行只记 `(method, payload)`，没有轮次身份，客户端拿一条重放上来的通知对不上「它已经落在我库里的哪一轮」。那需要通知帧带上轮次标识，本规格不做。

### R7 — 待决策在重连后可枚举

客户端可以查询某会话当前所有仍在阻塞的待决策，返回内容足以重建审批 / 提问卡片。查询结果来自 daemon 内存中的 waiter，不来自数据库。

### R8 — 提交幂等

同一 `requestID` 的决策提交多次时，第一次投回 waiter，其后各次返回成功且不产生副作用。对应 waiter 已不存在（已被回答、或会话已中断）时同样返回成功，而不是报错——客户端在断连重连后无法确定上一次提交是否送达，报错会让它误判。

### R9 — 待决策不超时

daemon 不为待决策设置任何过期时限。会话可以无限期停留在等待输入状态，直到被回答或被显式中止。

### R10 — 重启后标记中断

daemon 启动时，把库中所有处于非终态的会话标记为已中断。中断态会话的历史可读、不可续跑；对其提交决策按 R8 返回成功且无副作用。

### R11 — 等待输入不落库

会话在库中只记录必须跨进程存活的生命周期状态（运行中 / 空闲 / 已中断）。"正在等待输入"由 daemon 在返回会话清单时用实时 waiter 状态叠加计算，不写入数据库——它与 waiter 同生死，落库只会在重启后留下一条无法回答的记录。

### R12 — 游标与 daemon 实例绑定

桌面端为每个远端会话记录执行它的配对 daemon 及该 daemon 的 `instance_uuid`。重连时实例标识不匹配（daemon 重装、换机、数据目录被清）则判定该游标失效，不发起增量拉取，会话按已中断处理。

### R13 — 断连期间必须有区别于「思考中」的活信号

会话处于重连态时，转录流里原本的打字指示器换成断连形态：同一组点、同一动画曲线、节奏放慢一倍，加一个断线图形与一行内联短标签，说明连接中断且远端仍在运行。恢复连接后立即换回原形态。

这是本改动**新引入**的困惑所必需的：今天断连会把会话翻成失败态，用户至少知道停了；R4 之后会话继续显示为运行中，若不加区分，用户无法分辨「agent 在思考」与「网断了」。

### R14 — 补齐不夺走滚动位置

补齐重放的通知**逐条**经与实时同一个分发入口交付——「日志的一行 = 一条本该发出的通知」在结构上就要求如此，没有、也不需要一个把整段先攒起来再一次性渲染的机制。它与实时的差别只在节奏：拉回来多快就交付多快，不复现当时的速度。

判据因此是滚动位置：这段补进来的内容不得夺走用户此刻在看的位置。补齐产生了新内容且用户不在底部时，转录区底部浮出一个跳转控件，标明新增条数；补齐内容中含未回答的待决策时，同一控件额外标明待处理项数。点击跳到最新位置。用户本就在底部时沿用既有的贴底跟随行为，不出现该控件。

### R15 — 会话状态沿用既有四态，不新增取值

等待输入直接落在既有的 `waiting`（`markSessionWaiting` 已定义为「等用户操作」态，`needsAttention` 由它派生）。daemon 重启导致的中断映射到既有的 `error`，由消息文案区分其与真实错误。**不向 `AgentStatus` 增加第五个取值，也不向设计系统增加第五个 status token**——断连是运行态之上的连接态修饰，不是 agent 的运行状态。

### R16 — 会话身份带对端限定，保证跨对端唯一

daemon 侧的会话身份是（对端标识, 对端会话 id）的组合，不是对端会话 id 单独。两个不同对端各自持有同一个本地会话 id 时，它们在 daemon 上是两个不同的会话，各自的日志、游标与待决策互不干扰。

会话 id 是各客户端本地自增的，不同客户端必然重号。今天单客户端下这只是潜在冲突，本规格一旦把它固化为主键就变成持久化数据损坏；而配对模型本身（以设备指纹为键的对端表）从一开始就允许多个对端。

**这一条只解决身份唯一性，不定义可见性边界。** 本规格阶段 daemon 只认 LAN 配对、没有账号概念，多个配对对端不保证属于同一个人，因此查询与拉取一律限定在调用方自己的对端范围内——这是无账号前提下唯一安全的默认。引入账号后可见性边界会放宽到账号（同账号的桌面端与 web 端必须看到同一批会话，否则「关掉桌面端还能在手机上看」不成立），届时放宽的是过滤条件，主键结构不变。

### R17 — 隧道不可达时给出语义明确的工具错误

发起会话的客户端不在线时，内置工具的反向隧道没有目标。此时工具调用返回一条**语义明确、面向 LLM 可读**的错误，说明该工具需要发起端在线、当前不可达，而不是裸的 HTTP 503。会话继续运行，agent 自行决定改换做法或把这件事留到最后。

不挂起等待发起端回来：待决策等的是**人**（任何客户端都能答），这里等的是**特定机器**。那台桌面关一周，会话就卡一周，恰好抵消本规格「关掉客户端也照跑」的初衷。

### R18 — 能力探测与回落

桌面端在连上 daemon 后探测其是否支持本规格的四个 RPC。探测走**无副作用**的会话清单（开轮前问一次高水位时顺带完成）与重连时的显式接管，任一条回「方法不存在」即判定该 daemon 版本过旧。不支持时，该 daemon 上的会话沿用今天的断连即终止行为，且配对设备状态里说明该 daemon 版本过旧。

## 状态、数据与接口

### 日志的一行 = 一条本该发出的通知

这是本规格的核心结构选择。日志不建模事件类型，只记录 `(method, payload)` ——即那条本该经 WebSocket 发出去的 JSON-RPC 通知的原样。补齐就是按 `seq` 升序把它们重新投递给客户端的通知分发入口。

这样做使 R5 的等价性**结构上成立**而不只是被测试覆盖：补齐路径和实时路径投递的是同一个东西，客户端也用同一套 handler 消费。它同时让自主续轮的三类通知无需任何额外建模就被覆盖——它们本来就是通知。

### 会话生命周期

`running`（一轮执行中）→ `idle`（轮结束，等待下一轮）→ 可再次 `running`。任一状态遇 daemon 重启 → `interrupted`（终态）。"等待输入"不是这条链上的状态，它是 `running` 之上的一层实时叠加。

### 四个新 RPC

- **会话清单**（`runtime.session.list`）：返回该 daemon 上所有会话的标识、生命周期状态、是否正在等待输入、最新 `seq`。桌面 App 重启后的补齐由它起手；开轮前也用它读一眼本会话的日志高水位：一轮的开始不在 `seq` 时间线上（启动一轮的那条 RPC 不带 `seq`，日志载荷里也没有轮次身份），客户端靠这个高水位把「本轮自己的通知」与「日志里还没读到的旧通知」分开，否则补齐回放上来的上一轮终态帧会把刚发出的这一轮当场终结。同一条连接上每条会话只问一次，之后由游标接着跟——清单要为该对端的**每条**会话现算「是否正在等待输入」，成本随会话数增长，不该落在每一轮的启动路径上。**无副作用**，因此它同时是 R18 能力探测的入口。
- **显式接管**（`runtime.session.attach`）：客户端声明「这条会话此后由我消费」，daemon 受理后才把该会话的通知推送目标改到这条连接上。
- **增量拉取**（`runtime.session.pull`）：给定会话与起始游标，返回其后的通知（按 `seq` 升序）、新游标、是否还有更多，以及该会话此刻**现存最老的 `seq`**（`oldestSeq`）。daemon 对单次返回条数设上限，客户端按"还有更多"翻页直到拉平。
- **待决策查询**（`runtime.session.pendingWaiters`）：给定会话，返回当前仍在阻塞的 waiter 及其重建卡片所需的载荷。

`oldestSeq` 是「老前缀可能不在了」在读侧的对应物：这时一条会话的日志不再从 `seq=1` 开始，而落后的客户端游标正落在那段已经不存在的区间里。（~~它原本对应实现决策 7 的留存回收~~；决策 8 之后 agentred 恒从第一条开始报，但这个下界仍然要报、仍然要照它复位——见头部。）不报下界，它拉到的每一页第一条都比「游标 + 1」大，只会被 R6 的闸门当成跳号丢弃并再拉一次同一页——游标永远推不动，此后连实时通知也全被判成跳号，会话没有错误、没有跳号地冻住。客户端拿到它就知道那截尾巴是真的没有了，把游标复位到 `oldestSeq - 1` 接着补，并留一条 Warn。daemon 读不出下界时报 0（= 不知道），客户端一律不动游标。

**接管为什么必须是独立的一条 RPC**：清单只是「看一眼有哪些会话」，看一眼不该改变任何东西；拉取是只读补齐，而推送目标要在补齐**完成前**就改过去，不然补齐期间产生的实时通知只落库不推送。daemon 侧原有的认领是隐式的——任何被受理的 `runtime.*` 都会把该会话的流指向发起它的那条连接——补齐族刻意不走这条隐式路径，所以重连的客户端需要一个不含其它副作用的入口明说这件事。

### agentruntime 新增能力

现有 `ToolPermissionSink` / `AskAnswerSink` 只能按 `requestID` 投回决策，无法枚举。新增一个窄接口（`agentruntime.WaiterLister`）用于列出某会话当前的全部 waiter，由已有审批协议的 backend 实现——claudecode（`runtimes/claudecode/control.go`）与 codex（`runtimes/codex/runtime.go`）两家都实现了它。没有审批协议的 backend 不实现，调用方 type-assert 失败后回落空列表，不报错。

### 桌面端重连状态机

连接关闭 → 会话转入重连态（会话不关闭、事件 channel 不关闭）→ 退避重连 → 连上后校验 `instance_uuid` → 补齐三步 → 回到实时。重连尝试超过上限或用户主动解除配对 → 注入 `ErrDaemonDisconnected` 并按今天的路径收尾。

## 界面与交互

原型：`.dev-kit/artifacts/2026-08-01-agentred-session-durability/mockups/index.html`（**本地产物，不在 Git 里**）。下面的散文是判据，原型只是佐证；不打开原型也必须读得懂。

### 连接态是运行态之上的修饰，不是新状态

这是本节最重要的一条边界。设计系统的状态语言只有四态（`running` / `waiting` / `idle` / `error`），`docs/design.md` 要求状态一律经 `StatusDot` / `StatusPill` 渲染以保持点、胶囊、标签同步。「断连」不是 agent 的运行状态——远端此刻可能正在全速跑——它描述的是本机与远端之间的通道。把它做成第五个状态取值会污染整套状态语言，并让所有既有的状态判定点（退出确认的活跃态集合、侧边栏计数、工具栏禁用逻辑）产生错误归类。

因此断连只改变**活信号的形态**，不改变会话的状态取值。

### 转录流里的活信号

仓库已有两个同族指示器：打字指示器（三点跳动）与压缩上下文指示器（同样的三点 + 一行内联短标签，用于让用户知道这段时间不是普通回答）。断连指示器是它们的第三个兄弟，沿用同一组点尺寸、同一 `typing-dot` 动画曲线，仅把周期放慢一倍，并配一个断线图形与一行短标签。

它不是横幅：它出现在转录流中打字指示器原本的位置，随内容滚动，不横贯顶部、不挤压布局、不常驻。压缩指示器已经确立了「内联短标签」在这个位置是可接受的实践。

按 `docs/design.md` 的动效约定，该动画必须带 reduced-motion 修饰；降级后以静态低透明度呈现，信息不丢失。

### 补齐时刻

用户离开一小时回来，要的是结果，不是一场按原速的回放。补齐按日志顺序把内容逐条补进转录流，只受拉取速度限制；用户的滚动位置不受影响。滚动锚点机制已经存在且已处理过「内容增长把底部推远时不得关掉跟随」这一情形，补齐复用它，不另起一套。

补齐后若用户不在底部，转录区底部浮出一个跳转控件。它承载两类信息：新增了多少条，以及**其中有没有等你拍板的事**。第二类用既有的 `waiting` 状态色点表达。这一条不是装饰——待决策卡片可能埋在上百条补齐内容的中间，没有这个入口，用户要靠手动翻找才能发现远端正在等他。

### 中断态会话

daemon 重启导致的中断在会话里表现为一条终态消息，措辞需与真实的运行错误区分（是被打断，不是跑失败）。中断前的全部历史可读；用户可以直接发新消息开始新一轮。对中断态会话提交决策按 R8 静默成功。

### 配对设备

设备级在线状态已经存在于配对设备面板。R18 的版本过旧提示落在同一处，作为该设备的一条说明，不进入聊天界面——它是设备属性，不是会话事件。

## 安全、隐私、兼容性与可访问性

- **隐私**：transcript 落在 agentred 所在机器的本地磁盘（~~至少留存一个窗口~~ → 决策 8 之后**永久保存**，见下条），含完整工具输出、文件内容与 diff。数据目录沿用现有的 `0700` 权限（`cmd/agentred/run.go` 建目录时即用该模式）。本规格只走 LAN 直连，不引入任何网络外发。**但不要据此把整个产品读成 local-only**：后续的 server 中转已定为明文可转发，届时实时流会经过 server；那是那一轮的隐私边界，与本规格「落库只在本地」并不矛盾，但需要各自单独承诺。
- **磁盘增长**：~~默认保留 30 天（实现决策 7），daemon 起手扫一次、之后每 6 小时扫一次。回收只碰「整个留存窗口内一条新通知都没有、且 daemon 记着的生命周期已是终态（`idle` / `interrupted`）」的会话，并且**永远保留它的高水位那一行**；还在产出的会话、还在跑的会话、库里查不到会话行的孤儿日志，一行都不动。窗口经 `Options.JournalRetention` 可调，负数把回收整个关掉（回到永久保留）。~~→ **决策 8 之后没有任何回收**：日志永久保存，`Options.JournalRetention` 已删除，因此**本地库无上限增长**，而 agentred 常跑在小机器上——这是那条决策明确接受的已知代价，清理单开一轮做。库文件的路径与体量在 daemon 状态查询里可见——IPC 的 `/local/status` 与 `agentred status` 的输出两样都带，用户据此自行判断何时清理。经 LAN 发给已配对对端的 `health.ping` 只带体量：路径是绝对路径、通常含宿主机的 OS 用户名，而它的读者是坐在这台机器前面的人，不是每一个配对过的对端。
- **兼容性**：双向都必须可用，见「用户流程 / 老 daemon 老桌面端」与 R18。新增字段一律可选，老端忽略即可。
- **回滚**：agentred 侧迁移提供 Rollback；桌面端新增的三列可空/带默认值，回滚到旧版本桌面端时被忽略，不影响既有功能。
- **可访问性**：断连活信号带 reduced-motion 降级（`docs/design.md` 要求每个动画自带该修饰，本项目不依赖全局 reset），降级后以静态低透明度呈现，信息不丢失；断连与思考中的区别不仅在动画节奏，还有断线图形与文字标签，因此对动效不敏感与色觉受限的用户同样可辨。跳转控件是可聚焦的按钮，其「有待处理」信息除状态色点外另有文字。
- **权限边界**：本规格不改变鉴权模型。四个新 RPC 与既有 `runtime.*` 一样走 `wrapGuarded` 的 `requireAuth`，未配对连接拿不到任何会话数据。

## 实现决策

| # | 决策 | 理由（及被否方案） |
|---|---|---|
| 1 | 日志的一行是"一条本该发出的通知"，不建模事件类型 | 使 R5 的等价性结构上成立，且自动覆盖自主续轮的三类通知。否：按事件类型建表——补齐路径要重新拼装通知，与实时路径产生第二套代码，等价性只能靠测试保证 |
| 2 | 仓储与迁移放 `internal/daemon/repository` + `internal/daemon/migrations` | `internal/daemon/*` 是自成体系的子系统（client / handlers / rpc / sessions / state / pairing 均不走 cago 分层）。否：复用桌面的 `internal/repository/` 与 `migrations/`——会让桌面 App 的 composition root 注册只有 daemon 用的东西，且两套迁移列表混在一个 `migrationList()` 里 |
| 3 | 用 `db.WithContextDB` 注入句柄 | 见「持久化数据变化 / 数据库句柄的传递」。否：`db.SetDefault`——包级全局会让同进程内多个 Daemon 实例互相顶掉句柄，静默破坏既有集成测试 |
| 4 | 不建待决策表，查询直读内存 waiter | 待决策与阻塞中的 waiter 同生死。否：落库——唯一好处"跨重启存活"是假的，存活下来的是一条永远无法回答的记录，且立刻产生第二个真相源 |
| 5 | 不做超时 / 自动决策 | 超时即自动拒绝，等于替用户做决定，与"挂起等人"直接冲突。资源占用用既有的 `runtime.abort` 手动解决。否：TTL 过期 |
| 6 | daemon 重启不保会话 | 子进程是 daemon 的 child，进程消亡它必然消亡；为此设计需引入子进程托管与接管。否：会话跨重启接管 |
| 7 | ~~transcript 默认保留 30 天，只回收「安静满整个窗口的终态会话」高水位以下的那截前缀~~ **已被 [`2026-08-18-server-session-mirror.md`](2026-08-18-server-session-mirror.md) 决策 8 整个推翻**（2026-08-18 用户裁决）：两端都永久保存，agentred 的回收一并去掉 | 当初的依据：远端盒子上的会话历史是档案不是缓冲，判据是「这段还有没有人会来取」而不是「攒了多少」。**推翻它的是同一条依据走到底**——决策 8 认定「用户删了才少，别的什么都不会让内容悄悄消失」，而按窗口回收恰恰是在悄悄消失。当初写下的「否：完全不回收——会把库写到 GB 级且没有任何回收路径」现已被接受为已知代价，清理另开一轮。**高水位那一行永不删这一条与它一同消失，但它保护的东西还在**：删了该会话 `MAX(seq)` 归零，追加写会从 1 重新分配 `seq`，而客户端游标还停在旧高水位上，此后每条实时通知都被当成重复丢弃、会话无声冻住——不回收即天然不触发，读侧的 `dropCursorAboveHighWater` 仍然守着它 |
| 8 | 生命周期状态落库，等待输入不落库 | 「日志存事实，内存存现状」。否：把等待输入也写成状态列——重启后与内存必然不一致 |
| 9 | 老 daemon 走能力探测回落，不做硬性版本门禁 | agentred 独立部署，强制升级会让用户在升级完成前完全用不了远端执行。否：版本号门禁 |
| 10 | 断连做成运行态之上的连接态修饰，不进 `AgentStatus`、不加第五个 status token | 见「界面与交互 / 连接态是运行态之上的修饰」。否：新增 `disconnected` 状态取值——`AgentStatus` 被退出确认、侧边栏计数、工具栏禁用等多处判定消费，新增取值要扫遍所有判定点，且会把「通道断了」错误地表述成「agent 的运行状态」 |
| 11 | 断连活信号做成打字指示器的第三个同族形态（同点、同曲线、慢一倍 + 图形 + 内联短标签） | 压缩上下文指示器已确立同一位置上「点 + 内联短标签」的实践，复用它零新增布局。否：composer 上方的状态条——那是解释性横幅，且短暂断连时会频繁闪现顶得内容跳动；否：完全不区分——用户无法分辨 agent 在思考与网断了，是本改动新引入的困惑 |
| 12 | 补齐静默落定 + 保持滚动位置 + 底部跳转控件 | 用户离开后回来要的是结果不是回放；滚动锚点机制已存在可复用。跳转控件必须同时承载「有无待处理」，否则待决策会埋在上百条补齐内容中间。否：逐条按原速回放（断连一小时就回放一小时，且待决策要等回放到那一刻才能答）；否：渲染完直接滚到底（正在翻历史的用户会被夺走位置） |
| 13 | 中断态映射到既有 `error`，靠文案区分 | 用户视角里「被 daemon 重启打断」就是这轮没跑完，与 error 同构，可直接发新消息续上；daemon 库里仍区分 `interrupted`，只是桌面端状态收敛。否：新增 `interrupted` 状态取值——同决策 10 的成本 |
| 14 | daemon 侧会话身份用（对端标识, 对端会话 id）复合键，对端标识取已有的设备指纹 | 见 R16。对端会话 id 是各客户端本地自增的，必然重号；本规格把它固化成主键，单键会在多对端时变成持久化数据损坏，且配对表本身早已允许多对端。取设备指纹是因为配对模型已经以它为键，不需要引入第二套身份。否：单用对端会话 id（把冲突写进主键）；否：daemon 自行分配不透明 id（客户端要多维护一张映射表，且断连重连时无法凭本地 id 找回自己的会话） |
| 15 | 隧道不可达时返回语义错误让 agent 继续，不挂起会话 | 见 R17。待决策等的是人（任何客户端都能答），隧道等的是特定机器；那台桌面关一周会话就卡一周，与本规格初衷相反。否：挂起等发起端回来；否：让同账号的其它客户端代答——内置工具的实现与数据在发起端本地，别处执行结果不同（`mcpproxy.go:20-25`），web 端更是根本没有 |
| 16 | 不写单独的验收标准列表 | 「行为要求」各条已按"前置—动作—可观察结果"写成可直接建检的形式；再维护一份平行的验收列表意味着两份需要保持一致的副本，而具体命令与判定属于实施轮。否：仓库既有 spec 的 R+A 双列表体例 |

**刻意的取舍**：

- **不进 e2e。** Playwright harness 跑得动，但断连正确性已被第一条接缝以更低成本证死；e2e 只能额外验界面显示，那部分归前端组件测。为一个网络时序场景搭 e2e 编排，收益不抵维护成本。
- **靠人工验证的部分**：真机拔网线、杀掉桌面进程后重开、重启 daemon 三个场景下的活信号形态、补齐结果与跳转控件。真实的进程生命周期、窗口重建与「离开一小时后回来」的时间尺度在 fake 环境里模拟不出来，而后者恰恰是本规格的目标场景。按 `docs/verification.md` 留证据到 `e2e/scratch/2026-08-01-agentred-session-durability/`。
- **覆盖较弱的部分**：R18 的能力探测回落只能用构造出的"缺失方法"假 daemon 验证，无法验证真实老版本二进制的全部行为差异。
